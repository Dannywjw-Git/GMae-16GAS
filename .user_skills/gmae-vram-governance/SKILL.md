# GMae 显存管理最高指南（VRAM 铁律）

> **地位**：显存管理的唯一权威规则，优先级高于一切实施方案/运维脚本/个人习惯。
> **适用范围**：所有调用 GPU 显存的应用——Ollama、ComfyUI、Fooocus、rerank、游戏串流、语音三件套，以及未来任何新增占显存服务。
> **完整文档**：`references/显存管理最高指南_完整版.md`（本文件为核心提炼，细节以完整版为准）

## 何时使用

- ✅ 任何涉及 GPU 显存的操作前（出图/视频/音乐/游戏/部署/改参数）
- ✅ 新模型/新服务上线前的准入评估
- ✅ >5GB 模型运行前的显存可行性判断
- ✅ 显存异常/死机/OOM 后的根因排查
- ❌ 纯 CPU 任务（不涉及显存）

## 一、硬件硬约束（不可改变的底线）

| 项 | 值 | 说明 |
|----|-----|------|
| GPU | RTX 4060 Ti **16GB 单卡** | 无扩展，任何方案都绕不开 16G 天花板 |
| 固定底噪 | **~1.0~1.1G（空载）** | Ollama 空载 + ComfyUI 空闲 + 桌面，随桌面程序浮动 1.5~4G |
| 实际可给 AI 负载 | **~15G（空载）** | 16 - 1.0；保守按 12.9G 算 |
| 物理内存 | 32GB | 显存爆炸会牵连打满换页死机 |

> ⚠️ 教训：显存打满 → GPU 模型加载失败 → Ollama 重试循环 → 内存泄漏 → 物理内存打满 → 系统死机。**显存必须永远留余量，这是死机红线，不是性能问题。**

## 二、四大稳态与切换规则（状态机核心）

> 全系统任意时刻必须处于且仅处于一个稳态；**状态切换必须先释放对方资源，不许"边用边挤"**。

| 稳态 | 允许占用 | 合计 | 余量 |
|------|---------|------|------|
| **对话态**（默认） | 9B(6.6) + 底噪(1.0~3.1) | ~7.6~9.7G | ✅ |
| **SDXL 出图态** | SDXL(6.5) + 底噪 | ~7.5~9.6G | ✅（9B 需让位） |
| **Flux 出图态** | Flux(13) + 底噪 | ~14~16.1G | 🔴 极限，桌面程序尽量关 |
| **音乐态（Music3）** | Music3 峰值 14.5~15.1G + 底噪 | >16G（动态加载压缩至 16G 内） | 🔴 独占全卡 |
| **游戏态** | 游戏(2-4) + 底噪 | ~3~7.1G | ✅ 宽松 |

**切换规则：**

| 切换 | 必须动作 | 工具 |
|------|---------|------|
| 对话 → 出图 | ① 停 Fooocus ② `ollama stop` 全部模型 ③ 确认显存 <4G | `gpu_release.ps1` |
| 出图 → 对话 | 无需手动（Ollama 按需加载自动拉起） | keep_alive 到期自动卸载 |
| 对话/出图 → 游戏 | 释放全部 AI 模型 + 停文生图容器 | `game-on.ps1` |
| 对话/出图 → 音乐 | ① 停 Fooocus ② `gpu_release.ps1` ③ 起 ComfyUI ④ 确认 :8188 就绪 | 控制台 |

> 🔴 切换纪律：**先释放、后占用、再验证**。释放后必须用 `nvidia-smi` 确认水位达标再启动目标负载。

## 五、新服务准入流程（占显存应用上线 Checklist）

> 任何要碰 GPU 显存的新应用（新容器/新模型/新脚本），上线前必须逐项过：

| 步骤 | 检查项 | 通过标准 |
|------|--------|---------|
| 1 | 算账 | 查账本：峰值显存 + 允许状态 |
| 2 | 共存 | 按状态机逐组合核算，确认不会挤爆任一稳态 |
| 3 | 释放机制 | 提供"释放自身显存"的明确动作（stop/卸载/参数） |
| 4 | 启动参数 | 带 `--reserve-vram` 或等价预留 |
| 5 | 实测峰值 | 真实跑一次，记录峰值显存（≠理论值） |
| 6 | 登记 | 更新账本 + 变更记录 |

**未过 1-6 的服务 = R7 违规，不得上线。**

## 六、大模型显存评估清单（M10 操作细则）

> **适用场景**：任何 >5GB 的新模型首次运行前，或现有模型更换量化方式/参数前。

### 评估步骤

1. **查模型文件大小**（safetensors/gguf 文件大小 ≈ 最小显存）
2. **确认量化方式**（fp16/int8/int4/fp8/nvfp4 等）
3. **估算中间计算开销**：
   - LLM：+10-20%（KV cache）
   - 文生图：+20-30%（VAE 解码、注意力）
   - 文生视频：+30-50%（时序注意力、帧缓存）
   - 文生音乐：+20-30%（音频 latent）
4. **计算峰值显存**：
   ```
   峰值显存 ≈ 模型文件大小 × (1 + 中间计算比例) + 系统底噪(1-3GB)
   ```
5. **对比物理上限**：
   - 峰值 < 14GB：✅ 安全（留 2GB 余量）
   - 14GB < 峰值 < 15.5GB：⚠️ 极限（需关闭其他服务、桌面程序）
   - 峰值 > 15.5GB：❌ **不可行，不要尝试**

### 已知模型显存参考表

| 模型 | 量化 | 文件大小 | 峰值显存 | 16GB可行性 |
|------|------|---------|---------|-----------|
| qwen3.5:9b | Q4_K_M | 6.6GB | ~8GB | ✅ |
| SDXL | fp16 | 6.5GB | ~7GB | ✅ |
| Flux-dev | Q5_K_S | 7.7GB | ~13GB | ⚠️ 极限（独占） |
| Music3 | fp8 | 13GB | ~10GB | ✅ |
| Music3 | fp16 | 13GB | ~15GB | ⚠️ 极限（独占） |
| MiniMax H3 | int8 | 52GB | >20GB | ❌ 不可行 |
| Wan2.2-TI2V-5B | FP16 | 9.3GB | ~10.9GB | ✅ |

### 评估不通过时的选项

1. 换更轻量的量化（fp16 → int8 → int4）
2. 换更小的模型（27B → 9B → 0.6B）
3. 走云端 API（MiniMax API、即梦等）
4. 升级硬件（24GB / 48GB 显卡）

## 八、巡检与违规处置

### 例行巡检阈值

| 项 | 阈值 | 动作 |
|----|------|------|
| 显存水位 | >14G 持续 | 🔴 告警：找白占方 |
| ollama.exe 已提交内存 | >500MB 持续增长 | 🔴 泄漏信号：kill 重启 |
| 11434 假死 | LISTENING + 请求超时 | kill 重启 + 刷新 OWUI |
| 双 ollama serve | 进程数 >1 | 收敛到单 serve |
| Fooocus 容器 | 对话态仍 Up | `docker stop fooocus` |

### 违规处置流程

1. 识别违规方（账本对照 + nvidia-smi 实测）
2. **立即停用违规方**，恢复稳态
3. 记录到账本 + 当日 memory，复盘根因
4. 屡犯不改的服务 → 下线整改后再准入
