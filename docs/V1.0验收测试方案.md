# GMae-16GAS V1.0 验收测试方案

> **目的**：通过模拟真实 AI 工作场景的压力测试，验证 GMae 是否按预期工作、功能是否用户真正需要。全部通过后方可标记 V1.0 正式发布，并准备介绍文档和演示视频。
> **创建**：2026-09-01
> **环境基线**：Windows + WSL2 + Docker，16GB GPU（RTX 系列），ComfyUI/Ollama 容器运行中

---

## 测试原则

1. **模拟真实场景**：每个测试对应一个真实用户行为，不是人造的技术测试
2. **可量化通过标准**：每个测试有明确的数字阈值，不是"看起来正常"
3. **可重复执行**：测试脚本自动化，可反复运行
4. **不破坏系统**：测试后恢复环境，不留残留进程/模型
5. **安全优先**：高负载测试严格控制显存上限，绝不打满死机

## S01：冷启动健康检查

**模拟场景**：用户刚开机，双击启动调度中心，服务刚起来，还没加载任何模型。

**测试步骤**：
1. 确认服务运行中（/api/health 返回 ok=true）
2. 调用 /api/status，记录返回的显存数据
3. 与 nvidia-smi 实际数据对比
4. 检查服务列表（ComfyUI/Ollama 容器状态）

**预期结果**：
- health.ok = true
- gpu.free_mb 与 nvidia-smi 误差 < 200MB
- gpu.total_mb = 16384（或实际物理值）
- 服务状态与 docker ps 一致
- 响应时间 < 2 秒（冷路径）

**通过标准**：显存数据误差 < 200MB，服务状态准确，响应时间 P95 < 2s

---

## S02：进程级显存感知准确性

**模拟场景**：用户在 OWUI 里开始和 qwen3.5:9b 对话，Ollama 加载了模型。

**测试步骤**：
1. 记录基线显存（无模型加载）
2. 通过 Ollama API 加载 qwen3.5:9b（发一条消息触发加载）
3. 等待模型加载完成（ollama /api/ps 显示模型）
4. 调用 /api/status，检查进程账本
5. 对比：GMae 报告的 ollama 显存 vs nvidia-smi 实际占用
6. 测试完释放模型

**预期结果**：
- 进程账本中出现 ollama/llama-server 进程
- 该进程显存占用与 nvidia-smi 实际差值 < 10%
- 模型名称正确识别
- 显存水位条正确反映占用

**通过标准**：进程级显存误差 < 10%，模型识别正确，无遗漏进程

---

## S03：预算引擎决策准确性

**模拟场景**：用户想跑 Flux.1 dev（约 12GB），但当前已经加载了 qwen3.5:9b（约 6GB），用户点预演模式看能不能跑。

**测试步骤**：
1. 加载 qwen3.5:9b（约 6GB）
2. 调用 /api/budget?model=flux，记录返回的决策
3. 手动计算：总量 - 系统底噪 - 已用 - Flux 标称 = 是否够
4. 对比 GMae 决策与手动计算
5. 测试 context 覆盖（196K context 时显存重算）
6. 释放模型

**预期结果**：
- budget.decision 正确（ok / free_L1 / free_L2 / reject）
- budget.needed_gb 与手动计算差值 < 1GB
- context 覆盖时显存重算正确
- 独占模型（exclusive=true）触发强制释放建议

**通过标准**：预算决策与手动计算一致，显存差值 < 1GB

---

## S04：场景切换正确性

**模拟场景**：用户上午在写代码（对话态），下午想做图（出图态），点场景切换按钮。

**测试步骤**：
1. 确认当前场景（如对话态）
2. 加载对话模型（qwen3.5:9b）
3. 调用 /api/scene 切换到出图态
4. 观察：Ollama 模型是否被释放，ComfyUI 是否就绪
5. 切换后调用 /api/status，验证显存水位
6. 切回对话态，验证恢复

**预期结果**：
- 场景切换后，前一场景的模型被释放
- 新场景的服务就绪
- 切换日志记录正确
- 显存水位与预期一致
- 切换耗时 < 30 秒（模型级释放，非容器重启）

**通过标准**：切换后无残留模型占用，显存水位正确，切换耗时 < 30s

---

## S05：秒级释放验证

**模拟场景**：用户跑完图后，点"一键释放"，想快速把显存腾出来跑视频。

**测试步骤**：
1. 加载 ComfyUI 模型（SDXL 或 Flux）
2. 记录释放前显存
3. 调用 /api/free（ComfyUI /free 接口）
4. 每秒采样显存，持续 10 秒
5. 记录显存下降到稳定值的时间
6. 对比：容器级重启（docker restart）需要多久

**预期结果**：
- /free 后 5 秒内显存下降 > 模型大小的 80%
- 10 秒内显存稳定
- ComfyUI 容器仍在运行（只是卸载了模型）
- 释放后可立即加载新模型

**通过标准**：5 秒内释放 > 80% 显存，对比容器重启（10-30 秒）有数量级优势

## S06：高负载逼近上限（危险测试）

**模拟场景**：用户贪心，同时开了对话+出图+视频，显存快满了。

**⚠️ 安全约束**：
- 严格监控显存，空闲 < 1GB 时立即中止测试
- 绝不允许显存打满（16GB 打满 = 系统死机）
- 自动防死机功能默认关闭，测试时手动观察预警是否正确

**测试步骤**：
1. 记录基线（空闲 ~14GB）
2. 逐步加载模型：qwen3.5:9b（~6GB）→ SDXL（~7GB）→ 观察显存
3. 在每个水位记录 danger_level（safe/warning/danger/critical）
4. 当空闲 < 2GB 时，验证：
   - danger_level = danger 或 critical
   - 前端顶部危险指示器闪烁
   - /api/advice 返回智能建议
   - 紧急操作弹窗出现（critical 时）
5. 立即释放所有模型，恢复安全水位

**预期结果**：
- danger_level 随水位正确升级（safe>4GB → warning 2-4GB → danger 1-2GB → critical<1GB）
- 预警及时（水位变化后 3 秒内更新）
- 建议内容合理（"建议释放 XX 模型，可释放 Y GB"）
- 不死机（测试全程空闲 > 500MB）

**通过标准**：danger_level 准确，预警延迟 < 3s，建议合理，全程不死机

## S07：门卫未登记进程检测

**模拟场景**：用户偷偷开了一个不在白名单里的 GPU 程序（比如另一个 AI 工具），门卫应该发现并告警。

**测试步骤**：
1. 确认当前无未登记进程
2. 启动一个会占用 GPU 的进程（如用 Python 跑一个小 CUDA 程序，或启动未登记的容器）
3. 计时：门卫多久能检测到
4. 检查：
   - 门卫页出现未登记进程告警横幅
   - 进程明细中标记为"未登记"
   - 系统日志记录了检测事件
   - 建议驱逐操作可用
5. 停止测试进程，验证告警消失

**预期结果**：
- 检测延迟 < 5 秒（门卫轮询周期）
- 进程名、PID、显存占用正确
- 告警横幅显示正确
- 驱逐操作（L0 warn / L1 ask / L2 kick）按配置执行
- protect 类进程（dwm/explorer）不被误报

**通过标准**：检测延迟 < 5s，信息准确，不误报系统进程

---

## S08：任务队列串行执行

**模拟场景**：用户一次丢了 3 个生成任务（出图+视频+音乐），GMae 应该排队串行执行，不能并发（16GB 卡物理上不能并发）。

**测试步骤**：
1. 确认队列为空
2. 同时提交 3 个任务（通过 /api/queue）
3. 观察队列状态：
   - 第一个任务执行中，后两个排队
   - 第一个完成后第二个自动开始
   - 全程无两个任务同时执行
4. 检查每个任务的状态变化（排队→预检→释放→加载→生成→完成）
5. 验证取消功能（取消第三个任务）

**预期结果**：
- 任务严格串行，无并发
- 队列状态实时更新
- 任务完成后显存正确释放
- 取消功能正常
- 任务日志完整

**通过标准**：无并发执行，队列状态正确，取消功能正常

---

## S09：长时间稳定性（耐力测试）

**模拟场景**：用户一整天开着调度中心，频繁切换场景、轮询状态，看会不会内存泄漏或崩溃。

**测试步骤**：
1. 记录 server.py 初始内存占用
2. 持续 60 分钟：
   - 每 10 秒调用 /api/status（模拟前端轮询）
   - 每 5 分钟切换一次场景
   - 每 10 分钟加载/释放一次模型
3. 每分钟记录：
   - server.py 内存占用
   - API 响应时间（P50/P95/P99）
   - 错误数
4. 60 分钟后对比初始和最终内存

**预期结果**：
- 内存增长 < 50MB（无明显泄漏）
- API 响应时间 P99 < 2 秒
- 零崩溃、零 500 错误
- 看门狗无异常重启

**通过标准**：60 分钟内存增长 < 50MB，P99 < 2s，零崩溃

---

## S10：异常恢复（看门狗测试）

**模拟场景**：server.py 意外崩溃（比如代码 bug），看门狗应该自动重启。

**测试步骤**：
1. 确认看门狗运行中
2. 记录 server.py PID
3. 强制 kill server.py 进程（taskkill /F /PID）
4. 计时：多久后新的 server.py 启动
5. 验证新进程的 /api/health 返回 ok
6. 检查看门狗日志记录了崩溃和重启

**预期结果**：
- 看门狗 5 秒内检测到 server 死亡
- 10 秒内启动新 server.py
- 新进程 health ok=true
- 看门狗日志记录了崩溃原因和重启时间
- 1 小时内重启次数 < 10 次（防失控）

**通过标准**：重启时间 < 10 秒，服务恢复正常，日志完整

## 测试执行顺序

按风险从低到高、依赖从少到多：

1. **第一批（无模型依赖，可立即跑）**：S01、S03（预算模拟）、S10（看门狗）
2. **第二批（单模型加载）**：S02、S05
3. **第三批（多模型/场景切换）**：S04、S07
4. **第四批（高风险/长时间）**：S06（高负载，需人工监控）、S08（队列）、S09（60分钟耐力）
