### P0-1：中间层反向依赖修复（架构整改）

**问题**：7个文件违反依赖方向铁律
- engine/ → services/：budget.py, eviction_guard.py, qos.py, reaper.py, scanner.py（5个）
- core/ → engine/：docker_events.py, logger.py（2个）

**目标**：所有层依赖方向正确，engine/core 层可独立 import 和测试

**具体方案**：

#### 步骤1：事件总线下移（解决 core→engine 反向依赖）

- 将 `engine/event_bus.py` 移到 `core/event_bus.py`
- 更新所有引用：`from engine.event_bus import event_bus` → `from core.event_bus import event_bus`
- 验证：`python -c "import core.event_bus"` 无需启动服务

**工作量**：0.5天

#### 步骤2：engine 层数据获取上移（解决 engine→services 反向依赖）

**原则**：engine 层只接收纯数据，不调用 services 层获取数据

**改造模式**：

```python
# 错误（当前）：engine/budget.py 自己调用 services
from services.docker import docker_containers
from services.ollama import ollama_ps

def calculate_budget():
    containers = docker_containers()
    models = ollama_ps()
    ...

# 正确（整改后）：engine/budget.py 接收数据作为参数
def calculate_budget(containers: list, models: list) -> Budget:
    """计算显存预算
    Args:
        containers: 容器列表（由调用方获取）
        models: 模型列表（由调用方获取）
    Returns:
        Budget 预算对象
    """
    ...

# services/status.py 负责获取数据并调用 engine
from engine.budget import calculate_budget
from services.docker import docker_containers
from services.ollama import ollama_ps

def get_status():
    containers = docker_containers()
    models = ollama_ps()
    budget = calculate_budget(containers, models)
    ...
```

| engine/ 文件 | 需要上移的数据获取 | 改造工作量 |

### P0-2：后端静默吞异常整改（错误处理）

**问题**：74处静默吞异常（64处 `except: pass` + 10处 `except: print`）

**目标**：所有异常至少记录日志，区分"合理忽略"和"必须记录"

**具体方案**：

#### 步骤1：异常分类（整改前先分类）

| 类型 | 判断标准 | 处理方式 | 占比估计 |
|------|---------|---------|---------|
| **合理忽略** | 可选配置读取失败、缓存未命中、JSON解析失败用默认值 | 保留 pass，但加注释 `# 合理忽略：xxx` | ~20%（15处） |
| **需记录warning** | 外部服务调用失败、非核心操作失败、可恢复异常 | `logger.warning(f"xxx: {e}")` | ~50%（37处） |
| **需记录error** | 核心逻辑失败、状态更新失败、注册表操作失败 | `logger.error(f"xxx: {e}", exc_info=True)` | ~30%（22处） |

## 八、风险与注意事项

### 8.1 风险识别

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| 中间层反向依赖改造引入回归bug | 服务功能异常 | 中 | 每改一个文件跑测试，保留旧版备份 |
| app.js拆分后页面白屏 | 前端不可用 | 中 | 拆分后逐页面验证，保留旧app.js备份 |
| 静默吞异常改后日志刷屏 | 日志文件快速增长 | 低 | 合理设置日志级别，debug不默认开启 |
| 整改进度与大赛演示冲突 | 大赛节点延期 | 中 | P0优先保证，P1/P2可根据大赛进度调整 |
| 外部服务封装改变行为 | 外部调用不一致 | 低 | 封装时保持原有行为，只加统一错误处理 |

### 8.2 注意事项

1. **每步提交**：每个整改项完成后立即提交，commit message写明整改内容
2. **保留备份**：大规模改动前（如app.js拆分），先备份原文件到临时目录
3. **测试先行**：改动前先跑一遍现有测试，确保基线正常
4. **不停止服务**：整改期间服务保持运行，改动后热重载验证
5. **文档同步**：每完成一个整改项，更新评估报告和模块清单
6. **不引入新违规**：整改过程中新增代码必须符合代码工程最高指南
7. **蓝图禁止擅改**：整改过程中如涉及蓝图（调度中心架构与交互设计.md）修改，必须先经主公同意
