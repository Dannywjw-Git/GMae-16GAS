## 二、技术创新（83/100，目标≥85）

### 2.1 细项得分

| 细项 | 得分 | 证据 |
|------|------|------|
| 模型级显存可观测性技术深度 | 82 | 三路数据融合（Ollama API + ComfyUI torch锚点+history+文件大小估算+守恒校准 + 桌面进程PowerShell），动态底噪自学习。解决了 WSL2 下 nvidia-smi 拿不到容器内进程显存的硬伤。局限：Ollama 用 size_gb（文件大小）非实际显存，ComfyUI 用文件大小估算，超限时按比例缩放校准 |
| 预算引擎+准入闸门闭环完整性 | 85 | 预算引擎四级决策（ok/free_L1/free_L2/reject）+ 独占硬约束 + context感知 + 历史生成统计；准入闸门三道防线（格式→R1-R8铁律→预算），铁律从血泪教训提炼（R3=32K死机教训、R4=双进程误删模型）；自动防死机 L1-L4 逐级释放 + 内存>90%触发 + 120s冷却 |
| 与同类工具差异化 | 88 | 竞品对比表（OneGPU4All/Model Manager/Ollama Tray Guard/gpu-orchestrator）显示 GMae 是唯一覆盖"全模态+预算算账+门卫驱逐+QoS主动降级+空闲回收+模型登记台/扫描器+Web指挥台+预演模式+Windows深度适配"的项目 |
| 代码架构质量 | 75 | 后端分层清晰（api→engine→services→clients→core→gpu），配置驱动（registry.json），零外部依赖。但仍有历史包袱：场景切换硬编码（D-04偏差）、部分模块耦合。后端审计 77.5(B)，前端 67(B-) |

### 2.2 差距分析
- 代码架构质量（75）拖了后腿。场景切换仍硬编码 6 个场景的动作序列，registry scenes/system 字段已定义但后端未消费（D-04 偏差登记）
- 模型级可观测性有"估算"成分，评审可能质疑准确性。需要用 benchmark 数据证明误差率

## 三、场景落地（59/100，目标≥80）🔴

### 3.1 细项得分

| 细项 | 得分 | 证据 |
|------|------|------|
| 16GB 卡全模态跑通真实证据 | 70 | SDXL✅、Flux Q5✅、Wan2.2-TI2V-5B✅、Music3✅、qwen3.5:9b✅。但都是**单独跑通**，没有"队列串行跑全模态"的端到端演示记录。Wan2.2 视频素材标注"待补充" |
| 自动防死机实际效果 | 65 | 代码完整实现（L1-L4、内存触发、冷却、三路通知、历史记录）。但**没有触发记录或实测数据**证明"真的防止了死机"。auto_protect 默认关闭，需要用户手动启用 |
| 可部署性 | 60 | 有 start.bat/stop.bat/status.bat，有 Docker 容器管理。但**没有一键部署脚本**，统一 docker-compose.yml 是待办。新用户需要手动装 Docker Desktop、WSL2、拉取定制 ComfyUI 镜像、下载模型、配置 registry。README 快速开始只有 5 行概要，无具体命令 |
| Benchmark 数据完整性 | 40 | 零散数据：Wan2.2 峰值 10.9GB、冷路径 681ms、Flux 实测 11.7GB、SDXL ~60秒/张。**没有系统化的 benchmark 套件**，没有"有/无 GMae 对比"数据，没有显存分解准确率数据 |

### 3.2 差距分析
- **这是最大短板**。评审要求"验证数据来自真实或仿真环境"，当前几乎没有可直接引用的量化数据
- 自动防死机是核心卖点，但默认关闭+无触发记录，评审无法感知其价值
- 可部署性弱意味着评审"可部署、可运行、可测试"的要求难以满足
- 全模态跑通是事实，但缺一个"一次操作跑完全模态"的端到端证据

## 八、风险提示

1. **Benchmark 测试会真实占用显存**：跑 Flux/Wan2.2 等大模型时需遵守显存铁律（生成前释放到 <4GB），避免死机
2. **自动防死机实测有风险**：构造显存紧张场景可能触发真实的容器 stop，建议在测试前备份 ComfyUI 容器（docker commit）
3. **端到端队列演示依赖工作流模板**：SDXL 模板（sdxl_t2i.json）缺失，需要从 ComfyUI 前端导出
4. **场景切换配置驱动化可能引入回归**：现有 6 个场景行为必须保持不变，改完需逐个验证
