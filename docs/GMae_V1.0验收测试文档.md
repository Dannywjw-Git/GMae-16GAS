# GMae-16GAS V1.0 验收测试文档

> **文档版本**：v1.0
> **测试日期**：2026-09-01
> **测试环境**：Windows 11 + WSL2 + Docker Desktop，16GB GPU，ComfyUI/Ollama 容器
> **测试方法**：端到端真实场景自动化测试
> **测试结论**：核心能力验证有效，发现 2 个 P0 缺陷，建议修复后重测再发布 V1.0

---

## 1. 测试概述

### 1.1 测试目的

模拟真人使用消费级 AI 服务器进行实际创作（AI 漫剧、对话写作、批量出图等），验证 GMae（GPU Maestro-显存指挥家）是否能真正帮助用户管理显存、防止 OOM 死机、提升工作流效率。

### 1.2 测试范围

| 模块 | 测试内容 |
|------|---------|
| 显存感知 | GPU 显存数据准确性、进程级显存识别 |
| 预算引擎 | 模型加载前显存预算、决策建议 |
| 场景切换 | 对话态/出图态/视频态一键切换 |
| 自动防死机 | 显存逼近上限时自动释放 |
| 门卫检测 | 未登记 GPU 进程识别与告警 |
| 任务队列 | 批量任务排队、串行执行 |
| 一键释放 | 模型级显存释放 |

### 1.3 测试环境

| 项目 | 配置 |
|------|------|
| 操作系统 | Windows 11 + WSL2 |
| GPU | 16GB 显存（RTX 系列） |
| Docker | Docker Desktop，ComfyUI/Ollama/Immich 等容器运行中 |
| GMae 版本 | v0.3.1 模块化重构版（server.py 98 行入口） |
| 服务端口 | 8787（GMae）、8188（ComfyUI）、11434（Ollama） |
| 已加载模型基线 | 无（测试前显存空闲 >14GB） |

### 1.4 测试模型

| 模型 | 用途 | 标称显存 | 实测显存 |
|------|------|---------|---------|
| qwen3.5:9b | 本地对话/剧本写作 | 6GB | ~10GB |
| SDXL 1.0 | 文生图 | 7GB | ~6.5GB |
| Flux.1 dev Q5 | 高质量文生图 | 12GB | 11.7GB（预算引擎登记） |

## 2. 测试用例

### TC-S5：新手第一天

**场景描述**：不懂显存管理的新手用户，同时启动多个 AI 工具。

**前置条件**：
- GMae 服务运行中
- 显存空闲 >14GB
- 无模型加载

**测试步骤**：
1. 记录基线显存和 GMae 状态
2. 通过 Ollama API 加载 qwen3.5:9b（发一条消息触发）
3. 等待模型加载完成，记录 GMae 状态
4. 通过 ComfyUI API 提交 SDXL 生成任务
5. 等待 SDXL 加载，记录 GMae 状态（guard_level、告警、建议）
6. 调用 GMae /api/guard 验证门卫检测
7. 调用 GMae /api/budget 验证预算引擎
8. 调用 GMae /api/free 释放所有模型
9. 记录恢复后状态

**预期结果**：
- 显存数据与 nvidia-smi 误差 <300MB
- Ollama 加载后 GMae 正确识别
- 高负载时 guard_level 升级到 warning 以上
- 给出具体可操作的建议（如"停止 XX 可释放 Y GB"）
- 系统进程（dwm/explorer 等）不被误报
- 释放后显存回落到基线附近

**实际结果**：✅ 6/6 通过
- 显存误差仅 4MB
- guard_level 正确升级：ok → warning → critical
- 建议具体："停止 qwen3.5:9b，可释放 10.0GB"
- 峰值显存 15.9GB，空闲仅 192MB，系统未死机
- 释放后显存恢复到 0.9GB

### TC-S2：贪心创作者

**场景描述**：用户已加载大模型，还想同时跑另一个大模型。

**前置条件**：
- GMae 服务运行中
- 显存空闲 >14GB

**测试步骤**：
1. 记录基线
2. 加载 qwen3.5:9b（~10GB）
3. 调用 /api/budget 检查 Flux 是否能跑
4. 强行提交 ComfyUI SDXL 任务（模拟用户不听建议）
5. 每 5 秒采样显存，监控自动防死机是否触发
6. 记录自动防死机触发时间和动作
7. 恢复环境

**预期结果**：
- 预算引擎正确识别显存不足，返回 free_L1/free_L2/reject
- 高负载时 guard_level 升级
- 空闲显存 <2GB 时自动防死机触发，执行释放
- 系统不死机

**实际结果**：⚠️ 3/6 通过，核心功能验证成功
- 预算引擎正确：Flux-Q5 decision=free_L2，need_free=0.2GB
- **自动防死机触发成功**：空闲 247MB 时执行 L2 动作"ComfyUI 释放生成模型显存"
- 系统未死机
- **问题**：自动防死机触发延迟（阈值 2GB 但 247MB 才触发，因 QoS 检查间隔 10 秒）
- **问题**：GMae /api/free 不完全释放 ComfyUI 模型缓存

### TC-S4：创作流中断恢复

**场景描述**：用户出图到一半，突然想切去对话查资料，查完再回来。

**前置条件**：
- GMae 服务运行中
- 显存空闲 >14GB

**测试步骤**：
1. 提交 3 个任务到 GMae 队列
2. 提交 ComfyUI SDXL 任务模拟正在出图
3. 调用 /api/scene 切换到 chat
4. 等待 Ollama 加载，用 qwen3.5:9b 发消息查资料
5. 调用 /api/scene 切回 comfy
6. 检查队列状态是否保留
7. 恢复环境

**预期结果**：
- 场景切换成功（comfy → chat → comfy）
- 切换时正确释放前一场景模型，加载新场景模型
- 队列状态在切换后保留
- 队列 worker 运行中
- 恢复后显存回落

**实际结果**：⚠️ 4/7 通过
- 队列功能工作：worker 自动启动，任务完成
- 队列状态保留：切换后 tasks=3
- **P0 问题**：切换到 chat 时 server 崩溃（"Remote end closed connection"）
- 切换失败导致显存爆炸：SDXL 未释放 + qwen3.5=15.9GB，空闲仅 155MB
- 无队列 pause/resume API

- 任务严格串行（max_running ≤1）
- 完成率 >80%

**实际结果**：⚠️ 4/5 完成
- 完成率 80%（4 完成，1 失败）
- 队列 worker 运行中
- **P0 问题**：max_running=4，同时有 4 个任务在执行，不串行
- 队列中有历史残留任务（场景4的 3 个任务未清理）

## 3. 缺陷清单

### 3.1 P0 级缺陷（必须修复）

#### BUG-001：场景切换到 chat 时 server 崩溃

| 项目 | 内容 |
|------|------|
| 缺陷编号 | BUG-001 |
| 优先级 | P0 |
| 影响场景 | TC-S1、TC-S4 |
| 复现率 | 100%（4/4 次） |
| 现象 | POST /api/scene {"scene":"chat"} 返回 "Remote end closed connection without response"，server 连接被关闭 |
| 影响 | 用户无法从出图态切换到对话态，核心功能不可用 |
| 初步分析 | chat 场景的 scene_switch 执行逻辑中某个操作导致 server 异常退出；切到 comfy 正常，说明问题在 chat 特定分支 |
| 建议排查 | 检查 services/scene.py 中 scene_switch 函数的 chat 分支，重点看 docker 操作、PowerShell 脚本调用、异常处理 |

#### BUG-002：队列任务不严格串行

| 项目 | 内容 |
|------|------|
| 缺陷编号 | BUG-002 |
| 优先级 | P0 |
| 影响场景 | TC-S3 |
| 复现率 | 100% |
| 现象 | 提交 5 个任务后，max_running=4，同时有 4 个任务在执行 |
| 影响 | 16GB 卡上并发执行多个生成任务，极易 OOM 死机，违反"16GB 必须串行"的核心设计原则 |
| 初步分析 | 可能是队列 worker 的并发控制缺失，或 ComfyUI 自身队列在并行执行；GMae 队列可能只是转发到 ComfyUI，没有控制 ComfyUI 的并发数 |
| 建议排查 | 检查 engine/queue.py 的 _queue_worker 并发控制，以及 ComfyUI 端是否需要设置 --max-queue-size 或串行执行 |

### 3.2 P1 级缺陷（建议修复）

#### BUG-003：自动防死机触发延迟

| 项目 | 内容 |
|------|------|
| 缺陷编号 | BUG-003 |
| 优先级 | P1 |
| 影响场景 | TC-S2 |
| 现象 | emergency_threshold 设为 2047MB（2GB），但实际在空闲 247MB 时才触发 |
| 影响 | 显存增长快时，可能在检查间隔内就打满死机 |
| 原因 | QoS 检查间隔 check_interval_s=10 秒，SDXL 加载时显存从 4.5GB 降到 247MB 不到 10 秒 |
| 建议 | 检查间隔降到 3-5 秒，或增加显存变化率预测，快速下降时提前触发 |

#### BUG-004：GMae /api/free 不完全释放 ComfyUI 模型

| 项目 | 内容 |
|------|------|
| 缺陷编号 | BUG-004 |
| 优先级 | P1 |
| 影响场景 | TC-S2、TC-S4、TC-S1 |
| 现象 | 调用 GMae /api/free 后，ComfyUI 的 SDXL 模型仍在缓存中（6.5GB），需直接调用 ComfyUI /free 才真正释放 |
| 影响 | 释放后显存残留 6-7GB，影响后续模型加载 |
| 建议 | 检查 free_all 中 ComfyUI /free 的调用方式，确保调用后等待生效或轮询确认 |

#### BUG-005：场景切换耗时偏长

| 项目 | 内容 |
|------|------|
| 缺陷编号 | BUG-005 |
| 优先级 | P1 |
| 影响场景 | TC-S1 |
| 现象 | 成功的场景切换耗时 12-13 秒 |
| 影响 | 用户等待时间偏长，创作流可能被打断 |
| 目标 | <10 秒 |
| 建议 | 优化 scene_switch 中的串行操作，能并行的并行，减少不必要的等待 |

### 3.3 P2 级缺陷（可后续优化）

| 编号 | 描述 |
|------|------|
| BUG-006 | 无队列 pause/resume API，中断恢复只能靠场景切换 |
| BUG-007 | 队列无历史残留清理机制，旧任务一直留在任务列表 |
| BUG-008 | 单元测试运行器路径 bug（已修复，run_tests.py 的 BASE_DIR 少一层 dirname） |

## 5. 结论与建议

### 5.1 测试结论

GMae-16GAS 的核心能力（显存感知、预算引擎、自动防死机、门卫检测）经过真实场景验证，确实有效且有价值。但存在 2 个 P0 级缺陷（场景切换崩溃、队列不串行），严重影响核心使用流程，**当前状态不建议标记为 V1.0 正式发布**。

### 5.2 V1.0 发布门槛

必须完成以下事项后，方可标记 V1.0：

1. **修复 BUG-001**（场景切换 chat 崩溃），4 次切换全部成功
2. **修复 BUG-002**（队列串行），max_running ≤1
3. **修复 BUG-004**（ComfyUI 释放不彻底），释放后显存残留 <1GB
4. **全部 5 个场景重测通过**（通过率 >90%）
5. **综合价值评分 >8/10**

### 5.3 后续优化建议

- 修复 BUG-003（自动防死机延迟），检查间隔降到 3-5 秒
- 修复 BUG-005（切换耗时），目标 <10 秒
- 增加队列 pause/resume API
- 增加队列历史清理机制
- 增加场景切换的原子性保障（切换失败时回滚到原状态）

### 7.1 UI 测试发现的缺陷

#### BUG-009（P0）：登录按钮点击无反应

| 项目 | 内容 |
|------|------|
| 缺陷编号 | BUG-009 |
| 优先级 | P0 |
| 复现率 | 100% |
| 现象 | 用户在登录页输入邮箱和密码后，点击"登录"按钮没有任何反应，页面不跳转、不报错。按 Enter 键可以提交，通过 API 登录也正常。 |
| 影响 | 所有新用户无法通过正常点击方式登录系统，首次使用即卡住 |
| 控制台提示 | "Password field is not contained in a form"——密码输入框不在 form 元素内，可能导致按钮点击事件未绑定表单提交 |
| 建议 | 检查登录页 HTML 结构，确保按钮绑定了 click 事件，或将输入框和按钮包裹在 form 元素内 |

#### BUG-010（P0）：首次设置 tab 无法切换

| 项目 | 内容 |
|------|------|
| 缺陷编号 | BUG-010 |
| 优先级 | P0 |
| 复现率 | 100% |
| 现象 | has_admin=false 时，页面应显示"首次设置"表单，但实际显示的是登录表单。点击"首次设置"tab 没有任何反应，无法切换到设置页面。 |
| 影响 | 全新安装的用户无法创建管理员账号，系统完全不可用（只能通过 API 绕过） |

## 9. 核心功能紧急修复（2026-09-01 第二轮）

### 9.1 用户反馈

用户从局域网（192.168.1.8:8787）登录后，报告三个最核心功能全部无法正常工作：
1. **一键释放** — 点击后显存几乎不下降（仅释放 4MB）
2. **单独释放 ComfyUI** — 不工作
3. **启动 Helper** — 点击后无响应，8 秒超时

### 9.2 根因分析与修复

| 编号 | 优先级 | 缺陷 | 根因 | 修复方案 | 状态 |
|------|--------|------|------|---------|------|
| BUG-016 | **P0** | 一键释放不释放显存 | 服务进程中 `docker` 命令不在 PATH 环境变量中，`docker_containers()` 返回空集合，导致 free_all() 遍历 managed 列表时所有容器都被 `continue` 跳过，actions 为空 | ① server.py 启动时将 Docker Desktop 路径（`C:\Program Files\Docker\Docker\resources\bin`）加入 PATH；② docker_client.py 添加 `_get_docker_cmd()` 路径探测与回退机制，失败时记录错误日志 | ✅ 已修复并验证（释放 10.7GB） |
| BUG-017 | **P0** | 启动 Helper 失败 | ① helper_start() 中脚本路径写错：`vram-helper.py`（连字符）应为 `services/vram_helper.py`（下划线+子目录）；② vram_helper.py 中 BASE_DIR 指向 services/ 目录，导致 config.json 读取失败（token 不匹配） | ① 修正 script 路径为 `os.path.join(BASE_DIR, "services", "vram_helper.py")`；② vram_helper.py 中 BASE_DIR 改为上级目录（vram-console 根目录） | ✅ 已修复并验证（8788 端口响应正常） |
| BUG-018 | P1 | 单独释放 ComfyUI 不工作 | 前端 comfy_free 动作实际调用 `api.free()`（一键释放），并非单独释放 ComfyUI；随 BUG-016 修复后功能恢复，但语义上是"全量释放"而非"单独释放" | 随 BUG-016 修复；如需真正单独释放 ComfyUI，需新增 `/api/free/comfyui` 端点 | ✅ 功能恢复（语义待优化） |

### 9.3 验证结果

**一键释放验证**：
- 测试前：加载 qwen3.5:9b，GPU used 12028 MB
- 调用 /api/free：返回 actions=2（ollama stop models + comfyui /free），freed_mb=10726
- 结论：✅ 正常工作

**Helper 启动验证**：

### 9.4 修复涉及的文件

| 文件 | 修改内容 |
|------|---------|
| `server.py` | 启动时将 Docker Desktop 路径加入 PATH 环境变量 |
| `clients/docker_client.py` | 添加 `_get_docker_cmd()` 路径探测 + 所有 docker 命令调用使用动态路径 + 失败日志 |
| `services/helper.py` | 修正 helper 脚本路径为 `services/vram_helper.py` |

### 9.5 经验教训

1. **服务进程环境隔离**：由 watchdog/子进程启动的服务，其 PATH 可能与交互式 shell 不同。所有依赖外部命令的模块必须做路径探测与回退，不能假设命令在 PATH 中。
2. **文件命名一致性**：`vram-helper.py`（连字符）vs `vram_helper.py`（下划线）的命名不一致导致路径错误。建议统一命名规范。
3. **调试日志的价值**：在 free_all() 中临时添加 `containers=[]` 的调试日志，1 分钟内定位到根因。关键路径应保留可选的调试日志。
