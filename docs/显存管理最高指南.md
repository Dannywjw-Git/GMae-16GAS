# 家庭智能中枢 · 显存管理最高指南（VRAM 铁律！）

> **地位**：本指南是显存管理的**唯一权威规则**，优先级高于一切实施方案/运维脚本/个人习惯。 
> **适用范围**：所有调用 GPU 显存的应用——Ollama 模型群（对话/embedding）、ComfyUI（文生图专业端）、Fooocus（文生图家人端）、rerank（RAG 精排）、游戏串流（Sunshine）、语音三件套，以及**未来任何新增占显存服务**。 
> **强制条款**：接入即遵守；与本文冲突的既有配置视为违规，限期整改；新增服务未过准入不得上线。 
> **版本**：v1.0（2026-08-23）｜ 编制：子龙 + 姜维排障记录 ｜ 关联：《显存统一管理调度方案.md》（操作层）、《排障交接_Ollama反复假死与死机》（根因证据）

## 〇、为什么必须有这份指南（一句话版）

RTX 4060 Ti **16GB 单卡**要伺候对话 / 文生图 / 游戏 / 检索四类负载，**物理上装不下，只能靠规则错峰**。（08-19 曾因违反本指南的规则**两次死机**（显存+内存双爆），08-23 实测又出现 Ollama 僵死 + 显存 12.5G 打满。本指南把所有"谁能用、用多少、何时让位"写成铁律，杜绝显存太忙、不断调进出"。

## 五、各应用合规细则

### 5.1 Ollama（对话推理底座，历史事故重灾区）

| 配置项                       | 合规值                                                           | 违规后果              |
| -------------------------- | -------------------------------------------------------------- | ----------------- |
| `OLLAMA_MAX_LOADED_MODELS` | **2**                                                          | 多模型并存挤爆显存        |
| `OLLAMA_KEEP_ALIVE`        | 统一值（当前 2m/08-19 稳定修复版 20m，二选一全局一致）                             | 模型横跳/常驻冲突         |
| `OLLAMA_CONTEXT_LENGTH`    | **8192**（User env 已设）                                            | >8K → 显存爆 → 死机    |
| `OLLAMA_MODELS`            | `D:\ollama\models`                                             | 路径错误=看不到模型       |
| 自启                         | 仅 HKCU Run `OllamaServe` → `D:\scripts\start_ollama_serve.cmd` | 防双 serve           |
| embedding                  | **bge-m3-cpu**（CPU版）                                           | GPU embed = 泄漏触发器|
| 监控                         | `Get-Process ollama` 已提交内存正常 **120~150MB**，持续增长 = 复发信号         | 泄漏预警              |



> ⚠️ 假死特征识别：**端口 11434 LISTENING 但 API 请求超时 + CLOSE_WAIT 堆积** = 假死，不是慢。处置：kill 全部 ollama/llama-server → 用 `start_ollama_serve.cmd` 重启 → 刷新 OWUI `/api/models`。 
> ⚠️ 请求级 keep_alive 特批规则：任何应用想把模型挂长驻，必须先报主公批准并登记，禁止自行传 `keep_alive` 覆盖全局。

### 5.2 ComfyUI（文生图专业端，容器版）

- ✅ 合规：`--reserve-vram 2.5` 必带；空闲不加载模型（动态 VRAM 默认）；出图前跑 gpu_release
- 🔴 违规：Flux 与任何 AI 负载共存；未释放就出图（会抢死对话）
- 显存：SDXL ~6.5G / Flux Q5 ~13G，**Q8 已实测压垮引擎，禁用**。
- 📌 **Music 3 音乐生成（08-24 实测补记）**：峰值 14.5G（30s 版），生成完**自动卸载回底噪 ~1.0G**（无需手动释放）；实测耗时：30s → ~82s、60s → ~127s、90s → 3-5 分钟（含模型加载）；⚠️ 搭链坑：CLIPLoader 必须用 `minimax_music3_text_encoder_pruned_int8_convrot` + `type=minimax`、VAELoader 必须用 `minimax_music3_dav`（误用 SDXL 的 vae/clip 会报 `shape invalid`），TextEncode 的 `max_duration` 与 EmptyLatentAudio 的 `seconds` 必须同步
- 📌 **LTX-2.3 文生视频（08-23 上线）**：GGUF Q4_K_M（13.2G）走 `UnetLoaderGGUF` + gemma 文本编码器走 `DualCLIPLoader(type=ltxv, device=cpu)`；出视频态 = 独占全卡（同 Flux）；**解码必须用 `VAEDecodeTiled`**（普通 VAEDecode 在 16G 卡报 `HostBuffer.read_file_slice failed`）；采样可用 8 步 + lcm + cfg=1（蒸馏模型）；模型用完 `POST /free` 卸载（WSL RAM 回吐有延迟属正常）

### 5.3 Fooocus（文生图家人端，容器版）

### 5.4 rerank（RAG 精排，CPU 化已实锤）

## 六、新服务准入流程（占显存应用上线 Checklist）

> 任何要碰 GPU 显存的新应用（新容器/新模型/新脚本），上线前必须逐项过：

| 步骤 | 检查项  | 通过标准                        |
| -- | ---- | --------------------------- |
| 1  | 算账   | 查 §二 账本登记：峰值显存 + 允许状态      |
| 2  | 共存   | 按 §三 状态机逐组合核算，确认不会挤爆任一稳态   |
| 3  | 释放机制 | 提供"释放自身显存"的明确动作（stop/卸载/参数）|
| 4  | 启动参数 | 带 `--reserve-vram` 或等价预留   |
| 5  | 实测峰值| 真实跑一次，记录峰值显存（≠理论值）          |
| 6  | 登记   | 更新 §二 账本 + 本指南变更记录         |

**未过 1-6 的服务 = R7 违规，不得上线。**

## 七、巡检与违规处置

### 7.1 例行巡检（健康检查 skill `home-hub-health-check` 覆盖）

| 项               | 阈值              | 动作                            |
| ---------------- | ---------------- | ----------------------------- |
| 显存水位             | >14G 持续          | 🔴 告警：找白占方（查容器/进程）           |
| ollama.exe 已提交内存| >500MB 持续增长      | 🔴 泄漏信号：kill 重启 + 查 GPU embed |
| 11434 假死特征       | LISTENING + 请求超时 | kill 重启 + 刷新 OWUI /api/models |
| 双 ollama serve   | 进程数 >1           | 收敛到单 serve                    |
| Fooocus 容器       | 对话态仍 Up          | `docker stop fooocus`         |
| 孤儿 llama-server  | 存在且无会话           | 用 `gpu_orphan_clean` 清理       |

### 7.2 违规处置流程

1. 识别违规方（账本对照 + nvidia-smi 实测）
2. **立即停用违规方**（stop 容器 / kill 进程 / 卸载模型），恢复稳态
3. 记录到 §二 账本 + 当日 memory，复盘根因
4. 屡犯不改的服务 → 下线整改后再准入

## 附录 A：大模型显存评估清单（M10 操作细则）

> **适用场景**：任何 >5GB 的新模型首次运行前，或现有模型更换量化方式/参数前。
> **目标**：在运行前判断是否会 OOM，避免死机和服务崩溃。

### 评估步骤

1. **查模型文件大小**
   - Get-ChildItem <模型路径> | Select-Object Length
   - 注意：safetensors/gguf 文件大小 ≈ 模型加载后的最小显存（未计算中间计算）

2. **确认量化方式**
   - fp16/fp32：文件大小 = 显存占用（无量化压缩）
   - int8：文件大小 ≈ 显存占用（int8 量化）
   - int4/Q4_K_M/Q4_K_S：文件大小 ≈ 显存占用（4bit 量化）
   - nvfp4/awq：文件大小 ≈ 显存占用（4bit 量化）
   - fp8_e4m3fn：文件大小的一半 ≈ 显存占用（运行时可能转 fp16）

3. **估算中间计算开销**
   - 文本生成（LLM）：+10-20%（KV cache）
   - 文生图（SDXL/Flux）：+20-30%（VAE 解码、注意力）
   - 文生视频（H3/LTX）：+30-50%（时序注意力、帧缓存）
   - 文生音乐（Music3）：+20-30%（音频 latent）

4. **计算峰值显存**
   ```
   峰值显存 ≈ 模型文件大小 × (1 + 中间计算比例) + 系统底噪(1-3GB)
   ```

5. **对比物理上限**
   - 峰值显存 < 14GB：安全（留 2GB 余量）
   - 14GB < 峰值显存 < 15.5GB：极限（需关闭其他服务、桌面程序）
   - 峰值显存 > 15.5GB：**不可行**，不要尝试

### 已知模型显存参考表

| 模型 | 量化 | 文件大小 | 峰值显存 | 16GB可行性 |
|------|------|---------|---------|-----------|
| qwen3.5:9b | Q4_K_M | 6.6GB | ~8GB | ✅ 可行 |
| SDXL | fp16 | 6.5GB | ~7GB | ✅ 可行 |
| Flux-dev | Q5_K_S | 7.7GB | ~13GB | ⚠️ 极限（独占） |
| Music3 | fp8 | 13GB | ~10GB | ✅ 可行（fp8） |
| Music3 | fp16 | 13GB | ~15GB | ⚠️ 极限（独占） |
| MiniMax H3 | int8 | 52GB | >20GB | ❌ 不可行 |
| qwen3.8:27b | Q3 | 10-13GB | ~15GB | ⚠️ 极限（已删除） |

### 评估不通过时的选项

1. **换更轻量的量化**：fp16 → int8 → int4
2. **换更小的模型**：27B → 9B → 0.6B
3. **走云端 API**：本地跑不动的用 API（MiniMax API、即梦等）
4. **升级硬件**：24GB / 48GB 显卡
