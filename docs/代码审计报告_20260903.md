## 三、详细问题清单

### 3.1 【R2】模块级可变状态绕过 Registry 锁

**严重程度**：中（潜在竞态，当前低并发下未触发）

**问题描述**：
指南 M2 要求"所有共享状态必须放在 Registry 类中，通过方法访问"。实际代码中多个模块采用"从 registry 获取引用 → 直接修改引用内容"的模式，绕过了 registry 的锁保护。

**涉及文件**：
| 文件 | 变量 | 锁保护 | 风险 |
|------|------|--------|------|
| `engine/qos.py` | `_qos_state`, `_AUTO_PROTECT_STATE` | `_qos_lock`（仅部分操作） | qos_check() 和 qos_status() 并发时可能读到中间状态 |
| `gpu/monitor.py` | `_lifecycle_state` | 无独立锁 | 进程生命周期更新与查询并发 |
| `engine/queue.py` | `_queue_state` | `_task_lock`（覆盖较好） | 较低风险 |
| `engine/scanner.py` | `_last_ollama_tags`, `_auto_scanner_running` | 无锁 | 自动扫描器与手动扫描并发时可能重复登记 |

**典型代码**（qos.py 第33-42行）：
```python
_qos_state = registry.get("qos_state")
if _qos_state is None:
    _qos_state = {"level": "ok", ...}
    registry.set("qos_state", _qos_state)
# 之后直接 _qos_state["level"] = "emergency"，不经 registry.set()
```

**改进建议**：
- 短期：在所有修改 `_qos_state` 的地方统一加 `_qos_lock`（qos_status 读也加锁）
- 中期：将 qos_state 封装为 QosState 类，所有修改通过方法进行，内部加锁
- 长期：Registry 增加 `update(key, mutator_fn)` 原子操作方法，从机制上防止绕过锁

### 3.2 【R5】services/scene.py 职责混杂

**严重程度**：中（可维护性风险，尚未到上帝对象程度）

**问题描述**：
`services/scene.py`（436行）同时承担三类不相关职责：
1. **场景切换编排**（scene_switch, combo_switch, 7个步骤执行器）
2. **模型操作**（load_model_api, ollama_stop, model_action, service_action）
3. **模型同步**（_sync_ollama_models, _sync_comfyui_models, _comfy_installed_files, _match_comfy_model）

虽然是函数式而非单一类，但按指南 R5 的精神——"同时管>3个不相关职责"——已接近边界。

**改进建议**：
拆分为3个模块：
- `services/scene_switch.py`：场景切换编排 + 步骤执行器
- `services/model_ops.py`：模型加载/卸载/查询 + 服务启停
- `services/model_sync.py`：ollama/comfyui 模型自动同步

拆分后每个文件约150行，职责单一。

### 3.3 【R7】外部服务调用未走 Clients 层

**严重程度**：中高（最主要的架构债务）

**问题描述**：
指南 R7 要求"Ollama/ComfyUI/Docker/nvidia-smi 必须通过 Client 类调用"。项目已建立完整的 `clients/` 层（7个客户端），但部分模块绕过它直接调用外部服务。

**违规清单**：
| 文件 | 直接调用 | 应使用 |
|------|---------|--------|
| `engine/queue.py` | `urllib.request` 调 ComfyUI `/prompt` 和 `/history` | `clients.comfyui_client` |
| `engine/scanner.py` | `run_args(["docker","exec",...])` + `urllib.request` | `clients.docker_client` + `clients.ollama_client` |
| `services/scene.py` | `urllib.request` 调 Ollama `/api/generate` + `run_args(["docker","exec",...])` | `clients.ollama_client` + `clients.docker_client` |
| `clients/nvidia_smi.py` | `run_args(["docker","exec",...])` | 应内部调用 `clients.docker_client.exec_command()` |

**正面案例**（值得推广）：
- `gpu/monitor.py`：正确使用 `clients.nvidia_smi` + `clients.docker_client`
- `services/docker.py`：正确使用 `clients.docker_client`
- `services/helper.py`：正确使用 `clients.helper_client`

**改进建议**：
1. 优先改造 `engine/queue.py`（核心路径，ComfyUI调用集中在2个函数）
2. 其次改造 `services/scene.py`（模型操作部分）
3. `engine/scanner.py` 最后（自动扫描器，非核心路径）
4. 改造后删除模块内的 `urllib.request` 和 `run_args(["docker"...])` 导入

### 3.5 【R10】场景切换同步阻塞请求线程

**严重程度**：中（用户体验问题，非系统稳定性问题）

**问题描述**：
`POST /api/scene` 调用 `scene_switch()`，该函数同步执行 docker start/stop、gpu_release.ps1、wait_ready（最多120秒超时）等操作。整个场景切换可能耗时10-60秒，期间请求线程被阻塞。

**当前缓解措施**：
- `_scene_lock` 非阻塞获取，并发请求直接返回"切换进行中"
- 前端有 loading 状态

**与指南的差距**：
指南 R10 要求">5秒的任务必须丢给后台 worker，请求立即返回 task_id"。场景切换明显>5秒。

**改进建议**：
- 短期：在 API 层将 scene_switch 丢到线程池执行，立即返回 `{task_id, status: "running"}`，前端轮询 `/api/scene/status`
- 中期：复用现有任务队列（engine/queue.py）的 worker 机制，统一长任务管理

**现状**：
```

├── server.py              # 入口（123行，合规）

├── core/                  # 核心层（registry/config/logger/event_bus/status_cache/docker_events/exceptions/utils）

├── meng/                  # 模型评测子系统（独立）
```

## 五、指南之外的建议与观点

> 以下是审计者基于代码实际情况提出的、超出《代码工程最高指南》范围的建议。

### 5.1 建议增加"模块健康度看板"

当前代码质量信息分散在 AGENTS.md、工作交接、开发日志中。建议在 `docs/代码质量评估/` 下建立定期评估机制（指南 §10.7 已要求但未执行），每次里程碑后输出一份评分报告，跟踪质量趋势。本次审计是第一份基线。

### 5.2 建议统一"长任务异步化"模式

当前系统有3种长任务处理模式：
1. 任务队列（engine/queue.py）：完整的入队→worker→轮询模式
2. 状态缓存（core/status_cache.py）：后台异步刷新+返回stale数据
3. 场景切换（services/scene.py）：同步阻塞+并发锁

建议统一为模式1（队列模式），所有>5秒的操作都走任务队列。这不仅解决 R10 问题，还能让前端有统一的任务进度展示。

### 5.3 建议引入"客户端层使用检查"作为提交前检查

clients 层已建立但未被普遍使用（见 §3.3）。建议在 `scripts/` 下加一个简单的检查脚本：扫描 engine/ 和 services/ 层，禁止出现 `urllib.request`、`run_args(["docker"`、`subprocess` 等直接外部调用。这比人工审查更可靠。

### 5.4 建议将"配置驱动"进行到底

scene_switch 已实现配置驱动（steps在registry.json中定义），这是很好的实践。建议将此模式推广到：
- QoS 阈值和分级策略（当前硬编码在 QOS_CFG 和 _AUTO_PROTECT_MODE_PLAN）
- 告警升级规则（当前硬编码 ALERT_ESCALATION_THRESHOLD = 600）
- 诊断规则（当前在 diagnose.py 中硬编码9条规则）

配置驱动后，调整策略不需改代码，对大赛演示和后续迭代都有利。

### 5.5 建议清理"兼容层"代码

core/event_bus.py 中有大量兼容旧接口的方法（log/query_legacy/get_stats/get_alerts，约60行）。如果确认没有旧代码使用（已全局搜索确认只有测试用了新接口），可以删除兼容层，减少维护负担。

### 5.6 前端架构评价：超出预期

前端代码质量明显优于后端历史包袱：
- 已拆分为 core/components/pages 三层（app.js仅192行入口）
- pages.js 1846行包含9个页面，平均每页约200行，合理
- 有设计令牌系统（variables.css）
- BEM命名规范
- 建议：pages.js 可按页面拆分为9个文件（dashboard.js/diagnose.js/alerts.js等），进一步降低单文件复杂度

### 5.7 关于"75-85分就是健康状态"的观点

指南设定的健康目标非常务实。本次审计77.5分（B级），恰好落在健康区间。**不建议为了冲A级而大规模重构**——当前主要债务（R7外部服务封装、R2状态管理）都是渐进式可改的，不需要停服。建议每个迭代修1-2个模块，2-3个迭代后自然达到A级。
