# GMae 代码工程最高指南（工程铁律！）

> **地位**：本指南是 GMae 项目代码工程的**唯一权威规则**，优先级高于一切个人编码习惯、AI 生成风格、临时方案。
> **适用范围**：所有 Agent（豆包 / WorkBuddy / DSH）在本工作区编写、修改、重构的任何代码——Python / JS / PowerShell / Shell，以及未来任何新增语言。
> **强制条款**：接入即遵守；与本文冲突的既有代码视为技术债，限期重构；新增代码未过准入不得合并。
> **务实原则**：本指南目标是"防止代码腐烂到无法维护"，不是"达到企业级完美"。约束刚好够用来避免最痛的问题，再多就是负担。**75-85 分就是健康状态，不追求 100 分。**
> **版本**：v1.1（2026-08-31）｜ 编制：豆包 ｜ 关联：《显存管理最高指南》（运行时铁律）、《调度中心架构与交互设计》（设计蓝图）

## 〇、为什么必须有这份指南（一句话版）

**3000 行的 server.py 不是代码量大，是设计失败。** GMae 是状态密集、并发敏感、外部依赖多的系统，代码一旦失去边界，改一个功能要动 5 个文件、测一个模块要启动整个服务、加一个功能要在 if-else 里嵌套——这不是工程，是考古。本指南把"怎么写代码"写成铁律，杜绝面条代码和伪 OOP。

> ⚠️ 教训：显存管理最高指南管的是"运行时不死机"，本指南管的是"代码不腐烂"。两者同等重要。

## 一、核心哲学（5 条，先理解再动手）

### P1：状态是敌人，封装是武器
GMae 是状态密集系统（调度状态机、服务注册表、显存水位、任务队列）。**所有共享状态必须集中管理、显式访问、并发保护**。散落在全局变量、模块级变量、函数闭包里的状态，都是定时炸弹。

### P2：边界大于实现
模块之间的**接口（输入/输出/错误契约）**比内部实现重要 10 倍。接口定了，内部可以随便重写；接口乱了，改一个模块牵连全系统。**先定接口，再写实现。**

### P3：可测试性是设计质量的试金石
**不能在不启动整个服务的前提下写单元测试的代码，就是设计有问题。** 如果你发现测一个函数需要先 mock Flask、再启动 Docker、再连 Ollama——不是测试难写，是代码耦合太深。

### P4：范式是工具，不是宗教
OOP / 函数式 / 过程式都行，看场景。**有状态的服务用类，纯数据转换用函数，一次性脚本用过程式。** 不要为了"面向对象"把无状态函数塞进 class，也不要因为"函数式纯粹"把有状态的调度器写成一堆闭包。

### P5：渐进式演进，反对推倒重来
能抽离就抽离，能加测试就加测试，能拆模块就拆模块。**不要停服重构，不要"我重写一版更好的"。** 每一步改动都要让现有功能继续跑，每抽一块都要跑验证。推倒重来 = 引入新 bug + 丢失历史踩坑记录。

## 二、🔴 RED · 红线（违反 = 代码打回，必须重构）

| # | 红线条款 | 依据 |
|---|---------|------|
| R1 | **禁止单文件超过 500 行**（入口文件除外，入口文件上限 300 行） | 超过 = 职责混杂，必须拆分 |
| R2 | **禁止全局可变变量**（配置常量、单例注册表除外，且必须通过函数访问） | 隐式状态 = 竞态 + 不可测试 |
| R3 | **禁止核心层 import 框架**（scheduler / state_machine / vram_budget 不得 import Flask/FastAPI/request/response） | 核心逻辑必须可独立测试 |
| R4 | **禁止业务逻辑直接操作 request/response 对象** | API 层只做参数校验和响应格式化，业务逻辑在 core/services 层 |
| R5 | **禁止上帝对象**（一个类 >500 行 或 >15 个公共方法，**且**同时管 >3 个不相关的职责） | 单一职责原则；行数/方法数是预警信号，"同时管不相关职责"才是判定标准 |
| R6 | **禁止继承超过 2 层**（Object → A → B 是上限，B → C 禁止） | 深继承 = 改父类牵连所有子类，用组合替代 |
| R7 | **禁止外部服务调用散落在业务逻辑中**（Ollama/ComfyUI/Docker/nvidia-smi 必须通过 Client 类调用） | 接口隔离 + 可 mock |
| R8 | **禁止超过 3 个分支的 if-else 分发多实现**（3 个以内允许 if-else，超过 3 个或预计频繁新增实现时必须用多态/策略模式） | 开闭原则：新增实现不改现有代码；3 个以内 if-else 比策略模式更简单可读 |
| R9 | **禁止静默吞掉异常**（except: pass 或 except Exception: print 后继续 = 禁止） | 错误必须处理或传播，不能消失 |
| R10 | **禁止在请求处理线程中执行长耗时操作**（>5 秒的任务必须丢给后台 worker，请求立即返回 task_id） | 阻塞请求 = 服务假死 |

## 三、✅ MUST · 必须遵守

### M1：分层架构（简化版，4-5 层）

所有服务端代码必须按以下分层组织，**依赖方向只能从上到下，禁止反向依赖**。小项目允许合并层，但不得违反依赖方向。

```
{project}/
├── server.py / app.py          # 入口层：路由注册 + 依赖组装 + 启动，<300行
├── api/                         # API 层：路由 + 参数校验 + 响应格式化
│   ├── routes.py                # 路由总装
│   ├── {resource}.py            # 按资源拆分（tasks/services/vram...）
│   └── schemas.py               # 请求/响应数据模型（pydantic/dataclass）
├── core/                        # 核心领域层：纯业务逻辑 + 数据模型，零框架依赖
│   ├── scheduler.py             # 调度引擎
│   ├── state_machine.py         # 状态机定义与切换
│   ├── vram_budget.py           # 显存预算计算
│   ├── registry.py              # 服务/状态注册表（唯一状态持有者）
│   ├── models.py                # 数据模型（dataclass/pydantic，与 core 同层）
│   └── workers/                 # 后台任务（可选，放在 core 下不单独一层）
│       ├── watchdog.py          # 服务健康检查
│       ├── vram_monitor.py      # 显存采样
│       └── task_runner.py       # 任务执行器
├── clients/                     # 外部服务客户端：接口隔离
│   ├── base.py                  # 抽象基类（接口定义，可选）
│   ├── ollama_client.py         # Ollama API 封装
│   ├── comfyui_client.py        # ComfyUI API 封装
│   ├── docker_client.py         # Docker 操作封装
│   └── nvidia_smi.py            # 显存采样封装
├── services/                    # 应用服务层（可选：业务逻辑复杂时才拆，小项目可合并到 api）
│   ├── task_service.py          # 任务提交/取消/查询
│   └── generation_service.py    # 生成任务编排
├── config.py                    # 配置管理（环境变量 + 配置文件）
└── utils/                       # 纯函数工具（无状态、无副作用）
```

**依赖方向铁律**：
```
api → core → models
api → clients
services → core/clients
workers → core/clients
clients → utils
core → models/utils
```
- `core` 不得 import `api`、`services`、`workers`
- `clients` 不得 import `core`、`services`、`api`
- `models` 不得 import 任何业务层
- 跨层调用必须通过接口，不得直接访问内部状态

**分层豁免说明**：
- `services` 层是**可选**的——业务逻辑简单时，api 层直接调用 core，不拆 services
- `workers` 不单独一层，放在 `core/workers/` 下
- `models` 与 `core` 同层（合并为 `core/models.py` 或 `core/models/`），不单独一层
- 总层数 **4-5 层**（入口/api/core/clients/utils，可选 services），不是 8 层

### M2：状态管理

- **唯一状态持有者**：所有共享状态（服务列表、显存水位、任务队列、当前稳态）必须放在 `Registry` 类中，通过方法访问
- **并发保护**：Registry 内部所有读写共享状态的方法必须加锁（`threading.Lock` / `asyncio.Lock`），锁的粒度按状态域划分，不用一把大锁
- **不可变优先**：数据模型尽量用不可变对象（`frozen=True` 的 dataclass），状态变更通过返回新对象，不是原地修改
- **状态变更可追溯**：每次状态切换（稳态切换、服务启停、任务状态变更）必须记录日志，包含时间戳、变更前、变更后、触发原因

### M3：错误处理

- **错误分类（核心逻辑建议区分，简单脚本允许通用异常）**：
  - 核心调度逻辑（scheduler/state_machine）建议区分业务错误（模型不存在、显存不足、任务取消）和系统错误（网络超时、Docker 崩溃、OOM）
  - 简单脚本、工具函数、一次性数据迁移允许用通用异常（`ValueError` / `RuntimeError`），不需要为每种错误定义异常类
- **业务错误**：需要调用方根据错误类型做不同处理时，定义明确的异常类（`InsufficientVRAMError` 等）；不需要区分时用通用异常即可
- **系统错误**：捕获后记录完整堆栈，触发重试或降级，不得静默吞掉
- **错误传播**：底层错误向上传播时必须附加上下文（"调用 Ollama 加载模型 qwen3.5:9b 失败：连接超时"），不是裸异常
- **重试规则**：网络类错误可重试（指数退避，最多 3 次），业务错误不重试（重试也不会成功）

### M4：可测试性（建议性，不强制覆盖率）

- **核心调度逻辑建议有单元测试**：状态机切换、显存预算计算、任务队列管理这些纯逻辑，建议写单元测试验证正确性
- **测试不得依赖外部服务**：Ollama/ComfyUI/Docker 全部用 mock，nvidia-smi 用假数据
- **测试不得启动整个服务**：直接 import 被测模块，传入 mock 依赖
- **覆盖率不做强制要求**：不设 85% 之类的硬指标。核心逻辑有测试覆盖即可，胶水代码和脚本不强制
- **测试是加分项不是门槛**：有测试说明代码质量好，没有测试但逻辑正确也可以接受

### M5：并发安全

- **请求处理和任务执行分离**：API 层只入队，worker 执行，不共享线程
- **长耗时操作必须可取消**：任务执行器必须支持取消信号，不能跑起来就停不下来
- **定时器/看门狗必须有超时保护**：任何阻塞调用必须设超时，不能无限等待
- **并发访问的资源必须有明确的所有权**：一个状态只被一个 worker 写，其他 worker 只读

### M6：代码风格

- **命名**：类用 PascalCase（`TaskScheduler`），函数/变量用 snake_case（`calculate_vram_budget`），常量用 UPPER_SNAKE_CASE（`MAX_VRAM_THRESHOLD`）
- **函数长度**：单个函数不超过 50 行，超过就拆
- **参数数量**：函数参数不超过 5 个，超过就用 dataclass 打包
- **类型注解和 docstring（分层要求）**：
  - **core/clients 层的公共函数必须有**完整类型注解（参数 + 返回值）和 docstring（用途、参数、返回值、可能抛出的异常）
  - **utils/脚本/工具函数建议有**，但不强制——简单函数（如 `def parse_vram(s): return int(s)`）不需要写比函数本身还长的 docstring
- **注释**：注释解释"为什么"，不解释"做什么"（代码本身应该能看出做什么）
- **魔法数字**：禁止代码里出现裸数字（`if vram > 14336`），必须定义为命名常量（`VRAM_SAFE_THRESHOLD_MB = 14336`）

## 四、💡 SHOULD · 建议

| # | 建议 | 说明 |
|---|------|------|
| S1 | 优先用组合而非继承 | 继承用于"is-a"关系，组合用于"has-a"关系，大部分场景用组合更灵活 |
| S2 | 依赖注入而非全局 import | 需要 mock 测试的模块用依赖注入（构造函数传参），简单模块直接 import 单例即可 |
| S3 | 小步提交，每步可回滚 | 一次重构只做一件事，提交信息说明改了什么、为什么 |
| ~~S4 先写接口再写实现~~ | **已豁免**：实际开发中很多时候先写实现再抽接口更自然；只有预计有 2 个以上实现时才先写抽象接口 | — |
| S5 | 数据类用 dataclass/pydantic | 不要用 dict 传结构化数据，用类型化的数据类 |
| S6 | 日志分级使用 | DEBUG（开发调试）/ INFO（正常流程）/ WARNING（可恢复异常）/ ERROR（系统错误），不要全用 print |
| S7 | 配置集中管理 | 所有配置项（端口、阈值、路径、超时）集中在 config.py，不要散落在代码里 |
| S8 | 定期清理死代码 | 注释掉的代码、未使用的函数、过时的 TODO，定期删除，不要留着"以后可能用" |

## 五、新代码 / 重构准入流程（分级）

> 根据改动规模选择对应流程，**不是所有改动都走 10 步**。

### 5.1 简单改动（3 步简化流程）

**适用场景**：改参数、修 bug、加注释、改文案、调整阈值、小功能修补。

| 步骤 | 检查项 | 通过标准 |
|------|--------|---------|
| 1 | 红线检查 | 不违反 §二 RED 红线（特别是 R1 单文件行数、R2 全局变量、R9 静默吞异常） |
| 2 | 功能验证 | 现有功能跑通，没有引入回归 |
| 3 | 文档同步 | 相关文档/注释同步更新（如果改动影响了接口或行为） |

### 5.2 新增模块 / 大规模重构（完整 10 步流程）

**适用场景**：新增独立模块、拆分大文件、重构核心调度逻辑、更换外部服务架构。

| 步骤 | 检查项 | 通过标准 |
|------|--------|---------|
| 1 | **职责定位** | 这个模块属于哪一层？职责是什么？一句话能说清吗？ |
| 2 | **依赖方向** | 它依赖哪些模块？依赖方向符合分层规则吗？有没有反向依赖？ |
| 3 | **状态分析** | 它持有/访问哪些共享状态？状态怎么保护？有没有并发问题？ |
| 4 | **接口定义** | 它的公共接口是什么？输入/输出/错误契约明确吗？ |
| 5 | **可测试性** | 能不启动服务、不连外部服务就写单元测试吗？ |
| 6 | **错误处理** | 错误有上下文吗？重试策略明确吗？ |
| 7 | **红线检查** | 逐条对照 §二 RED 红线，有没有违反？ |
| 8 | **测试覆盖** | 核心逻辑有单元测试吗？（建议性，不强制覆盖率） |
| 9 | **文档更新** | 模块清单/AGENTS.md/相关文档更新了吗？ |
| 10 | **渐进验证** | 现有功能跑过了吗？没有引入回归吗？ |

**未过流程的代码 = 不得合并。**

## 七、违规处置流程

1. **识别违规**：代码审查或自查时发现违反红线
2. **标记技术债**：在代码中标注 `# TECHNICAL_DEBT: 违反 R{x}，原因：{xxx}，计划：{xxx}`，并登记到 `docs/技术债清单.md`
3. **限期重构**：红线违规必须在 2 个迭代内重构完成，建议违规可排期
4. **屡犯处理**：同一模块连续 3 次违反同一规则，模块负责人需提交重构方案
5. **例外申请**：确需违反红线的（如性能极端优化），必须在代码注释中写明原因、替代方案评估、性能数据，并经主公批准

- 📌 可测试性是设计质量的试金石 ｜ 📌 边界大于实现 ｜ 📌 范式是工具不是宗教 ｜ 📌 渐进式演进，反对推倒重来
- 📌 75-85 分就是健康状态，不追求 100 分 ｜ 📌 简单改动走 3 步流程，新增模块才走 10 步

## 十、代码质量评估体系

> 基于本指南的评分体系，用于评估模块/项目的代码质量。**百分制，60 分及格，75-85 分是健康状态，不追求 100 分。**

### 10.1 评分维度与权重

| 维度 | 权重 | 评分要点 |
|------|------|---------|
| **架构与分层** | 20 分 | 目录结构清晰、依赖方向正确、模块边界明确、职责单一 |
| **状态管理** | 15 分 | 无全局可变状态、状态集中管理、并发保护、不可变优先 |
| **错误处理** | 15 分 | 错误有分类、有上下文传播、不静默吞、重试策略明确 |
| **代码风格** | 15 分 | 命名规范、函数长度合理、无魔法数字、core/clients 层有类型注解和 docstring |
| **可测试性** | 10 分 | 核心逻辑可独立测试、不依赖外部服务、有单元测试（建议性） |
| **并发安全** | 10 分 | 请求执行分离、长任务可取消、超时保护、状态所有权明确 |
| **外部服务封装** | 10 分 | 通过 Client 类调用、接口隔离、可 mock、错误统一处理 |
| **文档与可维护性** | 5 分 | 注释解释"为什么"、README/模块清单更新、变更可追溯 |

**总分：100 分**

### 10.2 评分标准（每个维度按 4 档打分）

每个维度按以下标准打分（以该维度满分为基数）：

| 档位 | 得分比例 | 标准 |
|------|---------|------|
| 优秀 | 90-100% | 完全符合规范，有额外亮点（如完善的测试、清晰的文档） |
| 良好 | 75-89% | 基本符合规范，有小瑕疵但不影响可维护性 |
| 合格 | 60-74% | 主要规则遵守，有明显技术债但不影响功能运行 |
| 不合格 | <60% | 违反核心规则，代码难以维护，需要重构 |

**示例**：架构与分层（20 分），如果目录结构清晰、依赖方向正确，但有 1 个模块边界略模糊 → 良好档 → 20 × 80% = 16 分。

### 10.3 一票否决项（违反直接不及格，总分 ≤59）

以下任何一项违反，该模块/项目直接判定为 D 级（不合格），不论其他维度得分多高：

1. **单文件超过 1000 行**（严重职责混杂，不是 500 行的小超）
2. **全局可变状态导致竞态条件**（已实际触发或可明确预见）
3. **静默吞异常导致数据丢失或错误不可追溯**
4. **核心逻辑与框架强耦合，无法在不启动服务的情况下测试**
5. **长耗时操作阻塞请求线程，导致服务假死**

### 10.4 加分项（最多加 5 分，总分不超过 100）

| 加分项 | 分值 | 说明 |
|--------|------|------|
| 核心逻辑有完整单元测试 | +2 | 状态机、显存预算、任务队列等纯逻辑有测试覆盖 |
| 类型检查通过（mypy/pyright） | +1 | 核心模块无类型错误 |
| 有 CI/CD 自动化检查 | +1 | 提交自动跑测试/lint |
| 文档完善（模块 README + 架构图） | +1 | 新 Agent 能快速理解模块 |

### 10.5 质量等级

| 等级 | 分数 | 含义 | 行动 |
|------|------|------|------|
| **S** | 90-100 | 优秀，可作为标杆 | 保持，可作为其他模块的参考模板 |
| **A** | 80-89 | 良好，符合规范 | 保持，小瑕疵可排期改进 |
| **B** | 70-79 | 合格，基本达标 | 健康状态，有技术债但可控，定期改进 |
| **C** | 60-69 | 及格，有明显问题 | 需限期改进，列出技术债清单和改进计划 |
| **D** | <60 | 不合格，需重构 | 立即停止新增功能，先重构核心问题 |

> **GMae 项目的健康目标：B 级（70-79 分）以上。** A 级是优秀，S 级是可遇不可求的标杆。**不要求所有模块都达到 A/S，B 级就是可以接受的健康状态。**

### 10.6 评估流程

1. **选择评估对象**：单个模块 / 子系统 / 整个项目
2. **逐维度打分**：按 §10.2 标准，每个维度独立打分，记录扣分原因
3. **检查一票否决项**：如有违反，直接 D 级
4. **计算加分项**：符合条件的加分，总分不超过 100
5. **确定等级**：按 §10.5 确定等级
6. **输出评估报告**：包含各维度得分、扣分原因、技术债清单、改进建议
7. **登记存档**：评估结果存入 `docs/代码质量评估/` 目录，便于历史对比

### 10.7 评估频率

| 场景 | 评估要求 |
|------|---------|
| 新增模块完成时 | 必须评估，达到 C 级以上才能合并 |
| 大规模重构完成时 | 必须评估，重构后等级不得低于重构前 |
| 每个迭代结束时 | 抽查核心模块，跟踪质量趋势 |
| 项目里程碑时 | 全项目评估，输出整体质量报告 |
