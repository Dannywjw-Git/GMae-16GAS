# GMae 真实场景验证方案

> **目的**：不是测代码对不对，而是模拟真人用 AI 干活，看 GMae 到底能不能帮上忙、有多大价值。
> **方法**：设计 5 个真实用户场景，每个场景有明确的"用户行为 → GMae 反应 → 价值判断"。
> **创建**：2026-09-01
> **参考**：2026 年消费级 AI 服务器主流应用场景调研（AI 漫剧/短剧全流程、本地绘画、对话写作、批量生产）

---

## 调研结论：消费级 AI 服务器的真实工作方式

### 最火场景：AI 漫剧/短剧全流程制作

典型流水线（一个创作者一天的工作）：

```
小说/灵感
  ↓ 用 LLM（qwen3.5/deepseek）写剧本+分镜
剧本+分镜脚本
  ↓ 用 ComfyUI（Flux/SDXL）生成角色设定图+分镜图
20-50 张分镜图
  ↓ 用 Wan2.2/LTX2.3 把关键帧变成视频片段
视频片段
  ↓ 用 TTS/Music3 生成配音+BGM
音频
  ↓ 对口型+剪辑合成
成片
```

**每个阶段用不同模型，需要频繁切换，16GB 卡根本放不下两个大模型。**

### 用户反复提到的 6 大痛点

| 痛点 | 具体表现 | 严重程度 |
|------|---------|---------|
| 显存不够 OOM | Flux（12GB）+ LLM（6GB）= 18GB > 16GB，直接爆显存闪退 | 🔴 致命 |
| 模型切换慢 | 停容器重启 10-30 秒，打断创作思路 | 🟡 影响效率 |
| 不知道够不够 | 加载模型前不知道会不会爆，只能试，试错成本高 | 🟡 焦虑 |
| 批量任务怕死机 | 晚上想跑 20 个分镜，怕半夜 OOM 死机白跑 | 🔴 致命 |
| 多工具互相抢 | ComfyUI 出图时 Ollama 用不了，来回切 | 🟡 影响效率 |
| 残留显存泄漏 | 用完模型显存没释放干净，越用越慢 | 🟠 累积问题 |

### GMae 理论上能解决的

| GMae 功能 | 对应痛点 | 价值假设 |
|-----------|---------|---------|
| 场景一键切换 | 模型切换慢 | 10-30秒 → 秒级，创作不中断 |
| 预算引擎（预演） | 不知道够不够 | 加载前先算账，不盲目试错 |
| 秒级释放（/free） | 残留显存泄漏 | 模型级释放替代容器重启 |
| 任务队列 | 批量任务怕死机 | 串行执行+自动腾显存，无人值守不 OOM |
| 门卫+高负载预警 | 显存不够 OOM | 提前告警+建议，防止死机 |
| 自动防死机（第三层） | 显存不够 OOM | 紧急时自动释放，保系统不死 |

## 5 个真实场景测试

### 场景 1：漫剧创作者的一天（核心场景）

**模拟用户**：一个独立漫剧创作者，用一台 16GB 显卡的工作站做完整漫剧。

**时间线**：

| 时间 | 用户行为 | 显存变化 | GMae 应该做什么 |
|------|---------|---------|----------------|
| 9:00 | 打开 OWUI，用 qwen3.5:9b 写剧本 | Ollama 加载 ~6GB | 识别对话态，正常服务 |
| 10:30 | 剧本写完，点"出图态"切换 | 释放 Ollama → 加载 ComfyUI | 场景切换，秒级释放 Ollama，ComfyUI 就绪 |
| 10:31 | 用 Flux 批量生成 20 张分镜图 | Flux 加载 ~12GB | 队列串行执行，每张图前检查显存 |
| 12:00 | 20 张图跑完，想查个资料 | 用户切回对话态 | 释放 Flux，拉起 Ollama，秒级响应 |
| 14:00 | 查完资料，点"视频态" | 释放 Ollama → Wan2.2 就绪 | 场景切换，预算引擎确认 Wan2.2 能跑 |
| 14:05 | 提交 3 个视频生成任务 | Wan2.2 ~11GB | 队列串行，每个任务前自动腾显存 |
| 18:00 | 视频跑完，切回对话态写文案 | 释放 Wan2.2 → Ollama | 切换顺畅 |
| 19:00 | 同时想用 Music3 生成 BGM | Music3 ~5GB + Ollama ~6GB = 11GB | 预算引擎确认够，共存运行 |
| 22:00 | 收工，所有模型释放 | 显存回到空闲 ~14GB | 无残留泄漏 |

**验证点**：
1. ✅ 4 次场景切换，每次 < 30 秒（目标 < 10 秒）
2. ✅ 每次切换后显存无残留（前一个模型完全释放）
3. ✅ 批量 20 张图 + 3 个视频，全程不 OOM
4. ✅ 用户不需要手动 docker stop/restart
5. ✅ 收工时显存回到空闲状态（无泄漏）

**价值判断**：
- 没有 GMae：用户需要手动停容器、重启、等 10-30 秒，一天切换 4 次 = 浪费 2-5 分钟，还可能 OOM 丢工作
- 有 GMae：一键切换，秒级完成，不 OOM
- **价值：每天省 5-10 分钟 + 零 OOM 风险**

### 场景 2：贪心创作者（压力测试）

**模拟用户**：不懂显存管理，同时开了一堆东西。

**操作**：
1. ComfyUI 加载 Flux（~12GB）出图
2. 同时打开 OWUI 想跟 qwen3.5:9b 聊天（~6GB）
3. 浏览器还开着 AI 插件（~1GB）
4. 总需求 ~19GB > 16GB 物理上限

**GMae 应该做什么**：
1. 门卫检测到 Ollama 启动时显存不足
2. 预算引擎返回 reject："差约 3GB，建议先释放 Flux"
3. 前端弹出建议："当前 Flux 占用 12GB，启动对话需要 6GB，不够。是否释放 Flux 切换到对话态？"
4. 用户确认 → 秒级释放 Flux → 拉起 Ollama
5. 如果用户不确认强行启动 → 系统可能 OOM，但 GMae 的高负载预警应该在显存 < 2GB 时触发紧急释放

**验证点**：
1. ✅ 预算引擎正确计算差值（~3GB）
2. ✅ 前端建议清晰可操作
3. ✅ 用户确认后切换顺畅
4. ✅ 强行并发时，高负载预警在危险线前触发
5. ✅ 全程不死机

**价值判断**：
- 没有 GMae：用户盲目启动 → OOM → 系统死机 → 丢工作
- 有 GMae：提前算账+建议+紧急保护，不死机
- **价值：防止一次 OOM 死机 = 省 10 分钟重启 + 不丢工作**

### 场景 3：夜间无人值守批量生产

**模拟用户**：睡前提交一批任务，想早上起来看到成果。

**操作**：
1. 23:00 用户提交任务队列：
   - 5 张 Flux 分镜图（每张 ~2 分钟）
   - 3 个 Wan2.2 视频片段（每个 ~5 分钟）
   - 2 首 Music3 BGM（每首 ~2 分钟）
2. 用户去睡觉
3. GMae 自动排队执行：
   - 每个任务前检查显存
   - 不够就释放前一个模型
   - 执行完自动释放
   - 下一个任务开始
4. 02:00 全部完成，显存回到空闲

**验证点**：
1. ✅ 10 个任务严格串行，无并发
2. ✅ 每个任务切换时显存正确释放+加载
3. ✅ 全程显存峰值 < 15GB（留 1GB 安全余量）
3. ✅ 零 OOM、零崩溃
4. ✅ 早上起来 10 个任务全部完成
5. ✅ 任务日志完整（每个任务的开始/结束/耗时/显存峰值）

**价值判断**：
- 没有 GMae：用户不敢夜间批量跑（怕 OOM 死机白跑），只能守着电脑一个个手动跑
- 有 GMae：睡前一键提交，睡醒收成果，8 小时无人值守
- **价值：把 8 小时睡眠时间变成生产时间，一天产出翻倍**

---

### 场景 4：创作流中断与恢复

**模拟用户**：出图到一半突然需要查资料，然后回来继续。

**操作**：
1. ComfyUI 正在跑 Flux 批量出图（队列里还有 5 张）
2. 用户突然想查一个剧本细节，切到 OWUI 对话
3. GMae：暂停 ComfyUI 队列 → 释放 Flux → 拉起 Ollama
4. 用户查了 5 分钟资料
5. 用户切回出图态
6. GMae：释放 Ollama → 重新加载 Flux → 从断点继续出图队列

**验证点**：
1. ✅ 中断时队列状态保存（已完成几张、还剩几张）
2. ✅ 切换 < 30 秒
3. ✅ 恢复后从断点继续，不重复已完成的
4. ✅ 用户不需要重新提交任务

**价值判断**：
- 没有 GMae：用户要么等出图完（浪费 10 分钟），要么手动停了再重开（队列丢失，重新提交）
- 有 GMae：暂停-切换-恢复，队列状态保留
- **价值：创作流不被打断，灵感不丢失**

---

### 场景 5：新手用户的第一天

**模拟用户**：刚装完 GMae，不懂显存管理，什么都想开。

**操作**：
1. 用户同时启动 ComfyUI + Ollama + Fooocus + 浏览器 AI 插件
2. 显存快速攀升到 14GB（危险）
3. GMae 门卫检测到 4 个 GPU 进程，其中 Fooocus 未登记
4. danger_level 升到 warning → danger
5. 前端顶部告警闪烁，弹出建议：
   - "检测到 4 个 GPU 进程，显存使用 14/16GB（87%）"
   - "Fooocus 未登记，占用 6.9GB"
   - "建议：关闭 Fooocus 或切换到单一场景"
6. 用户按建议关闭 Fooocus
7. 显存降到 8GB，danger_level 回到 safe

**验证点**：
1. ✅ 门卫正确识别所有 GPU 进程（含未登记的）
2. ✅ danger_level 随水位正确升级
3. ✅ 告警及时（水位超过 85% 后 3 秒内）
4. ✅ 建议具体可操作（不是笼统的"显存不足"）
5. ✅ 用户操作后告警消除

**价值判断**：
- 没有 GMae：新手不知道发生了什么，直到系统死机才明白
- 有 GMae：实时可视化+具体建议，新手也能管好显存
- **价值：降低使用门槛，新手不翻车**

## 测试执行计划

### 前置条件
- 调度中心服务运行中（http://127.0.0.1:8787）
- ComfyUI、Ollama 容器运行中

## V1.0 发布的价值标准

不是"功能都做完了"，而是：

1. **5 个场景全部通过**（或有条件通过且不影响核心价值）
2. **每个场景都有明确的"没有 GMae vs 有 GMae"对比数据**
3. **用户视角价值评分 ≥ 7/10**
4. **零 OOM 死机**（所有场景全程）
5. **场景切换平均 < 15 秒**

满足以上条件，GMae 才算真正"有用"，可以标记 V1.0，然后基于这些真实场景数据写介绍文档和演示视频。

## 与单元测试的关系

- **单元测试**（tests/ 目录）：保证代码逻辑正确，是基础
- **真实场景验证**（本文档）：保证产品对用户有价值，是目的
- 两者都要过，但真实场景验证不通过，单元测试全绿也没意义
