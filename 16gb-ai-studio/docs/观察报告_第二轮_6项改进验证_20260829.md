## 三、发现的问题与优化建议

### 问题 1：小模型大 context 的账本差异（持续 loading）

**现象**：
- qwen3.5:0.8b（5.5GB，256K context）：GPU 11.1GB，ollama ps size=5.5GB，差异 4.4GB → 持续 loading
- qwen3.5:9b（8.0GB）：GPU 9.6GB，差异 0.4GB → consistent

**根因**：ollama ps 的 `size` 字段只包含模型权重，**不包含 KV cache**。小模型大 context 时 KV cache 占比极高（qwen3.5:0.8b 的 KV cache 约 4.4GB，是权重的 4 倍）。

**优化建议**：
1. 动态噪声基线：根据已加载模型的 context 大小动态调整 expected_used（增加 KV cache 估算）
2. KV cache 估算公式：`kv_cache ≈ params × 2 × context / 1e9`（GB），或从实测数据拟合
3. 放宽 loading 状态阈值：对于已知大 context 模型，差异阈值从 1GB 提高到 3GB

### 问题 2：QoS utilization 字段未同步到 /api/status

**现象**：观察脚本读取 `/api/status.qos.utilization` 显示为空，但 QoS 水位变化证明利用率在内部起作用。

**根因**：`qos_enforce()` 中更新 `_qos` 全局变量的代码可能有执行顺序问题，或 `_qos` 初始值缺少 utilization 字段。

**优化建议**：检查 `qos_enforce()` 中 `_qos["utilization"] = q.get("utilization", 0)` 的执行路径，确保每次调用都更新。

### 问题 3：自动登记的小模型显存估算偏高

**现象**：
- minicpm5-1b:q4km 实际 688MB，估算 1.5GB（偏高 118%）
- minicpm5-fable5:q8 实际 1.2GB，估算 2.0GB（偏高 67%）
- qwen3.5:0.8b 实际 1.0GB，估算 1.8GB（偏高 80%）

**根因**：`_estimate_ollama_vram()` 公式 `params × q + 1.0` 中的 1GB 固定开销对小模型偏大。

**优化建议**：
- 小模型（<2B）开销改为 0.3GB
- 或用分段函数：`overhead = max(0.3, params × 0.3)`

### 问题 4：QoS 水位偶尔异常（空闲时显示 red）

**现象**：12:22:xx GPU 仅 1.0GB（空闲）但 QoS=red，持续约 30 秒后恢复。

**根因**：可能是 QoS 冷却防抖机制的副作用，或 `_qos` 全局变量未及时更新。

**优化建议**：在 `qos_enforce()` 开头增加水位重置逻辑，如果 `qos_check()` 返回 green 且已降级，立即恢复（不受冷却限制）。
