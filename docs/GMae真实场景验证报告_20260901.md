# GMae-16GAS 真实场景验证报告

> **目的**：模拟真人用 AI 干活，验证 GMae 是否真的能帮上忙、有多大价值。
> **测试时间**：2026-09-01
> **测试环境**：Windows + WSL2 + Docker，16GB GPU，ComfyUI/Ollama 容器
> **测试方法**：5 个真实用户场景，自动化脚本执行，记录显存/告警/切换/队列等关键指标
> **结论**：核心能力验证有效，但发现 2 个 P0 级问题，建议修复后再标记 V1.0

## 二、各场景详细结果

### 场景5：新手第一天 — ✅ 6/6 通过

**模拟**：新手同时启动 Ollama qwen3.5:9b + ComfyUI SDXL，不懂显存管理。

**关键数据**：
- 基线显存：1.3GB
- 加载 qwen3.5:9b 后：12.0GB，guard=warning，建议"停止qwen3.5可释放10GB"
- 加载 SDXL 后：15.9GB（空闲仅192MB），guard=critical，告警"逼近打满，死机风险"
- 一键释放后：0.9GB，恢复正常

**验证通过项**：
1. ✅ 显存数据准确（GMae vs nvidia-smi 误差仅 4MB）
2. ✅ Ollama 模型加载后正确感知
3. ✅ guard_level 正确升级（ok→warning→critical）
4. ✅ 建议具体可操作（"停止 qwen3.5:9b，可释放 10.0GB"）
5. ✅ 系统进程（dwm/explorer等）不误报为未登记
6. ✅ 一键释放后显存恢复

**价值**：新手能实时看到显存状态和具体建议，不会盲目操作导致死机。

---

### 场景2：贪心创作者 — ⚠️ 3/6，核心功能验证成功

**模拟**：用户加载 qwen3.5:9b（10GB）后，还想跑 Flux（12GB），强行启动 SDXL。

**关键数据**：
- 预算引擎：Flux-Q5 decision=free_L2，need_free=0.2GB，"释放 ComfyUI /free 后可加载" ✅
- 强行加载 SDXL 后：峰值 16.1GB，空闲仅 247MB
- **自动防死机触发**：执行 L2 动作"ComfyUI 释放生成模型显存" ✅
- 系统未死机 ✅

**重大发现：自动防死机确实能救命！**
- 空闲显存降到 247MB 时自动触发
- 执行了 ComfyUI 模型释放
- last_trigger 和 history 都有记录
- （场景5中怀疑没触发，是因为测试脚本在触发前就手动释放了）

**发现的问题**：
1. 🟡 自动防死机触发延迟：emergency_threshold 设的是 2GB，但实际在 247MB 才触发。原因是 QoS 检查间隔 10 秒，而 SDXL 加载时显存增长太快。
2. 🟡 GMae 的 /api/free 没有完全释放 ComfyUI 模型（SDXL 仍在缓存中，需直接调用 ComfyUI /free）

---

### 场景4：创作流中断恢复 — ⚠️ 4/7，发现 P0 崩溃

**模拟**：ComfyUI 出图中，用户突然切到 Ollama 查资料，查完切回来。

**关键数据**：
- 队列功能工作：3个任务入队，worker 自动启动，2个完成，1个运行中 ✅
- 队列状态在场景切换后保留 ✅
- **场景切换到 chat 时 API 崩溃**：返回 "Remote end closed connection without response" ❌
- 切换失败导致显存爆炸：SDXL（6.5GB）未释放 + qwen3.5:9b（10GB）= 15.9GB，空闲仅 155MB ❌
- Ollama 响应超慢（180秒），因显存不够在使用内存交换
- 切回 comfy 成功（26.2秒）

**发现的问题**：
1. 🔴 **P0：场景切换到 chat 时 server 崩溃**——第一次调用经常返回连接关闭，需重试。崩溃原因待查（可能是 scene_switch 中的某个操作导致 server 异常）。
2. 🟡 无队列 pause/resume API——只有 enqueue/cancel/snapshot，中断恢复依赖场景切换，不是队列级别的断点续跑。

---

### 场景1：漫剧创作者一天 — ⚠️ 2/4 切换成功

**模拟**：创作者一天的工作流——对话写剧本→出图→对话查资料→出图。

**关键数据**：
- 4 次场景切换：2 次成功（切 comfy），2 次崩溃（切 chat）
- 成功率：50%
- 平均切换耗时：8.7 秒（成功的两次 12.6s + 13.0s）
- 全程未死机 ✅

**发现的问题**：
1. 🔴 **P0：切到 chat 场景时 100% 崩溃**（2/2 次都崩），切到 comfy 正常。说明 chat 场景的切换逻辑有 bug。
2. 🟡 切换耗时偏长（12-13秒），目标 <10 秒。

---

### 场景3：夜间无人值守批量 — ⚠️ 4/5 完成，发现不串行

**模拟**：睡前提交 5 个出图任务，队列自动执行。

**关键数据**：
- 5 个任务入队，4 个完成，1 个失败，完成率 80% ✅
- 队列 worker 自动运行 ✅
- **严重问题：max_running=4，同时有 4 个任务在执行！** ❌
- 队列没有严格串行，16GB 卡上同时跑 4 个任务非常危险

**发现的问题**：
1. 🔴 **P0：队列不严格串行**——同时跑 4 个任务，违反"16GB 卡必须串行"的核心设计原则。可能是队列 worker 的并发控制有问题，或 ComfyUI 自身队列在并行。
2. 🟡 队列中有历史残留任务（场景4的 3 个任务还在），没有清理机制。
3. 🟡 1 个任务失败，失败原因待查。

## 三、问题汇总（按优先级）

### 🔴 P0 级（必须修复，否则 V1.0 不能发布）

| 编号 | 问题 | 影响 | 复现方式 |
|------|------|------|---------|
| P0-1 | 场景切换到 chat 时 server 崩溃 | 用户无法从出图态切到对话态，核心功能不可用 | POST /api/scene {"scene":"chat"}，返回"Remote end closed connection" |
| P0-2 | 队列不严格串行，同时跑4个任务 | 16GB 卡上并发执行可能 OOM 死机，违反核心设计原则 | 提交5个任务到队列，观察到 max_running=4 |

### 🟡 P1 级（建议修复，影响体验）

| 编号 | 问题 | 影响 |
|------|------|------|
| P1-1 | 自动防死机触发延迟（阈值2GB但247MB才触发） | 极端情况下可能来不及释放就死机了 |
| P1-2 | GMae /api/free 不完全释放 ComfyUI 模型 | 释放后仍有 6-7GB 模型缓存残留 |
| P1-3 | 场景切换耗时 12-13 秒 | 用户等待时间偏长，目标 <10 秒 |

### 🟢 P2 级（可后续优化）

| 编号 | 问题 | 影响 |
|------|------|------|
| P2-1 | 无队列 pause/resume API | 中断恢复只能靠场景切换，不是队列级断点续跑 |
| P2-2 | 队列无历史残留清理机制 | 旧任务一直留在任务列表中 |
| P2-3 | 单元测试运行器路径 bug | 已修复（run_tests.py 的 BASE_DIR 少一层 dirname） |

## 四、价值判断

### GMae 确实能帮上忙的地方

1. **显存可视化**：实时显示显存占用、进程级明细，用户不再是"黑盒操作"
2. **预算引擎**：加载模型前先算账，告诉用户"够不够、差多少、释放什么"，避免盲目试错
3. **自动防死机**：显存快满时自动释放模型，关键时刻能救命（已验证触发）
4. **门卫检测**：未登记进程及时告警，防止偷偷占显存
5. **一键释放**：模型级释放替代容器重启，10-30秒 → 秒级
6. **批量队列**：支持任务排队自动执行，可无人值守

### 还不够的地方

1. **场景切换不稳定**：切 chat 必崩，这是核心功能，必须修复
2. **队列不串行**：这是 16GB 卡的生命线，必须修复
3. **释放不彻底**：ComfyUI 模型缓存残留，需要二次释放

### 用户视角价值评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 显存感知准确性 | 9/10 | 误差仅 4MB，非常准 |
| 预算引擎实用性 | 8/10 | 计算准确，建议具体 |
| 自动防死机 | 7/10 | 能触发但有延迟 |
| 场景切换 | 3/10 | 切 chat 必崩，不可用 |
| 队列管理 | 4/10 | 能排队但不串行，危险 |
| 一键释放 | 6/10 | 能释放但不彻底 |
| **综合** | **6.2/10** | 核心能力有效，但 2 个 P0 问题严重影响使用 |

## 五、V1.0 发布建议

### 当前状态：不建议直接标记 V1.0

**理由**：2 个 P0 问题（场景切换崩溃、队列不串行）都是核心功能缺陷，会直接导致用户在正常使用中遇到崩溃或 OOM 风险。

### 建议的 V1.0 发布门槛

1. **必须修复 P0-1**：场景切换到 chat 时的崩溃
   - 排查 scene_switch 函数中 chat 场景的执行逻辑
   - 可能是某个 docker 操作或 PowerShell 脚本导致 server 异常
   - 修复后 4 次切换全部成功

2. **必须修复 P0-2**：队列严格串行
   - 确保同一时间只有 1 个任务在执行
   - 排查队列 worker 的并发控制逻辑
   - 可能需要限制 ComfyUI 自身的队列并发数

3. **建议修复 P1-2**：ComfyUI 释放不彻底
   - 确保 /api/free 调用 ComfyUI /free 后等待生效
   - 或增加轮询确认显存已释放

4. **修复后重测**：5 个场景全部重新跑一遍，确保全部通过

### 修复后的 V1.0 预期

- 5 个场景全部通过
- 场景切换成功率 100%，平均耗时 <10 秒
- 队列严格串行，完成率 >90%
- 自动防死机触发延迟 <5 秒
- 综合价值评分 >8/10
