# 显存管理指南（16GB 消费级显卡）

> **适用**：RTX 4060 Ti / 3060 / 4070 等 16GB 单卡环境，同时跑对话 + 文生图 + 视频 + 音乐等多类 AI 负载。
> **核心教训**：显存打满 = 系统死机（不是性能问题，是稳定性问题）。16GB 物理装不下所有模型，必须靠规则错峰。
>
> 📖 **本文件为开源项目精简版**。完整运维版（含 RED·MUST·SHOULD 分层细则、H3/Music3 独占态登记、准入流程）见家庭智能中枢内部文档 `docs/显存管理最高指南.md`（v1.3）。

---

## 一、硬件硬约束

| 项 | 值 | 说明 |
|---|---|---|
| GPU | 16GB 单卡 | 无扩展，任何方案绕不开 16G 天花板 |
| 固定底噪 | ~1.0–1.5GB | 桌面+浏览器+WSL/Docker 底座，腾不出 |
| 可给 AI 负载 | ~14.5GB | 16 − 底噪 |
| 物理内存 | 建议 32GB+ | 大模型 offload 依赖内存，内存打满会换页死机 |

> ⚠️ **死机根因链**：显存打满 → 模型加载失败 → 推理服务重试循环 → 进程内存泄漏 → 物理内存打满 → 换页 → 系统死机。**显存必须永远留余量。**

## 二、显存预算账本

> 任何新模型上线前，先查本表算总账。未登记的占用 = 违规。

| 占用方 | 运行时显存 | 允许状态 |
|---|---|---|
| 系统底噪 | ~1.0–1.5GB | 恒在 |
| 9B 对话模型 | ~6.6–8.4GB（8K~16K ctx） | 仅对话态 |
| SDXL 出图 | ~6.5GB | 仅出图态 |
| Flux (Q5 GGUF) | ~13GB | 仅 Flux 出图态，**独占全卡** |
| MiniMax Music 3 | 峰值 ~14.5GB | 仅音乐态，**独占全卡** |
| MiniMax H3 视频 | ~12.8–14GB | 仅出视频态，**独占全卡** |
| Fooocus (Juggernaut XL) | ~6.9GB（启动即预加载） | **禁止常驻**，用时才启 |
| 游戏串流 | ~2–4GB | 仅游戏态 |

## 三、状态机（核心）

> 任意时刻必须处于且仅处于一个稳态。**状态切换必须先释放对方资源，不许"边用边挤"。**

| 稳态 | 允许占用 | 合计 | 余量 |
|---|---|---|---|
| 对话态（默认） | 9B + 底噪 | ~7.6–9.9GB | ✅ 充足 |
| SDXL 出图态 | SDXL + 底噪 | ~7.5–8GB | ✅ 充足 |
| Flux 出图态 | Flux + 底噪 | ~14–14.5GB | 🔴 极限，桌面程序尽量关 |
| 音乐态 | Music3 + 底噪 | ~15.5–16GB | 🔴 独占全卡，生成完自动卸载 |
| H3 出视频态 | H3 + 底噪 | ~13.8–15.5GB | 🔴 极限，offload 到内存 |
| 游戏态 | 游戏 + 底噪 | ~3–5.5GB | ✅ 宽松 |

### 切换规则

| 切换 | 必须动作 |
|---|---|
| 对话 → 出图/出视频/出音乐 | ① `gpu_release.ps1` 释放全部模型 ② 确认显存 <4GB ③ 启动目标负载 |
| 出图 → 对话 | 无需手动（模型按需自动加载） |
| 任意 → 游戏 | 释放全部 AI 模型 + 停文生图容器 |

> **切换纪律**：先释放、后占用、再验证。释放后必须 `nvidia-smi` 确认水位达标。

## 四、铁律

### 🔴 RED · 红线（违反 = 立即停用）

| # | 条款 |
|---|---|
| R1 | 禁止两个大模型（≥5GB 级）同时常驻显存 |
| R2 | 禁止 Flux / H3 / Music3 与任何其他 AI 负载共存（独占全卡） |
| R3 | 禁止 num_ctx 超 8192（9B 模型 32K → KV cache 13.7GB 爆显存） |
| R4 | 禁止 GPU embedding（必须用 CPU 版，如 bge-m3-cpu） |
| R5 | 禁止 Fooocus/ComfyUI 模型常驻于对话态（用毕停容器） |
| R6 | 禁止未过准入的新服务占用显存 |

### ✅ MUST · 必须遵守

| # | 条款 |
|---|---|
| M1 | 出图/出视频/出音乐前必须先释放，确认显存 <4GB |
| M2 | ComfyUI 启动必须带 `--reserve-vram 2.5`（为 OS 留余量） |
| M3 | keep_alive 统一 30m（避免频繁换载，也避免常驻） |
| M4 | 大模型 offload 时监控宿主内存，<5GB 空闲勿开跑 |
| M5 | 每次显存相关变更必须登记本账本 |

## 五、各应用合规细则

### 5.1 Ollama（对话推理）

| 配置项 | 合规值 | 违规后果 |
|---|---|---|
| MAX_LOADED_MODELS | 2 | 多模型并存挤爆显存 |
| KEEP_ALIVE | 30m | 模型横跳/常驻冲突 |
| CONTEXT_LENGTH | 8192（默认），最高 16384 | >16K → 显存爆 |
| embedding | CPU 版（bge-m3-cpu） | GPU embed = 泄漏触发器 |

> **假死特征**：端口 LISTENING 但 API 请求超时 + CLOSE_WAIT 堆积 = 假死，不是慢。处置：杀全部进程 → 重启 → 验证。

### 5.2 ComfyUI（多模态生成）

- ✅ `--reserve-vram 2.5` 必带；空闲不加载模型（动态 VRAM）
- ❌ Flux/H3/Music3 与任何 AI 负载共存
- 📌 **Music 3**：峰值 14.5GB，生成完自动卸载回底噪；30s≈82s / 60s≈127s / 90s≈3-5min
- 📌 **H3 视频**：Turbo LoRA 4 步 + euler，~4 分钟出片；`POST /free` 卸载模型
- 📌 **Flux**：Q5 GGUF，cfg=1，euler，20 步；Q8 会压垮引擎，禁用

### 5.3 Fooocus（极简出图）

- 🔴 启动即预加载 ~6.9GB → **用毕必须 `docker stop fooocus`**，不许常驻

## 六、新服务准入流程

任何要碰 GPU 显存的新应用，上线前必须逐项过：

1. **算账**：登记峰值显存 + 允许状态
2. **共存**：与状态机逐组合核算，确认不会挤爆
3. **释放机制**：提供"释放自身显存"的明确动作
4. **启动参数**：带 `--reserve-vram` 或等价预留
5. **实测峰值**：真实跑一次，记录峰值显存（≠理论值）
6. **登记**：更新本账本

**未过 1-6 的服务 = 违规，不得上线。**
