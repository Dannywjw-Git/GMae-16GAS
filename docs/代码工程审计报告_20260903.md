### R2：全局可变变量 — ⚠️ 部分违规

**合规部分（单例注册表，指南允许）**：
- `core/registry.py:111` — `registry = StateRegistry()`（唯一状态持有者）

**违规部分（真正的可变状态散落在模块级）**：

| 文件 | 变量 | 问题 |
|------|------|------|
| engine/queue.py:25-37 | `_queue_state`, `_tasks`, `_task_queue` | 队列状态虽存入 registry，但取出后保持模块级直接引用，绕过 registry 锁 |
| engine/qos.py:33-45 | `_qos_state`, `_qos_lock` | QoS 状态同上模式，有独立锁但未走 registry.lock() |

| services/scene.py:26,61 | `_scene_lock`, `_last` | 场景锁和最后状态 |
| services/vram_helper.py:56 | `_last_activity` | 最后活动时间 |
| engine/scanner.py:27 | `_auto_scanner_running` | 扫描器运行标志 |

**风险**：这些状态虽有锁保护，但分散在各模块，违反 M2"唯一状态持有者"原则。新增模块时容易遗漏锁，且难以统一审计。

**建议**：将这些状态的读写统一通过 `registry.get()/set()` + `registry.lock(namespace)` 进行，模块级只保留对 registry 的引用，不保留状态对象的直接引用。

## 三、必须条款（MUST）逐项检查

### M1：分层架构 — ⚠️ 基本合规，依赖方向有违规

**现有分层**（实际 8 个目录，比指南建议的 4-5 层多，但职责清晰）：

```
vram-console/
├── server.py          # 入口层（136行，合规）
├── api/               # API 层（endpoints/ 按资源拆分，routes.py 总装）
├── core/              # 核心层（registry/config/logger/exceptions/event_bus 等）
├── engine/            # 引擎层（调度/QoS/队列/预算/诊断等，相当于指南的 core+services）
├── services/          # 服务层（外部服务编排，与 engine 职责有重叠）
├── clients/           # 客户端层（外部服务 API 封装，未充分使用）
├── gpu/               # GPU 专用层（monitor/process_guard）
├── observability/     # 可观测层（health_probe）
├── meng/              # 模型评测层（benchmark_engine 等）
├── ceng/              # 认知引擎层（LLM 对话/工具调用）
├── cli/               # CLI 客户端
└── utils/             # 工具函数（合并在 core/utils.py）
```

**依赖方向违规**：

| 违规类型 | 数量 | 详情 |
|---------|------|------|
| clients → core（反向依赖） | 5 个文件 | comfyui_client, docker_client, helper_client, nvidia_smi, ollama_client 均 import core（主要是 core.logger 和 core.config） |
| engine → services（模块级导入） | 5 个文件 | budget, eviction_guard, qos, reaper, scanner 均在模块级 import services |

**分析**：
- clients → core 的依赖：主要是 import `core.logger`（日志工具）和 `core.config`（配置）。指南规定 clients 不得 import core，但日志和配置是横切关注点。**务实建议**：将 logger 和 config 提取到独立的 `common/` 或 `infra/` 层，允许所有层依赖；或者允许 clients import core.logger/core.config（作为例外，需在指南中明确）。
- engine → services 的依赖：engine 层调用 services 层的外部服务编排函数，这是**分层方向错误**（engine 应比 services 更核心，不应依赖 services）。实际代码中已大量使用"函数内延迟导入"（qos.py 有 13 处函数内导入 services），说明开发者已意识到这个问题但未彻底解决。

**建议**：
1. 明确 engine 和 services 的职责边界：engine = 纯业务逻辑（调度/预算/QoS），services = 外部服务编排（调用 Ollama/ComfyUI/Docker）。engine 需要外部服务时通过 clients 层，不通过 services 层。
2. 将 services 层中被 engine 调用的纯逻辑（如 docker_containers, ollama_ps）下沉到 clients 层，services 层只做组合编排。

### M2：状态管理 — ⚠️ Registry 存在但未完全集中

**优点**：
- `core/registry.py` 实现了线程安全的全局状态注册表（单例 + 全局锁 + 命名空间锁 + 原子操作方法）
- 队列状态、QoS 状态、自动防死机状态等已"存入" registry（通过 `registry.set()` 初始化）

**问题**：
- 如 R2 所述，状态从 registry 取出后保持模块级直接引用（`_tasks = _queue_state["tasks"]`），后续修改绕过 registry 的锁和方法
- 各模块使用自己的 `_lock`（`_task_lock`, `_qos_lock`, `_gpu_status_lock`），未使用 `registry.lock(namespace)` 统一管理
- 状态变更日志不统一：部分模块有 `log_event`，部分没有

**建议**：
1. 短期：在各模块的模块级状态旁添加 `# TECHNICAL_DEBT: 状态应通过 registry 统一管理` 标记
2. 中期：将高频读写的状态（队列、QoS）改为通过 registry 方法访问，移除模块级直接引用
3. 长期：实现状态变更审计钩子（registry.set 时自动记录变更前后值和触发原因）
