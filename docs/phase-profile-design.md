# 驻留复用与分阶段显存预算：下一阶段设计

状态：分阶段预算已按限定 SDXL 双证据实现，正式队列初步验证见 [驻留准入报告](resident-phase-admission-2026-10-08.md)；只读来源观察已在 PR #11/#12 实现并完成当前 SDXL 实机验收，见 [启动与驻留验证](comfy-startup-residency-validation-2026-10-08.md)。依据：[测量准入](measured-profile-admission-2026-10-08.md)及本阶段真实加载条件试验。不能因该文档存在而宣称暖启动准入或性能提升已完成。

## 必须解决的问题

当前预算把整卡峰值再加到当前整卡占用上，同模型复用也可能要求卸载。另一个冲突来自 `/history` 的文件名与注册表模型 ID 不一致。简单改名或将“已加载”的峰值变成零，会把未知/部分卸载状态误判为容量保证。

512×512 实验中保留驻留时仍观察到额外整卡占用，不能把 warm growth 假定为零。卸载后 `/free` 首次读数可能没有任何回收，随后 torch 下降与物理读数才逐步变化。必须把冷加载、驻留生成和释放核验分开。

## 下一阶段实施边界

增加可选的 ComfyUI 只读观察扩展，读取真实 loaded-model 对象与已加载字节；启动实例身份与模型来源绑定。已部署源码的 `LoadedModel.model_loaded_memory()` 调用实际 `ModelPatcher.loaded_size()`；它比历史模型名更接近实际驻留量，但没有提供 checkpoint 文件身份，需要在标准 loader 返回对象时记录来源，再以对象弱引用匹配。只支持已核验的原生 SDXL loader，未知对象必须显式报 unknown。

扩展不修改调度、模型参数或 GPU 配额。接口缺失、版本不支持、对象来源不明、文件改变、模型部分卸载、队列忙碌或实例重启时，不采用 warm 准入。继续使用保守预算或拒绝，不能回退历史名猜测。

拟议快照包含：schema、backend_instance_id、采集时间、活动状态、checkpoint 来源摘要/加载时文件身份、每个组件的来源和实际 resident_bytes、unknown_components、torch 占用。模型摘要应复用已核验的不可变文件身份，不能只因 basename 相同确认模型一致。不要公开私有模型路径。

## Profile 条件与预算

冷/驻留试验分别保存起始整卡占用、起始 torch/组件驻留、完整采样、成功终态、未缓存采样器、实际工作流、模型/服务/GPU 身份。复用只改变 seed 与输出名，不外推尺寸、批量或提示词。

候选驻留增量为每次试验 `max(0, observed_peak - baseline_used)`，取多次上界并加入明确余量。仅在 fresh 组件集合、身份及驻留量满足校准前提时，候选预测采用 `fresh_used + measured_growth + margin`，再检查保留空间。观测增量不直接安装为可用预算；先通过自动化拒绝场景与真实对照验证。采样漏峰、背景变化和外部客户端仍使该模型不构成 OOM 保证。

实现时起点、峰值和 fresh 占用必须统一使用 `max(used_mb, total_mb - free_mb)` 的保守计数口径，不能把 Windows 下不守恒的读数当作额外容量。本阶段报告增长仅是原始 used 读数的描述性差值，不是该安全预测的实现或验收。

## 验收与对照

必须验证未知模型、部分卸载、后端重启、来源文件替换、缺失接口、活动竞争和取数失败不会采用 warm 路径。验证原队列持久化、未知请求阻挡与所有权机制保持有效。

真实比较使用同一工作流和不同 seed，记录身份核验是否计入时间、加载状态、卸载次数、成功率、端到端耗时和整卡峰值。分别报告原保守协调器、驻留复用协调器及直接提交的结果，不能把不同条件的裸加载时间直接称为 GMae 加速。重复次序应交错；每次都确认没有其他用户工作。保留失败及原始文件。

发布前还需要混合 AI 工作负载与参数网格；本设计只解决第一项已知性能瓶颈，不替代完整竞赛验收。
