## 四、详细问题分析

### 4.1 错误处理（最严重，6/15分）

**问题描述**：
15+ 处 `except Exception: pass`，错误被静默吞掉，导致：
- 问题不可追溯
- 调试困难
- 潜在的数据丢失或状态不一致

**根本原因**：
- 开发时为了快速跑通，用 `pass` 跳过异常处理
- 缺乏统一的错误处理规范
- 没有代码审查机制

**影响范围**：
- engine/ 层（核心业务逻辑）有 10 处
- services/ 层有 1 处
- api/ 层有 2 处
- server.py 有 2 处

### 4.2 前端代码结构（严重，影响代码风格得分）

**问题描述**：
`web/js/app.js` 2184 行，包含：
- 路由注册（Router）
- 全局状态管理（State）
- API 封装（API）
- 工具函数（Utils）
- 5+ 个页面逻辑（Dashboard、VRAM、Models、Alerts、Settings）
- 组件渲染

**根本原因**：
- 前端重写时为了快速交付，所有逻辑写在一个文件
- 缺乏前端代码分层规范
- 只有 topology.js 做了独立拆分（378行）

**影响**：
- 代码难以维护
- 修改一个页面需要翻找2000+行
- 容易引入回归 bug
- 违反 R1 红线

### 4.3 外部服务封装（不合格，5/10分）

**问题描述**：
9 个文件直接调用 `requests.get/post` 或 `subprocess.run`，未通过 Client 类。

**根本原因**：
- Client 层只覆盖了主要服务（ollama/comfyui/docker/nvidia_smi）
- 新增的服务（helper、health_probe、docker_events）没有封装到 Client
- 工具函数（utils.py）中散落了外部调用

**影响**：
- 接口不统一
- 难以 mock 测试
- 错误处理不一致
- 违反 R7 红线

### 4.4 架构与分层（合格，12/20分）

**问题描述**：
顶层目录 17 个，结构混乱：
```
api/ ceng/ cli/ clients/ core/ docs/ engine/ gpu/ legacy/
logs/ meng/ observability/ resources/ services/ tests/ web/ workflows/
```

**问题分析**：
- `engine/` 和 `core/` 职责重叠（都有业务逻辑）
- `ceng/`、`meng/` 是实验性模块，应归档或明确分层
- `observability/` 应合并到 `engine/` 或 `services/`
- `workflows/` 应合并到 `engine/`
- `gpu/` 应合并到 `clients/`（nvidia_smi 已在 clients）

**影响**：
- 新代码不知道放哪层
- 模块边界模糊
- 依赖方向可能混乱

### 4.5 状态管理（合格，10/15分）

**问题描述**：
Registry 存在（85行），但可能有状态散落在其他模块。

**待确认**：
- 所有共享状态是否都在 Registry 中？
- Registry 内部所有读写方法是否都加锁？
- 状态变更是否都记录了日志？

## 六、结论

当前代码质量 **C 级（61分）**，低于健康目标（B级70分）。

**主要问题**：
1. **错误处理**（静默吞异常，最严重）
2. **前端代码结构**（app.js 上帝文件）
3. **外部服务封装**（直接调用散落）

**好消息**：
- Python 后端代码质量尚可（行数控制、类型注解、测试覆盖都不错）
- 主要问题集中在前端和错误处理
- 改进工作量可控（预计 1-2 天可完成 P0 项）

**建议**：
优先解决 P0 问题（错误处理 + app.js拆分），完成后评分可提升到 **70-75 分（B级健康状态）**。
