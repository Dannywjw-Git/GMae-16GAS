# 16GAS 基础设施对接修复计划 v1.0

> **创建时间**：2026-09-02
> **背景**：S1/S2/S3 基础设施（StatusCache/EventBus/AlertManager/规则引擎/故障场景库）已全部编写完成，也有对应的 API 端点和前端页面，但**基础设施与业务逻辑之间没有对接**，导致所有这些功能在实际运行时都是空的。
> **目标**：将 S1/S2/S3 的基础设施与业务逻辑对接，让事件流、告警流、诊断流真正跑起来，用户能在 WEBUI 中看到真实的数据。

---

## 一、问题审计结果

### 1.1 S1 轻量采集优化

| 组件 | 状态 | 问题 |
|------|------|------|
| StatusCache 类 | ✅ 代码完整 | ❌ **没被使用**。`services/status.py` 的 `current_status()` 用的是 `registry.get("status_cache", {})` 简单字典缓存，不是 `core/status_cache.py` 的 `StatusCache` 类 |
| Docker Events 监听 | ✅ 线程在运行 | ⚠️ 回调 `docker_events.on_state_change = lambda: status_cache.invalidate()` 调用的是 `core.status_cache.status_cache` 对象，但这个对象的缓存是空的（current_status 没往里面存），所以**失效无效** |
| 并行采集 | ✅ 在使用 | `_fetch_parallel_status()` 正常工作 |

**影响**：
- 容器启动/停止后，status 缓存不会立即失效，用户可能看到旧数据（最多2.5秒延迟）
- StatusCache 的高级功能（危险状态缩短TTL、后台异步刷新、线程安全）完全没用到

### 1.2 S2 事件关联引擎

| 组件 | 状态 | 问题 |
|------|------|------|
| EventBus 类 | ✅ 代码完整 | ❌ **没有任何业务代码调用 `event_bus.publish()`** |
| log_event 函数 | ✅ 100+处调用 | ❌ **只写日志文件**（`logger.info(json.dumps(entry))`），没有发布到 EventBus |
| /api/events/timeline | ✅ API存在 | ❌ 返回空列表（EventBus 是空的） |
| 前端"最近事件" | ✅ 页面存在 | ❌ 显示"暂无事件" |
| 前端"事件时间线" | ✅ 页面存在 | ❌ 显示空 |
| 规则引擎 | ✅ 9条规则 | ⚠️ 可调用，但依赖事件数据做根因分析，而事件是空的，诊断结果不准确 |
| 用户操作审计 | ✅ 设计了13个写操作端点 | ❌ **没有记录**（写操作没有发布审计事件到 EventBus） |

**影响**：
- Dashboard 的"最近事件"永远是空的
- 诊断中心的"事件时间线"永远是空的
- 根因诊断没有事件数据支撑，只能返回默认诊断
- 用户操作（启动/停止服务、加载/卸载模型、切换场景等）没有审计记录

### 1.3 S3 故障场景库+告警降噪

| 组件 | 状态 | 问题 |
|------|------|------|
| AlertManager 类 | ✅ 代码完整 | ❌ **没有任何业务代码调用 `alert_manager.submit()`** |
| /api/alerts 等6个API | ✅ API存在 | ❌ 返回空列表（AlertManager 是空的） |
| 前端告警中心 | ✅ 页面存在 | ❌ 显示"暂无告警" |
| 告警升级线程 | ✅ 每60秒运行 | ⚠️ 在运行，但没有告警可升级 |
| 故障场景库 | ✅ 5个场景文档 | ❌ **没有和诊断/告警对接**，前端也没有展示 |
| 告警聚合/降噪 | ✅ 逻辑完整 | ❌ 没有实际数据可处理 |

**影响**：
- 告警中心永远是空的
- 显存危险、服务故障、模型加载失败等异常情况不会自动产生告警
- 告警聚合/静默/升级等高级功能完全没用到
- 故障场景库的知识没有被利用

## 二、修复计划（分三阶段）

### P0：核心对接（让事件流和告警流跑起来）

**目标**：EventBus 和 AlertManager 不再是空的，用户能在 WEBUI 中看到真实的事件和告警。

#### P0.1：log_event 对接 EventBus

**改动文件**：`core/logger.py`

**改动内容**：
- 在 `log_event()` 函数中增加 `event_bus.publish()` 调用
- 将 log_event 的参数映射到 EventBus 的事件结构：
  - `event_type` → `event`（事件类型）
  - `kwargs` → `metadata`（事件元数据）
  - 自动推断 `category`（vram/container/model/task/user_action/system/guard）
  - 自动推断 `level`（debug/info/warning/error/critical）
  - `source` = 调用模块名
  - `message` = 从 kwargs 中提取或自动生成

**事件类别映射规则**：
- 包含 `vram`/`gpu`/`memory` → `vram`
- 包含 `container`/`docker` → `container`
- 包含 `model`/`ollama`/`comfy` → `model`
- 包含 `task`/`queue` → `task`
- 包含 `user_action`/`audit` → `user_action`
- 包含 `guard`/`evict`/`kick` → `guard`
- 其他 → `system`

**事件级别映射规则**：
- `log_error()` → `error`
- `log_event()` 中包含 `fail`/`error`/`critical`/`danger` → `error` 或 `critical`
- `log_event()` 中包含 `warn`/`warning` → `warning`
- 其他 → `info`

**验证方法**：
1. 启动服务，执行任意操作（如切换场景）
2. `curl /api/events/timeline` 应返回非空事件列表
3. 前端 Dashboard 的"最近事件"应显示事件

---

#### P0.2：写操作端点增加用户操作审计

**改动文件**：`api/endpoints/` 下的 service.py、scene.py、vram.py、model.py、guard.py、queue.py

**改动内容**：
- 在13个写操作端点的成功路径中，调用 `log_event()` 并标记 `category="user_action"`
- 记录内容：操作类型、操作对象、操作结果、操作时间
- 示例：
  ```python
  log_event("user_service_stop", category="user_action", service=name, result="success")
  ```

**13个写操作端点清单**：
1. POST /api/service（start/stop/restart）
2. POST /api/scene（切换场景）
3. POST /api/free（一键释放）
4. POST /api/model（load/unload）
5. POST /api/guard（check/evict/kick）
6. POST /api/queue（提交任务）
7. POST /api/queue/cancel（取消任务）
8. POST /api/alerts/silence（静默告警）
9. POST /api/alerts/resolve（解决告警）
10. POST /api/scan/register（登记模型）
11. POST /api/diagnose（执行诊断）
12. POST /api/qos/execute（执行QoS建议）
13. POST /api/service（action=restart）

**验证方法**：
1. 在前端执行任意写操作（如停止一个服务）
2. `curl /api/events/timeline?category=user_action` 应返回审计事件
3. 诊断中心的事件时间线应显示用户操作事件

#### P0.3：告警源对接 AlertManager

**改动文件**：`services/status.py`、`engine/qos.py`、`gpu/monitor.py`、`services/docker.py`

**改动内容**：
- 在检测到异常情况时，调用 `alert_manager.submit()` 提交告警
- 告警源清单：

| 告警类型 | 触发条件 | 级别 | 来源文件 |
|---------|---------|------|---------|
| `vram_critical` | 空闲显存 < 1GB | critical | services/status.py（_build_vram_ledger） |
| `vram_danger` | 空闲显存 < 2GB | error | services/status.py |
| `vram_warning` | 空闲显存 < 4GB | warning | services/status.py |
| `vram_unaccounted` | 未登记显存 > 2GB | warning | services/status.py |
| `qos_degraded` | QoS 降级 | warning | engine/qos.py |
| `service_down` | 关键服务停止 | error | services/docker.py |
| `model_load_failed` | 模型加载失败 | error | services/scene.py |
| `guard_evicted` | 门卫驱逐进程 | warning | gpu/monitor.py |

**告警去重**：
- 相同类型的告警在 `cooldown_s` 秒内只提交一次（默认60秒）
- 告警恢复时（如显存从 danger 回到 ok），自动 resolve 之前的告警

**验证方法**：
1. 模拟显存危险（如加载大模型）
2. `curl /api/alerts` 应返回非空告警列表
3. 前端告警中心应显示告警
4. Dashboard 顶部应显示告警横幅

### P1：增强对接（让诊断和缓存真正生效）

#### P1.1：current_status 改用 StatusCache 类

**改动文件**：`services/status.py`

**改动内容**：
- 将 `current_status()` 中的 registry 简单字典缓存改为使用 `core.status_cache.status_cache` 对象
- 使用 `status_cache.try_background_refresh(_fetch_and_assemble)` 方法
- 享受 StatusCache 的高级功能：
  - 危险状态（danger/critical）TTL 缩短为2秒
  - 后台异步刷新（不阻塞请求，返回旧数据+stale标记）
  - 线程安全
  - 深拷贝（避免外部修改缓存）

**Docker Events 回调修复**：
- 确认 `docker_events.on_state_change = lambda: status_cache.invalidate()` 现在能真正失效缓存
- 因为 current_status 现在使用同一个 status_cache 对象

**验证方法**：
1. 启动服务，频繁请求 `/api/status`，观察响应时间（缓存命中应<10ms）
2. 启动/停止一个容器，立即请求 `/api/status`，应返回新数据（缓存已失效）
3. 显存危险状态时，观察缓存TTL是否缩短（可通过日志或响应中的 cached_at 字段判断）

## 五、风险与注意事项

1. **log_event 性能影响**：log_event 被调用100+次，增加 event_bus.publish() 可能影响性能。EventBus 的 publish 应该是轻量级的（内存操作，环形缓冲区），不会有明显性能影响。但需要监控。

2. **告警风暴**：异常情况下可能产生大量告警。需要确保告警去重和冷却机制正常工作，避免 AlertManager 被打爆。

3. **向后兼容**：所有改动应保持 API 端点100%不变，只增加内部逻辑和数据。前端页面可以增加内容，但不应破坏现有功能。

4. **测试覆盖**：每个 P0 任务完成后，应运行现有的单元测试（91个），确保没有破坏现有功能。

5. **日志文件 vs EventBus**：log_event 仍然写日志文件（用于持久化和调试），同时发布到 EventBus（用于实时展示和诊断）。两者是互补关系，不是替代关系。
