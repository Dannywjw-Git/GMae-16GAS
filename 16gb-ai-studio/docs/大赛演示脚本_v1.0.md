> **目的**：为 2026 上海开源软件应用创新大赛（智算云赛道）提供标准化演示流程。
> **创建**：2026-09-03 ｜ S6.1 演示流程设计

## 一、演示概述

### 1.1 核心卖点

**GMae（GPU Maestro-显存指挥家）** — 消费级 AI 服务器的显存编排专家。

- **实时掌握**：GPU→容器→模型→任务四层全链路显存状态
- **智能诊断**：故障自动告警 + 根因推断 + 处置建议
- **一键处置**：显存释放、场景切换、模型卸载，闭环管理

### 1.2 演示环境

- **硬件**：16GB 单卡（RTX 4080/类似），32GB 内存
- **系统**：Windows 11 + WSL2 + Docker Desktop
- **服务**：vram-console（8787端口）+ ComfyUI + Ollama + OWUI
- **浏览器**：Chrome/Edge，1920x1080 分辨率

## 二、5分钟完整版演示脚本

### 第一幕：开场展示（0:00 - 0:30，30秒）

**目标**：展示 GMae 的实时监控能力，建立第一印象。

**操作步骤**：
1. 打开浏览器，访问 `http://127.0.0.1:8787`
2. 停留在 **Dashboard（总览）** 页面

**讲解词**：
> "大家好，这是 GMae-显存指挥家，一个面向消费级 AI 服务器的显存编排系统。
>
> 大家现在看到的是总览页面，顶部实时显示 GPU 显存水位、健康度评分、容器和模型状态。
>
> 与传统的 nvidia-smi 不同，GMae 不仅显示总显存，还能穿透到 Windows → WSL2 → Docker → 容器 → 模型，看到每一层的显存占用。"

**画面重点**：
- 顶部显存进度条（实时变化）
- 健康度评分卡片（4维度加权）
- 容器状态卡片（运行中/停止）
- 模型加载状态（已加载/未加载）

---

### 第二幕：故障注入（0:30 - 1:30，1分钟）

**目标**：展示 GMae 的故障检测和告警能力。

**操作步骤**：
1. 打开命令行，运行故障注入脚本：
   ```bash
   python scripts/fault_inject.py --scene vram_exhaustion
   ```
2. 切换回浏览器，观察 **Dashboard** 页面的变化
3. 等待告警出现（约5-10秒）

**讲解词**：
> "现在我们模拟一个典型故障：显存耗尽。
>
> 我运行故障注入脚本，加载一个大模型，让显存迅速接近上限。
>
> 大家看，GMae 在5秒内检测到了显存异常，顶部出现了红色告警横幅。
>
> 告警不是简单的'显存不足'，而是包含了：当前显存使用率、持续时间、受影响的容器和模型、以及建议的处置措施。"

**画面重点**：
- 顶部红色告警横幅（动态出现）
- 显存进度条变红（>85%）
- 健康度评分下降
- 告警中心页面的新告警条目

---

### 第三幕：根因诊断（1:30 - 2:30，1分钟）

**目标**：展示 GMae 的根因推断能力，这是核心差异化卖点。

**操作步骤**：
1. 点击告警横幅中的 **"查看根因分析"** 按钮
2. 进入 **诊断中心** 页面
3. 展示根因候选 Top3 和事件时间线

**讲解词**：
> "传统监控只告诉你'出问题了'，但 GMae 还能告诉你'为什么出问题'。
>
> 点击'查看根因分析'，进入诊断中心。
>
> 大家看，这里显示了根因候选 Top3，每条都有置信度评分和相关事件。
>
> 第一名是'Ollama 模型 qwen3.5:9b 加载导致显存耗尽'，置信度 92%。
>
> 下方是事件时间线，GMae 自动回溯了最近5分钟的事件流，高亮了与故障相关的关键事件：模型加载、显存上升、容器状态变化。
>
> 这是基于规则的推断引擎，不是 AI 黑盒，每条结论都可解释、可追溯。"

**画面重点**：
- 根因候选 Top3 卡片（置信度进度条）
- 事件时间线（彩色标记，相关事件高亮）
- 处置建议列表（可执行的操作按钮）

---

### 第四幕：处置执行（2:30 - 3:30，1分钟）

**目标**：展示 GMae 的一键处置能力，完成闭环。

**操作步骤**：
1. 在诊断中心页面，点击处置建议中的 **"一键释放显存"** 按钮
2. 确认操作（弹出确认框）
3. 观察显存变化（约5-10秒）
4. 展示释放报告：释放了哪些进程，剩余什么进程

**讲解词**：
> "诊断完成后，GMae 不仅告诉你原因，还提供可执行的处置建议。
>
> 这里有三个选项：一键释放显存、切换到游戏场景、卸载指定模型。
>
> 我们选择'一键释放显存'。
>
> 大家看，GMae 自动停止了非关键容器和模型，显存从 92% 降到了 35%。
>
> 释放报告清晰显示：释放了哪些进程（Ollama qwen3.5:9b、ComfyUI 空闲模型），释放了多少显存，以及剩余还在占用显存的进程（系统进程、关键服务）。
>
> 告警自动消除，健康度恢复正常。整个过程不到10秒，无需手动 SSH 到服务器 kill 进程。"

**画面重点**：
- 一键释放按钮（确认对话框）
- 显存进度条从红变绿（动态变化）
- 释放报告（释放的进程列表 + 显存变化）
- 告警自动消除（横幅消失）
- 健康度评分恢复

---

### 第五幕：收尾总结（3:30 - 4:00，30秒）

**目标**：展示更多功能，总结价值，留下深刻印象。

**操作步骤**：
1. 切换到 **拓扑图** 页面
2. 展示四层拓扑：GPU → 容器 → 模型 → 任务
3. 切换到 **告警中心** 页面
4. 展示历史告警和告警统计

**讲解词**：
> "最后，我们看一下 GMae 的另外两个核心功能。
>
> 这是拓扑图页面，展示 GPU → 容器 → 模型 → 任务四层拓扑，每个节点显示显存占用和状态，点击节点可以查看详情。
>
> 这是告警中心，所有历史告警都在这里，可以按级别、时间、状态筛选，支持告警聚合和静默，避免告警风暴。
>
> 总结一下：GMae 不仅是一个显存监控工具，更是一个完整的显存编排系统——实时监控、智能诊断、一键处置，形成闭环。
>
> 对于消费级 AI 服务器用户来说，GMae 让 16GB 显卡也能稳定运行多个 AI 模型，不用再担心显存溢出导致系统死机。
>
> 谢谢大家！"

**画面重点**：
- 拓扑图（四层 SVG 拓扑，节点可点击）
- 告警中心（历史告警列表 + 统计卡片）
- 健康度评分（恢复正常）

## 四、演示准备清单

### 4.1 环境准备

- [ ] vram-console 服务正常运行（8787端口）
- [ ] ComfyUI 容器运行中（8188端口）
- [ ] Ollama 容器运行中（11434端口），已加载 qwen3.5:9b
- [ ] OWUI 容器运行中（3000端口）
- [ ] 显存初始状态：30-50%（留有故障注入空间）
- [ ] 浏览器已打开，清除缓存
- [ ] 屏幕分辨率：1920x1080 或以上
- [ ] 关闭无关程序，避免干扰

### 4.2 数据准备

- [ ] 故障注入脚本已测试通过
- [ ] 历史告警数据（至少5条，不同级别）
- [ ] 事件时间线数据（至少10条事件）
- [ ] 模型加载状态（至少2个模型已加载）
- [ ] 容器状态（至少5个容器运行中）

### 4.3 应急预案

| 风险 | 应对措施 |
|------|---------|
| 故障注入脚本失败 | 手动加载大模型（ollama run qwen3.5:9b） |
| 告警未出现 | 检查 alert_manager 状态，手动触发测试告警 |
| 根因诊断为空 | 检查 diagnose.py 规则引擎，确保事件数据充足 |
| 一键释放失败 | 手动执行释放脚本，展示结果 |
| 服务崩溃 | 快速重启服务（start.bat），展示恢复能力 |
| 网络延迟 | 提前预热，确保缓存命中 |

## 五、演示话术要点

### 5.1 必说要点

1. **"穿透四层"**：Windows → WSL2 → Docker → 容器 → 模型
2. **"5秒检测"**：故障检测延迟 <5秒
3. **"根因 Top3"**：不是单一结论，而是候选排序 + 置信度
4. **"可解释"**：基于规则引擎，不是 AI 黑盒
5. **"一键闭环"**：检测 → 诊断 → 处置，全程 <30秒
6. **"16GB也能跑"**：消费级显卡也能稳定运行多模型

### 5.2 避免说的话

- ❌ "这是 AI 自动诊断"（实际是规则引擎，要诚实）
- ❌ "永远不会死机"（GMae 是降低风险，不是保证）
- ❌ "支持所有模型"（实际是支持主流模型，要留余地）
- ❌ "比 Prometheus/Grafana 好"（不要贬低竞品，强调差异化）
