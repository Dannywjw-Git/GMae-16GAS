#### 1. docker pause/unpause 支持（L2 分级释放基础）
- clients/docker_client.py：新增 pause_container() / unpause_container()

#### 2. auto_protect 逐级升级（L1→L2→L3）
- engine/qos.py：L4 硬释放改造为两级升级
  - L4a：先 docker pause（保留状态，秒级恢复）
  - 验证 3 秒后显存仍 <1G → L4b：docker stop（最后手段）
- 新增内存触发：系统内存 >90% 也触发 critical（内存打满 = docker exec 失效 = 软释放全废）
- 每次只升级一级，避免跳级过度杀伤

#### 3. 场景感知主动调度
- services/scene.py：新增 docker_pause / docker_unpause step handler

#### 4. 内存监控与预警
- services/status.py：新增 _get_system_memory()，/api/status 返回 system 字段
  - {total_mb, used_mb, free_mb, percent}
- auto_protect 内存 >90% 触发 critical
- SSE /api/stream 已包含内存状态

#### 5. 任务提交前预算预检
- api/endpoints/queue.py：POST /api/queue 提交前调用 budget_engine
- 显存不足时返回 budget_warning 字段（不阻止提交，用户可选择排队）
- 提示信息："显存可能不足（需要 X G，当前空闲 Y G），任务可能排队或触发自动释放"

#### 6. 被暂停容器自动恢复
- server.py：新增 paused-recover 后台线程（每60秒检查）
- 显存空闲 >8G 时，按暂停时间顺序自动恢复被暂停的容器
- 每次只恢复一个，避免瞬间占满
- 记录 paused_auto_recover 事件日志

### 设计原则（指挥家气质）
1. **能暂停就不杀死**：docker pause 保留状态，unpause 秒级恢复，用户无感知
2. **逐级升级不跳级**：L1→验证→L2→验证→L3，每级之间有间隔
3. **自动恢复有兜底**：被暂停的容器在资源宽松时自动回来，不用用户手动操作
4. **内存显存双监控**：内存打满和显存打满同样危险，都要触发保护

## 2026-09-01 模块化重构遗留问题排查与修复（看门狗链路 + toast bug）

### 背景
接手时发现：watchdog.log 从 09-01 18:27 起持续 "port open but /api/health failed (half-dead)" 无限循环
（多次触发 10 次/小时暂停），且 vram-console.log 09-01 00:53~01:10 反复出现
`toast_failed: log_event() got multiple values for argument 'event_type'`（标题 "GMae 自动防死机"）。

### 排查结论（根因链）
1. **v2.0 模块化重构（09-01）把 watchdog.py 从根目录迁到 `engine/watchdog.py`，但启动脚本未同步**：
   - 根目录 `watchdog.py` 已删除；`run_watchdog.bat`（第32行）与 `start.bat`（第38行）仍调用根目录 `watchdog.py` → 手动/自启拉起看门狗必然失败
   - 新 `engine/watchdog.py` 自身路径错误：`BASE_DIR` 指向 engine 目录、`SERVER_SCRIPT=engine\server.py`（不存在）、日志写到 `engine\logs\` → 该文件从未被正确运行过
2. **实际在跑的是重构前的残留 watchdog 进程**（根目录版，写 `vram-console\logs\watchdog.log`），它检测到 8787 被残留 server 进程占用但 /api/health 不通过 → 无限重启循环（复现 08-31 P0 事故模式，只是这次是残留进程占端口）
3. **toast bug（重构引入）**：`core/logger.py` 的 `toast_notify()` 内 `log_event("toast_sent", ..., event_type=event_type)` 与签名 `log_event(event_type, **kwargs)` 冲突 → TypeError 被吞 → 所有 toast 记录为 toast_failed（toast 本体已发出，仅日志语义错误）

### 已修复（4 处）
1. `core/logger.py:85` — `event_type=` → `toast_event_type=`（消除参数冲突；全项目 grep 确认仅此一处）
2. `engine/watchdog.py` — `BASE_DIR` 改为 vram-console 根目录（`dirname(dirname(__file__))`），`SERVER_SCRIPT`/`LOG_FILE` 随之正确
3. `run_watchdog.bat:32` — 改调 `engine\watchdog.py`
4. `start.bat:38` — 改调 `engine\watchdog.py`

### 链路确认（修复后）
- 开机自启 `Startup\VRAM_Console.vbs` → `run_watchdog.bat` → `engine\watchdog.py` → `server.py` ✅
- 手动 `start.bat` → `engine\watchdog.py` ✅
- `stop.bat`（按命令行匹配进程）无需改动 ✅
- 第三层自动防死机代码在重构中已完整迁移（`engine/qos.py` 的 qos_check/_auto_protect_run + `services/helper.py` 的 _auto_protect_cfg/_auto_protect_save），本次确认无遗漏 ✅

### 待用户手动操作（本会话沙箱 runner 不可用：WorkBuddy node 22.22.2 正在删除，DSH pwsh 无法启动）
1. 清理残留进程：双击 `stop.bat`（按 vram-console 命令行精确匹配停止旧 watchdog/server）
2. 重启看门狗：双击 `start.bat`（现在会正确启动 engine\watchdog.py）

### 经验教训
- **模块化重构必须同步更新启动/自启脚本**（bat/vbs/计划任务），否则旧入口指向已删除文件，且残留旧进程会无限循环重启
- **watchdog 迁移后路径依赖必须用真实运行验证**（BASE_DIR/SERVER_SCRIPT/LOG_FILE 三件套），本次三处全错

**验证**：修复后 auto_protect 在 834MB 空闲时 **<10s 触发**，执行 L4 停止 ollama 容器，显存 1s 内恢复到 11GB。
