## 控制核心设计

一个资源协调器拥有 GPU 账本；API 只提交意图。任务持久化状态：queued → assessing → reserved → releasing → verifying → running → succeeded/failed/cancelled。每个动作有 job_id、attempt_id、事件序号、单调时钟和适配器结果；释放和取消必须得到反馈。进程重启先对账真实 GPU/服务任务，再恢复队列。

预算统一 MiB：直接峰值 = 实时占用 + 目标增量峰值 + 安全余量；释放后峰值 = 不可回收占用 + 目标峰值 + 安全余量。驻留权重与增量激活应分别校准，不能固定相加也不能将已加载当零成本。预留在同一临界区完成；无法控制外部应用时不能提供绝对 OOM 保证。

What-if 展示参数、profile 版本、直接/串行方案、需要卸载的服务和未验证条件；没有统计校准就不显示成功概率。先做可解释规则与保守区间，再根据留出实验比较误差，决定是否引入学习模型。

## 性能实验协议

基线 A：Ollama/ComfyUI 默认运行；基线 B：相同任务顺序的手动释放/固定 FIFO；实验 C：GMae 统一协调器；消融 D：关闭参数 profile 或释放核验。固定模型、后端、显卡、驱动、工作流和任务输入，不用不同生成质量换取吞吐。

至少选 LLM-only、SDXL-only、LLM→图像→LLM、视频独占、外部占用五类负载。冷/热各跑至少 10 个完整序列，保留失败及重试；样本数、方差和硬件适用范围一并公开。规模不足则展示观察值及范围，不夸大统计显著性。

JSONL 每条记录包含：run_id、job_id、baseline、GPU UUID/容量、OS/驱动/CUDA、后端 commit、镜像 digest、模型 SHA256、完整参数、输入/输出 hash、单调时间、准入理由、采样间隔、显存 used/free、任务结果、OOM、重试和释放结果。开始前清空或记录事件游标；只统计本轮新事件。

指标：完成率、OOM/误拒绝率、端到端 makespan、吞吐、等待 p50/p95、释放确认时延、峰值估计绝对/相对误差、取消与重启恢复时间。总显存、进程显存、allocator reserved/allocated 分别记录，不混称分解准确率。报告 GPU 利用率须定义采样/积分方式及对照，不能仅比较瞬时 nvidia-smi 截图。

## 长期发展与材料策略

贡献边界优先是新增适配器、profile 采集、故障场景、安装验证和界面可解释性。发布路线从单卡可靠生命周期扩展到多卡和远程节点，集群集成作为后续方向。只有已验证的能力进入比赛摘要；待实现项目明确列路线图。创新主张与实验结论应由维护者和一名独立复现者共同核对。
