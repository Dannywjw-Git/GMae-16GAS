## 二、重构目标与范围

### 2.1 核心目标

1. **性能**：/api/status 热路径从 13-17 秒降至 <3 秒
2. **可观测**：从"告警"升级到"告警 + 根因诊断 + 处置闭环"
3. **前端**：全新 WEBUI，信息架构清晰，演示效果好
4. **大赛就绪**：故障注入→告警→根因→处置完整演示闭环

### 2.2 明确不做的边界

- 不集成 ZSvirt 虚拟化平台（GMae 是裸机 Windows + Docker Desktop）
- 不引入虚拟机层和 VM 内探针
- 不全盘转向 OpenTelemetry/Prometheus/Grafana 生态（保持自研轻量）
- 不做 Agent 任务轨迹追踪
- 不改动底层（感知层/账本层/执行层）的核心逻辑，只在其上叠加增强层

### 2.3 重构范围总览

| 阶段 | 名称 | 内容 | 优先级 | 估算 |
|------|------|------|-------|------|
| S0 | 已完成 | 中间层重构 + 前端存档 + watchdog bug 修复 | — | ✅ |
| S1 | 轻量采集优化 | 指标缓存层 + Docker Events + 并行化 + nvidia-smi 缓存 | P0 | 4 人天 |
| S2 | 事件关联引擎 | 事件标准化 + 时间线 API + 根因推断规则引擎（5规则） | P0 | 6 人天 |
| S3 | 故障场景库 + 告警降噪 | 5 故障场景定义 + 处置步骤可执行化 + 4 条新规则 + 注入脚本 + 告警管理器（聚合/静默/升级） | P1 | 5 人天 |

### S1：轻量采集优化（P0，4 人天）

**目标**：/api/status 热路径从 13-17 秒降至 <3 秒

#### S1.1 指标缓存层（核心，1.5 人天）
- 新建 `api/status_cache.py`：`StatusCache` 类，TTL 10 秒
- 缓存键：完整 status 响应 JSON
- 缓存命中直接返回，跳过所有 docker exec
- 缓存失效时后台刷新（不阻塞请求，返回旧数据 + stale 标记）
- 写操作（/api/free、/api/scene、/api/guard/kick 等）后主动失效缓存
- API 响应加 `cached: true` 和 `cached_at` 时间戳

#### S1.2 Docker Events API（1 人天）
- 用 `docker events` 命令的 subprocess 流式读取（Windows 下用 named pipe 或命令行）
- 后台线程维护内存容器状态表（running/stopped/exited）
- /api/status 中容器状态直接读内存表，不再 docker exec ps
- 服务停止时优雅退出后台线程

#### S1.3 并行化 docker exec（0.5 人天）
- 对无法缓存的调用（ollama ps、comfyui 模型状态、容器状态），用 `concurrent.futures.ThreadPoolExecutor` 并行执行
- 串行 3-5 秒 → 并行 1-2 秒

#### S1.4 nvidia-smi 缓存（0.5 人天）
- 新增 5 秒 TTL 缓存（显存变化不需要毫秒级实时）
- 危险状态（danger/critical）时缓存 TTL 缩短为 2 秒

#### S1.5 验证
- 连续调用 /api/status 5 次，第 2-5 次响应 <500ms（缓存命中）
- 调用 /api/free 后立即调用 /api/status，返回最新数据（缓存失效）
- 启动/停止 Docker 容器，/api/status 中容器状态 5 秒内更新
- 现有单元测试全部通过

#### 涉及文件
- 新建：`api/status_cache.py`
- 修改：`api/endpoints/status.py`（集成缓存）、`api/endpoints/vram.py`（写操作失效缓存）、`api/endpoints/scene.py`、`api/endpoints/guard.py`
- 测试：`tests/test_status_cache.py`（新建）

### S2：事件关联引擎（P0，6 人天）

**目标**：告警触发时自动回溯最近 5 分钟事件流，输出根因候选 Top3

#### S2.1 事件标准化 + 时间线 API（2 人天）
- 新建 `engine/event_bus.py`：事件标准化模块
- 统一事件格式：`{timestamp, category, level, source, event, message, metadata}`
- category 枚举：`vram`、`container`、`model`、`task`、`user_action`、`system`、`guard`
- 事件来源：vram-console.log 结构化日志 + Docker events（S1.2）+ 显存状态变化 + 用户操作
- 新建 API：`GET /api/events/timeline`（参数 start_time/end_time/limit/category）
- 新建端点模块：`api/endpoints/events.py`

#### S2.2 根因推断规则引擎（2.5 人天）
- 新建 `engine/diagnose.py`：规则引擎
- if-then 规则（非 ML，保证可解释性），每条规则含：id/name/description/condition/root_cause/confidence/suggested_action/related_events_query
- 初始规则集 5 条：

| 规则 ID | 触发条件 | 根因 | 置信度 | 处置建议 |
|---------|---------|------|-------|---------|
| RC-001 | vram_critical + comfyui running + 最近有 task_submit | ComfyUI 生成任务显存溢出 | 85% | 暂停队列 / 降低分辨率 / 释放 ComfyUI 显存 |
| RC-002 | vram_critical + ollama 加载了 >7B 模型 + 最近有 model_load | 大模型加载导致显存不足 | 80% | 卸载大模型 / 切换到小模型 / 降低 context |
| RC-003 | vram_critical + fooocus running + 最近有 scene_switch | Fooocus 场景切换后显存未释放 | 70% | 重启 Fooocus 容器 / 切换到其他场景 |
| RC-004 | vram_danger + 多个容器同时 running + 无新任务 | 多服务并发占用累积 | 60% | 停止非必要服务 / 切换到独占场景 |
| RC-005 | vram_critical + 桌面进程显存 >2GB + 最近无容器操作 | 桌面应用占用显存 | 75% | 关闭桌面 GPU 应用 / 检查是否误开游戏 |

- 规则匹配算法：拉取时间窗内事件 → 逐条规则检查 condition → 匹配的按 confidence 排序 → 返回 Top3
- 未匹配时返回默认诊断 + 最近 10 条事件
- 新建 API：`POST /api/diagnose`（参数 alert_type/alert_time/window_seconds）

#### S2.3 显存状态变化事件（0.5 人天）
- 在 QoS 状态机中，safe→warning→danger→critical 的状态跃迁时记录事件
- 事件含：旧状态、新状态、当前显存、触发原因

#### S2.4 用户操作事件审计（1 人天）
- 检查所有写操作（场景切换、模型加载、任务提交、门卫驱逐、释放显存），确保都有 log_info 记录
- 遗漏的补上，事件格式统一

#### S2.5 验证
- 模拟显存 critical 状态，调用 /api/diagnose 返回 Top3 根因候选
- 每条规则用构造事件测试（正例 + 反例）
- /api/events/timeline 返回最近事件，格式统一，category 正确
- 规则引擎单元测试：5 条规则各至少 1 正例 + 1 反例
- 现有测试全部通过

#### 涉及文件
- 新建：`engine/event_bus.py`、`engine/diagnose.py`、`api/endpoints/events.py`、`api/endpoints/diagnose.py`、`tests/test_diagnose.py`、`tests/test_event_bus.py`
- 修改：`engine/qos.py`（状态变化事件）、各写操作端点（补日志）

### S3：故障场景库 + 告警降噪（P1，5 人天）

**目标**：5 个标准化故障场景 + 告警聚合/静默/升级

#### S3.1 故障场景定义文档（1 人天）
- 新建 `docs/故障场景库.md`，定义 5 个场景：

| 场景 ID | 名称 | 检测规则 | 告警级别 | 对应根因规则 |
|---------|------|---------|---------|------------|
| FC-001 | 显存耗尽/OOM 风险 | free_vram < 1GB 持续 10 秒 | critical | RC-001/002/003/005 |
| FC-002 | 容器异常退出/频繁重启 | Docker die 事件 + 5 分钟内重启 ≥3 次 | warning | RC-006（新增） |
| FC-003 | 推理延迟升高 | 模型推理 P95 响应时间 > 阈值持续 3 次 | warning | RC-007（新增） |
| FC-004 | 任务队列堆积 | ComfyUI 队列 pending >5 持续 30 秒 | info | RC-008（新增） |
| FC-005 | 服务不可达 | health check 连续 3 次失败 | danger | RC-009（新增） |

- 每个场景含：触发条件、告警模板、处置步骤（可执行 API/CLI）、验证方法、预防建议

#### S3.2 处置步骤可执行化（0.5 人天）
- 每个场景的处置步骤是具体 API 调用或 CLI 命令，不是文字描述
- 示例（FC-001）：①`gmae vram free --dry-run` 预览 ②`POST /api/free` 释放 ③`POST /api/queue/pause` 暂停队列 ④`POST /api/scene {scene:"idle"}` ⑤`GET /api/status` 验证

#### S3.3 根因规则扩展（0.5 人天）
- 在 S2 的规则引擎基础上，新增 RC-006~009 对应 FC-002~005
- 规则定义格式与 S2 一致

#### S3.4 故障注入演示脚本（1 人天）
- 新建 `scripts/fault_injection/` 目录，5 个注入脚本：
  - `inject_vram_pressure.py`：加载大模型 + 提交高分辨率生成任务
  - `inject_container_crash.py`：docker kill 容器模拟异常退出
  - `inject_latency.py`：提交超大 context 推理任务
  - `inject_queue_backlog.py`：批量提交 10 个生成任务
  - `inject_service_down.py`：停止 Ollama 容器
- 每个脚本含：注入操作、等待时间、恢复操作、预期告警、dry-run 模式、确认提示

#### S3.5 告警管理器（2 人天）
- 新建 `engine/alert_manager.py`：`AlertManager` 类
- 核心数据结构：
  - `active_alerts`：当前活跃告警字典，key = alert_type
  - `silenced_alerts`：静默中的告警，key = alert_type，value = 静默截止时间（持久化到 `alerts_silenced.json`）
  - `alert_history`：告警历史（最近 100 条，含聚合计数）
- 告警提交流程：
  1. 检查是否在静默期 → 是则丢弃
  2. 检查是否已有同类型活跃告警 → 是则聚合（count+1，不重复推送）
  3. 否则新建告警，推送到前端
- 升级机制：告警持续超过 10 分钟未解决，自动升级 level（info→warning→danger→critical），最高到 critical
- 新建 API：
  - `GET /api/alerts`：活跃告警列表（含聚合计数、首次触发时间、持续时长）
  - `POST /api/alerts/{alert_type}/silence`：静默告警（参数 duration_minutes，默认 30）
  - `GET /api/alerts/history`：告警历史
- 新建端点模块：`api/endpoints/alerts.py`

#### S3.6 验证
- 5 个场景文档完整，每个含触发条件/告警模板/处置步骤/验证方法/预防建议
- 4 条新规则单元测试通过

- 调用静默 API 后同类型告警不再推送，30 分钟后自动恢复
- 告警持续 10 分钟未解决，level 自动升级
- 单元测试：聚合、静默、升级、过期恢复各 1 个测试

- 新建：`docs/故障场景库.md`、`engine/alert_manager.py`、`api/endpoints/alerts.py`、`scripts/fault_injection/*.py`、`tests/test_alert_manager.py`

## 六、风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| /api/status 缓存导致数据不一致 | 用户看到旧数据 | 中 | API 响应加 cached/cached_at 标记；写操作后主动失效；前端显示"数据更新于 X 秒前" |
| Docker events 在 Windows 下不稳定 | 容器状态不实时 | 中 | 降级方案：events 失败时回退到 docker exec ps（缓存 5 秒） |
| 规则引擎规则覆盖不全 | 根因诊断不准 | 高 | 初始 5+4 规则覆盖常见场景；未匹配时返回默认诊断 + 事件时间线；文档说明"基于规则的推断，非 AI 分析" |
| 故障注入脚本误操作 | 影响生产环境 | 中 | 脚本开头加确认提示 + dry-run 模式；脚本名和目录明确标注"仅用于演示和测试"；执行前检查显存状态，空闲 <4GB 时拒绝高显存压力注入 |
| 前端重做工作量超预期 | 工期延误 | 高 | P0 页面优先（Dashboard/诊断/告警），P2 页面简化或延后；沿用 v2 的功能逻辑，只重写 UI；必要时 S5 跳过 |
| 大赛时间紧 | 材料准备不足 | 中 | S6 演示整合提前准备脚本；核心演示流程（故障注入→告警→根因→处置）在 S3 完成后即可预演 |
| 告警管理器状态丢失 | server 重启后告警/静默失效 | 低 | 活跃告警内存存储（可接受，告警是实时的）；静默期持久化到 alerts_silenced.json |
