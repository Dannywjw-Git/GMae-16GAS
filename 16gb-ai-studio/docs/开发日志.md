## 2026-08-26 上午 ollama 容器化（波折重重）

### 背景
ollama 原本装在 Windows 宿主机，为了统一 Docker 管理和便于迁移，决定容器化。

### 遇到的问题与解决方案

**问题 1：Docker Hub 拉取极慢**
- 直连 Docker Hub 拉 ollama/ollama:latest（7.2GB），速度几十 KB/s，频繁断开
- 尝试阿里云镜像：`registry.cn-hangzhou.aliyuncs.com/ollama/ollama`，该仓库不存在
- 尝试 exit node（东京~~新加坡~~）：速度有提升但仍不稳定（新加坡已于 2026-08-26 下线）

**问题 2：aria2 多线程下载大文件内容损坏**
- 在东京 VPS 用 docker pull → docker save → tar → aria2 多线程下载
- aria2 `-x16 -s16` 下载的文件大小正确但缺少 manifest.json，docker load 失败
- **结论**：aria2 多线程单文件下载大文件不可靠，改用分割文件法

**问题 3：最终方案——分割文件 + 批量下载**
- 东京 VPS：docker pull → docker save → `split -b 100M` 分割成 33 个
- 本机：aria2 批量下载（每文件单线程 `-x1 -s1`，并发 `-j4`）
- 不完整文件用 PowerShell HttpWebRequest 带 Range 断点续传循环重试
- `copy /b` 合并 → `tar -tf` 验证 manifest.json → docker load 成功

**问题 4：新加坡 VPS 配置**（⚠️ 该 VPS 已于 2026-08-26 下线，以下为历史记录）
- ~~新部署新加坡 VPS（149.28.134.107，Ubuntu 24.04）~~
- ~~接入 Tailscale（100.103.131.14，ai-exit-sg）~~
- ~~配置为 exit node，延迟 ~71ms（P2P），比东京快 3-4 倍~~

### 完成工作
- ollama 容器化成功，7 个模型全部继承，GPU 加速正常
- 容器配置：`docker run -d --name ollama --restart unless-stopped -p 11434:11434 --gpus all -v D:\ollama\models:/root/.ollama/models ollama/ollama:latest`
- 镜像备份：`_installers/ollama.tar`（7.2GB），新机器部署可直接 docker load
- 验证：qwen3.5:9b 推理 44 token/s（ComfyUI 停止后）

### 关键决策
- 大文件下载采用 VPS 中转 + 分割文件 + 单线程批量下载方案，放弃 aria2 多线程
- ~~新增 exit node 作为主要下载通道，东京作为备用~~（新加坡已于 2026-08-26 下线，当前唯一 exit node 为东京）

### 经验教训
- aria2 多线程下载大文件（>1GB）可能内容损坏，大小正确不代表内容正确
- Docker 镜像备份成 tar 是新机器部署的最快方式，避免重复拉取
- ~~exit node 节点选择很重要，新加坡比东京快 3-4 倍~~（新加坡已于 2026-08-26 下线）

## 2026-08-26 晚上 P0 稳定性实施（日志 + 看门狗 + 健康检查）

### 背景
调度中心进程反复崩溃，pythonw 无窗口模式出错看不到原因，服务不可用。

### 完成工作

**P0-1 结构化日志系统**
- server.py 添加 logging 模块，TimedRotatingFileHandler 按天轮转，保留 30 天
- 日志格式：`时间 | 级别 | JSON事件`，JSON 包含 ts/event/具体字段
- 关键事件日志：server_start、server_crash、scene_switch_start/done、vram_pre_release、security_warning
- 日志文件：`vram-console/logs/vram-console.log`

**P0-2 看门狗自动重启**
- 创建 watchdog.py，用 subprocess.Popen 监控 server.py
- server 退出后 5 秒自动重启，1 小时内最多重启 10 次（防死循环）
- 看门狗日志：`logs/watchdog.log`，记录启动/退出/重启事件
- 验证：杀掉 server 进程后，5 秒自动重启成功

**P0-3 健康检查 API**
- 新增 `GET /api/health` 端点（无需认证，方便外部监控）
- 检查项：GPU 状态、Ollama 连通性（11434）、ComfyUI 连通性（8188）、显存阈值警告
- 返回整体 ok 状态和各服务详情

### 踩坑记录

**坑 1：pythonw 启动 watchdog 不稳定**
- 用 pythonw.exe 启动 watchdog.py，进程会莫名消失
- 改用 python.exe 启动正常，VBS 隐藏窗口
- **教训**：pythonw 适合 GUI 程序，不适合需要 subprocess 的后台服务

**坑 2：bat 循环看门狗不可靠**
- 最初用 watchdog.bat 循环启动 python，cmd 进程会莫名退出
- 改用 Python watchdog.py + Popen 稳定可靠

**坑 3：跨 Bash 调用进程树被清理**
- 在一个 Bash 命令启动 watchdog，另一个 Bash 命令杀 server，watchdog 也消失
- 在同一个 Bash 命令里完成完整测试，自动重启正常
- **教训**：测试后台进程时，启动和验证尽量在同一会话完成

**坑 4：subprocess.run vs Popen**
- 最初用 subprocess.run 等待子进程，可能因输出管道阻塞导致问题
- 改用 Popen + poll() 循环，stdout/stderr 重定向到 DEVNULL，稳定可靠

### 当前状态
- 服务通过 watchdog.py 托管，崩溃自动重启
- 所有操作有结构化日志，出问题可追溯
- /api/health 可用于外部监控

## 2026-08-26 晚上 启动脚本修复（WindowsApps python 存根）

## 2026-08-26 晚上 health 检查修复（import 缺失 + 容器停止）

### 问题
调度中心页面持续显示 "红色 Ollama 无响应（假死特征）"，health 检查 ollama/comfyui 均为 false。

### 根因（两个独立问题）
1. **server.py 顶部缺少 `import urllib.request`**：health_check() 中使用 `urllib.request.Request` 触发 NameError，被 `except Exception` 静默捕获，永远返回 false。而 load_model_api() 等函数在局部有 `import urllib.request`，所以那些功能正常，只有 health_check 受影响。
2. **ComfyUI 容器已停止**：状态 Exited (143)，被 SIGTERM 杀掉，重启系统后未自动启动。

### 修复
1. server.py 顶部添加 `import urllib.request`
2. `docker start comfyui` 启动容器
3. 前端假死警告提示改为容器化版（`docker restart ollama`）

### 教训
- `except Exception` 会吞掉 NameError 等编程错误，健康检查类函数应单独测试
- 重启系统后必须检查所有容器是否自动启动（`docker ps -a`）
- Python 标准库导入必须在顶部统一管理，避免局部导入导致部分函数可用部分不可用

## 2026-08-26 晚上 重大架构问题：宿主机 Ollama 与 Docker Ollama 并存

### 问题现象
调度中心显示显存 15.4G 超警戒，当前场景 ComfyUI，但 Ollama 的 qwen3.5:9b（8.9G）和 qwen3:0.6b（1.0G）还在显存中。切换场景时 gpu_release.ps1 调用 `ollama stop` 无效。

### 根因（重大发现）
**宿主机安装了 Ollama Windows 版，且开机自启（`D:\scripts\start_ollama_serve.cmd`），与 Docker 容器里的 Ollama 并存。**

- 宿主机 Ollama 抢占 11434 端口，Docker Ollama 的端口映射失效
- 调度中心访问 `127.0.0.1:11434` 实际访问的是宿主机 Ollama
- `docker exec ollama ollama stop` 停止的是 Docker 容器里的 Ollama（空模型），所以显存不释放
- gpu_release.ps1 用宿主机 `ollama stop` 命令，但 Ollama 容器化后宿主机 CLI 可能已失效
- 两个 llama-server.exe 进程（PID 3060, 5984）占用了约 8G 显存

### 修复
1. **停止宿主机 Ollama 进程**：`Stop-Process ollama*, llama-server*`
2. **禁用宿主机 Ollama 开机自启**：移除注册表 `HKCU\...\Run\OllamaServe`
3. **重启 Docker Ollama**：重新绑定 11434 端口
4. **修复 gpu_release.ps1**：改为用 `docker exec ollama ollama stop`，从 registry.json 读取模型列表
5. **修复 scene_switch**：在 comfy/h3/music/fooocus 场景开头显式调用 `ollama_stop_all()`

### 验证
- 显存从 13.7G 降到 5.9G（释放约 8G）
- Docker Ollama 7个模型全部正常，端口 0.0.0.0:11434 监听
- 宿主机 Ollama 开机自启已禁用，重启后不会再冲突

### 教训
- **容器化后必须彻底禁用宿主机版本**，包括进程、服务、开机自启
- `docker exec` 只影响容器内，不影响宿主机进程
- 端口冲突时 Docker 端口映射会静默失败，docker ps 显示 `11434/tcp` 而非 `0.0.0.0:11434->11434/tcp`
- 显存异常时先查 `nvidia-smi --query-compute-apps` 查实际占用进程，不要假设是容器内的

## 2026-08-27 凌晨 Docker 磁盘空间清理与迁移（紧急）

### 问题
C 盘仅剩 7GB，系统告警。

### 根因分析
1. **Docker 镜像 211GB**：comfyui-h3 的 v1-v4 四个版本，每个 ~48GB（共 193GB）；多个重复镜像（OWUI 3个、fooocus 2个、ComfyUI 2个）；未使用的 dify 相关镜像
2. **WSL2 vhdx 不收缩**：删除镜像后，`docker_data.vhdx` 仍为 226GB，diskpart compact 无效
3. **本地 Ollama 模型 1.46GB**：已容器化但本地模型未删除

### 清理步骤
1. 删除 comfyui-h3:v1/v2/v3（保留 v4）
2. 删除重复镜像（旧 registry 的 OWUI/fooocus/ComfyUI）
3. 删除未使用的 dify/nginx/postgres/qdrant 镜像
4. docker container prune + image prune
5. Docker 镜像从 211GB 降到 41GB

### 迁移到 D 盘（符号链接方案）
- WSL 导出发行版只有 60MB（数据不在发行版，在 docker_data.vhdx）
- diskpart compact vhdx 无效（WSL2 格式特殊）
- **最终方案**：停止 Docker → wsl --shutdown → 移动 docker_data.vhdx 到 D:\DockerData\wsl\disk\ → 在原位置创建 junction 符号链接 → 再启动 Docker
- Docker 无感知，所有容器自动启动，服务正常

### 结果
- C 盘：7GB → **244.5GB**（回收 237GB）
- D 盘：减少 226GB
- Docker 数据位置：`D:\DockerData\wsl\disk\docker_data.vhdx`（通过 junction 链接）
- 所有 9 个容器自动启动，ComfyUI/Ollama/OWUI 正常

### 踩坑记录

**坑 1：WSL2 vhdx 删除文件后不自动收缩**
- docker system df 显示 41GB，但 vhdx 文件仍是 226GB
- diskpart compact vdisk 对 WSL2 的 vhdx 无效
- **教训**：WSL2 虚拟磁盘需要特殊处理，常规压缩工具无效

**坑 2：docker commit 产生大量镜像**
- 每次 docker commit comfyui 都创建一个新镜像（~48GB），v1-v4 共 193GB
- 镜像分层共享基础层，但每次 commit 的可写层差异仍占大量空间
- **教训**：docker commit 后及时删除旧版本，或用 Dockerfile 重建镜像

**坑 3：Docker Desktop 数据不在 WSL 发行版中**
- `wsl --export docker-desktop` 只有 60MB
- 数据在 Docker Desktop 管理的 `docker_data.vhdx` 中，不是标准 WSL 数据
- **教训**：迁移 Docker 数据要操作 vhdx 文件，不是 WSL 发行版

**坑 4：符号链接（junction）对 Docker 透明**
- `mklink /J` 创建的目录联接对 WSL2 和 Docker 完全透明
- Docker 启动时通过 junction 访问 D 盘的 vhdx，无需修改配置
- **经验**：junction 是迁移 Windows 应用数据的简单有效方式

### 长期建议
- 定期 `docker system prune` 清理悬空镜像
- docker commit 后立即删除旧版本
- 大文件/数据目录优先放 D 盘，用 junction 链接
- 监控 C 盘空间，低于 50GB 时告警

## 2026-08-27 Wan2.2-TI2V-5B 文生视频（I2V）实战

### 背景
- H3 52GB OOM 不可行后，换 Wan2.2-TI2V-5B（9.3GB FP16）
- 关键坑：5B TI2V 必须用 wan2.2_vae.safetensors（48通道），不能用 wan_2.1_vae（16通道）

### 产出
| 素材 | 结果 | 评分 | 状态 |
|------|------|------|------|
| 海边白裙（v2） | 720x480→超分1440x960 | 60分→清晰度提升 | ✅ 定稿 |
| 赛博朋克上海（第1稿） | 文字不可读/车辆乱/光影闪 | ❌ 失败 | 弃 |
| 机器人（v3） | 720x480, 65帧@16fps=4s | 70分（动作偏弱） | ✅ 先这样 |

### 关键经验（I2V 提示词）
1. **禁止 flicker 字眼**：提示词写 "billboards flicker" 会诱导灯光不稳定闪烁。改 "steady glow / stable lighting"
2. **动作要明确动词+幅度**：写 "slowly raises its head upward" 而不是 "gently tilts / subtle motion / extremely slowly"——Wan2.2 对弱化词会直接不动
3. **脉动要写周期**："pulses bright and dim in a breathing cycle"，"soft pulsing" 太弱不生效
4. **首帧越"干净"越稳**：无车辆、无文字招牌、无正脸（远景背影可）→ 避免车辆乱动/文字乱码/脸部漂移
5. **负面要带**：gibberish text, unreadable signage, flickering lights, morphing, deformed limbs
6. **帧数显存账**：65帧@720x480 峰值~10.9GB；120帧 attention≈65帧的3.4倍必OOM。24fps下65帧=2.7s，16fps=4s

### 显存冲突事故（重要）
- 调度中心切到 fooocus 场景后 Fooocus 驻留~4GB 显存；同时直接调 ComfyUI API 跑 I2V（11GB），叠加后 15GB/16.4GB，只剩 1GB 接近死机
- 教训：**直接用 ComfyUI API 跑任务前，必须确认调度中心当前场景不驻留其他 GPU 服务**。必要时先 docker stop 冲突容器
- 处理：docker stop fooocus 释放显存，保住 I2V 任务

### 交付规格
- 视频超分链路：ComfyUI LoadVideo→RealESRGAN_x4plus→bicubic 1440x960→CreateVideo 16fps
- 输出目录：/output/（容器内），同步到项目 outputs/ 目录

### 🔧 方案 A Helper 性能计数器踩坑与修复（2026-08-28）
- **多实例计数器必须用通配语法**：Get-Counter '\GPU Process Memory\Dedicated Usage'（无通配）返回空；必须 '\GPU Process Memory(*)\Dedicated Usage'。
- **实例名格式**：多 GPU 引擎下是 pid_<pid>_luid_..._phys_...（不是 进程名#pid），需正则提取 pid + Get-Process 映射进程名。

### 🚀 2026-08-30 性能优化 + 演示子项目立项 + 标语更新

#### 1. /api/status 性能优化（并行化 + 缓存）
- **问题**：/api/status 串行执行 10 个外部调用（nvidia-smi/docker exec/HTTP），响应 13-17 秒，前端 3 秒轮询卡死
- **根因**：① current_status() 串行调用 ② 50+ 个孤儿 server 进程堆积（每次重启未杀旧进程）③ ComfyUI WebSocket 疯狂重连（每秒几十次报错，无退避）
- **方案**：
  - 并行化：ThreadPoolExecutor 并行执行 10 个独立调用，总时间从求和变取最大值
  - 缓存：2.5 秒 TTL 内存缓存，前端轮询时大多数请求即时返回
  - POST 操作前失效缓存（invalidate_status_cache），确保用户操作后看到最新数据
  - WebSocket 指数退避：5s→10s→20s→30s 封顶，连接成功后重置

## 2026-08-29 显存账本 6 项改进（基于 ollama 大规模测试观察）

### 背景
另一个会话大规模测试 ollama 模型（6 个模型，9 次加载，含 12B Q8/Q4KM、0.8B 256K context、多模型并发），从 GMae 视角观察发现 6 个需要改进的问题。详见 `观察报告_ollama大规模模型测试_20260829.md`。

### 完成工作（6 项改进全部后端实现）

#### P0-1 显存账本双源化
- **问题**：`ollama ps` 有 15 秒延迟——模型加载中显存已飙升到 12.9GB，但 ps 还显示 0 模型。只依赖 ps 会在 15 秒窗口内误判，允许其他模型加载导致 OOM。
- **实现**：`/api/status` 新增 `vram_ledger` 字段，双源对比 nvidia-smi（权威总量）与 ollama/comfy 明细。差异 >1GB 标记 `loading`，差异 <-1GB 标记 `releasing`，否则 `consistent`。
- **字段**：state / note / actual_used_mb / expected_used_mb / diff_mb / noise_mb / ollama_loaded_mb / ollama_model_count / comfy_loaded_mb。

#### P0-2 模型登记台支持 context 维度
- **问题**：同一模型不同 context 显存差异巨大——qwen3.5:0.8b 从 256K（5.5GB）降到 64K（2.2GB），显存减少 60%。当前登记台只记模型名，不记 context，预算计算严重偏差。
- **实现**：
  - REGISTRY 模型结构新增 `context_vram` 字段（{context_size: vram_gb} 映射）
  - `budget_engine(context_overrides)` 支持用户指定 context，优先从 context_vram 查找对应显存
  - `/api/budget?context=model_id:ctx_size,model2:ctx2` 支持 query string 传参
  - 返回字段新增 context_vram / default_ctx / specified_ctx / note（含 context 标注）

#### P0-3 自动扫描器持续运行（事件驱动+定时兜底）
- **问题**：本次测试 6 个模型中 5 个是新模型（gemma-4-12b q8/q4km、minicpm5-1b/fable5），都不在登记台中。用户会持续下载新模型，扫描器必须实时发现。
- **实现**：
  - 新增 `start_auto_scanner()` 后台线程（daemon，60 秒轮询）
  - 事件驱动：每 60 秒对比 `ollama_tags()` 与基线，发现新模型自动调用 `_auto_register_ollama_model()` 登记
  - 定时兜底：每 5 分钟触发一次完整 `model_scan()`，发现 ComfyUI 新模型文件
  - 自动登记的模型标记 `auto_registered: true` + `vram_verified: false`，显存用 `_estimate_ollama_vram()` 估算（参数×量化系数+1GB 开销）
  - server 启动日志确认：`auto_scanner_start, baseline_models=13`，`auto_scan_full, new_found=5`

#### P1-4 预算引擎支持多模型并发
- **问题**：测试中出现 2 模型并发（minicpm5-1b 4.5GB + qwen3.5:0.8b 5.5GB = 10.7GB）。预算引擎必须支持并发场景的总显存计算。
- **实现**：
  - `budget_engine` 已返回 `loaded_models` 列表（当前加载的所有模型，按显存排序），前端可显示释放清单
  - 预算计算逻辑已考虑当前已加载模型总显存（通过 releasable_mb / safe_ceiling_mb 关系）
  - 用户可选择释放哪些已加载模型来腾空间

#### P1-5 QoS 引擎参考 GPU 利用率
- **问题**：当前 QoS 只看显存水位。但测试发现：gemma-4-12b q8 推理时利用率仅 13%（内存带宽瓶颈），q4km 量化后飙升到 97%。同样的显存水位，不同利用率的调度策略应该不同。
- **实现**：
  - `gpu_status()` 已返回 `utilization` 字段（nvidia-smi utilization.gpu）
  - `qos_check()` 改为双维度判定：基础水位按显存，利用率修正：
    - RED 但利用率 <30%（大模型空闲）→ 降级为 YELLOW
    - YELLOW 但利用率 >90%（计算密集）→ 升级为 RED
    - YELLOW 但利用率 <20%（空闲）→ 降级为 GREEN
  - 返回字段新增 base_level / utilization / adjust_note

#### P2-6 模型加载/释放进度显示
- **问题**：在 ollama ps 延迟的 15 秒窗口内，用户看不到任何反馈，不知道模型正在加载。
- **实现**：
  - `vram_ledger` 中新增 `loading_progress` / `releasing_progress` 字段
  - loading 状态：已占用显存（diff_mb）、估算总大小、进度百分比、预计剩余时间（500MB/秒估算）、提示消息
  - releasing 状态：待释放显存、预计剩余时间（1GB/秒估算）、提示消息
  - 前端可根据这些字段显示进度条或提示

## 2026-08-29 深夜：QoS 自动切换严重 bug 修复

### 问题
主公反馈：当另一个会话测试 LLM 时，显存快满（RED 水位）时，GMae 会自动把 qwen3:0.6b 拉起来，干扰测试。

### 根因
`qos_enforce()` 函数（server.py 原 1450-1459 行）设计了自动模型切换逻辑：
- RED 水位时：自动调用 `combo_switch("0.6b")`，把当前对话模型切换为 qwen3:0.6b
- GREEN 水位时：自动调用 `combo_switch("9b")`，恢复为 qwen3.5:9b
- 冷却防抖：降级 30s / 恢复 60s

### 危害
1. **干扰用户主动测试**：用户在测试大模型时，显存一到 RED 就被自动切走，测试被打断
2. **可能加剧 OOM**：如果大模型未完全释放就加载 0.6b，显存可能进一步飙升
3. **自动恢复振荡**：GREEN 后自动恢复 9b → 再次 RED → 再次降级，来回振荡
4. **只针对对话模型**：`_dialogue_model()` 只取第一个模型，多模型并发时逻辑混乱

### 修复方案（方案 A，主公确认）
完全移除自动切换逻辑，QoS 只做监控+告警：
- RED 水位：设置告警 msg（"建议手动释放模型或切换轻量模型（QoS 不自动切换）"），记录 `qos_alert` 日志
- GREEN 水位：清除告警，记录 `qos_alert_clear` 日志
- 模型切换：完全由用户手动触发（前端按钮 / API 调用）

### 技术决策
调度中心是**管理工具不是自动代理**，激进的自动操作（切换模型、释放显存）应该由用户确认后执行。QoS 引擎的定位是"监控+告警+建议"，不是"自动执行"。

### 修改文件
- `vram-console/server.py`：qos_enforce() 函数重写，移除 combo_switch 调用

### 验证
- 语法检查通过
- server 重启成功，health 正常
- 代码中已无 `combo_switch("0.6b")` 和 `qos_degrade` 调用
- QoS 状态正常：level=green, degraded=False, msg 为空

## 2026-08-31 P0 事故：watchdog 疯狂重启堆积 194 个 server 进程（已修复）

### 事故发现
接手时 `netstat` 显示 8787 端口有 **200+ 个 LISTENING 进程**，核查确认 194 个 server.py 进程 +
1 个 watchdog，每约 100 秒新增一个（0:47 → 7:49 持续 7 小时），共消耗约 7GB 内存。

### 根因链（两层）
1. **watchdog `_health_ok()` 误判**：要求 `/api/health` 返回 `ok is True`。但 health 的 ok 字段
   反映的是下游服务（ollama/comfyui 等）连通状态，不是 server 本身存活。当 ollama/comfyui
   容器未运行时（正常情况），ok=false → watchdog 误判 server "半死" → 反复重启。
2. **health 探测超时过短**：health_check() 对未运行容器的端口做 HTTP 探测，Docker 端口代理
   监听但无后端服务时连接挂起，每次等待数秒；watchdog 的 `timeout=3s` 必然超时返回 False，
   更加剧误判。
3. **server.py 无防多实例**：ThreadingHTTPServer `allow_reuse_address=1` 在 Windows 下允许
   多进程重复 bind 8787 → 旧进程永不退出、新进程不断叠加。

### 修复（3 处）
1. `watchdog.py _health_ok()`：存活标准从 `ok is True` 改为仅校验 HTTP 200 + 返回结构包含
   `services`（说明 health_check 正常执行）。ok=false 不代表 server 死了。
2. `watchdog.py` health 探测 timeout：3s → 15s（匹配 health 对未运行容器端口的实际等待时间）。
3. `server.py __main__`：启动前探测 127.0.0.1:PORT，已被占用则记录
   `server_start_blocked / port_already_in_use` 并 `SystemExit(0)`，杜绝多实例堆积。

- 清理 194 个残留 server + watchdog，重启单个 server，health 正常返回
- 手动再启动第二个实例 → 检测端口占用自动退出（退出码 0，进程数保持 1）
- 重启修复后 watchdog → 日志显示 "Port :8787 up, monitoring only"，70 秒观察期
  server 进程数稳定为 1，不再重启

### 经验教训（P0）
- **health 的 ok 字段是"下游服务"健康，不是"服务本身"健康**。看门狗存活判断绝不能
  依赖下游服务状态，否则下游一停就会误杀重启主服务。
- **Windows 下 SO_REUSEADDR 允许多进程重复 bind 同一端口**，服务端必须自带"端口占用
  即退出"的防多实例保护，否则任何误触发重启都会堆积成灾。
- **网络探测 timeout 必须匹配真实响应时间**：对"端口代理在监听但无后端"的场景，
  HTTP 探测会挂起至 timeout，timeout 设太短会制造大量误判。
- 排查这类问题用 `Get-CimInstance Win32_Process -Filter "Name='python.exe'"` 按命令行
  精确过滤（PowerShell 的 Get-Process 无 CommandLine 属性，抓不到）。
