## 二、架构评估（亮点）

### 2.1 模块化拆分合理

```
web/
├── index.html              # 入口HTML（侧边栏+顶栏静态结构）
├── login.html              # 登录页
├── js/
│   ├── app.js              # 应用入口（192行，仅做初始化和路由注册）
│   ├── topology.js         # 拓扑图页（独立模块，未在导航中）
│   ├── core/
│   │   ├── api.js          # 统一API层（封装所有后端调用+错误处理）
│   │   ├── state.js        # 全局状态管理（含vramHistory趋势数据）
│   │   ├── router.js       # Hash路由（10个页面）
│   │   ├── utils.js        # 工具函数（格式化/DOM/防抖）
│   │   └── eventbus.js     # 前端事件总线
│   ├── components/
│   │   ├── toast.js        # 通知组件
│   │   ├── modal.js        # 弹窗组件（含confirm）
│   │   └── icons.js        # SVG图标库
│   └── pages/
│       └── pages.js        # 9个页面渲染逻辑（1846行，唯一问题点）
└── css/
    ├── main.css            # 主样式（1967行，设计令牌+组件样式）
    └── login.css           # 登录页样式
```

### 2.2 值得肯定的设计决策

1. **统一显存账本**：`_calcVramSegments()` + `_getVramBreakdown()` 是全系统唯一的显存分类计算函数，所有页面（总览/显存账本/释放结果）都调用它，**彻底解决了之前各页面数据不一致的问题**。这是前端架构中最有价值的设计。

2. **纯SVG图表**：显存趋势图用原生SVG实现，无第三方依赖，包含：
   - 动态Y轴刻度（整齐刻度0/2G/4G...）
   - 安全阈值线（14GB红色虚线+警告区域）
   - 峰值/谷值自动标注
   - 平均线
   - 鼠标悬停十字线+tooltip
   - 渐变面积图
   - 这在无构建工具的纯前端项目中属于高质量实现。

3. **事件中文翻译层**：`_eventDescriptions` 字典将40种技术事件（如"comfy ws connected"、"vram auto cleanup"）翻译成用户易懂的中文说明，降低了用户理解门槛。

4. **统一API层**：`API.request()` 统一处理鉴权token、错误解析、loading状态，各页面调用简洁。

5. **状态缓存策略**：`State.get('status')` 优先用缓存，避免多次请求；关键操作后主动 `State.set('status', null)` 强制刷新。

6. **CSS设计令牌**：`variables.css` 定义了完整的颜色/间距/圆角/阴影系统，BEM命名规范，暗色主题统一。

### 3.2 严重功能缺口详情

#### 🔴 P0：设置页全假（最严重）

`settings()` 函数的7个配置分区（系统/服务/QoS/自动防死机/账号/看门狗/关于）**全部是硬编码静态HTML**：

- 服务端口"8787"、监听地址"0.0.0.0"是写死的
- 服务管理表格5个服务状态永远"在线"，重启/停止按钮无事件
- QoS阈值"8GB/4GB/2GB"写死，保存按钮无onclick
- 自动防死机开关是纯div（`<div class="toggle"></div>`），不可点击
- 看门狗"PID 12345 · 运行2小时30分"是假数据
- 账号管理表单无提交逻辑

**影响**：用户无法通过UI修改任何配置，所有设置项都是摆设。后端已有 `/api/qos/config`、`/api/auto-protect/config`、`/api/auth/change-password` 等接口，但前端完全没对接。

#### 🔴 P0：任务队列半成品

- "✅ 显存充足"徽章是硬编码的，**没有调用 `/api/admission` 做预算预检**
- 模型下拉框硬编码4个选项（flux_q5/wan2_2/sdxl/music3），没有从 `/api/registry` 动态获取
- 任务提交后进度条不更新（没有轮询 `/api/queue` 或WebSocket）
- "清空已完成"按钮无onclick
- "查看"按钮无onclick
- 队列状态统计（运行中/等待中/已完成）只在页面加载时计算一次

#### 🟡 P1：场景切换无进度反馈

- 6个场景（对话态/生成态/视频态/音乐态/空闲态/独占态）是前端硬编码的，**没有从 `/api/scene` 获取真实场景配置**
- 点击切换后同步等待API返回（可能10-60秒），期间无loading、无步骤提示、无进度条
- 用户只能看到按钮变成"当前场景"，不知道切换过程中发生了什么
- 后端 `scene_switch()` 有7个步骤（停止服务→释放显存→启动服务→等待就绪...），但前端完全没展示

#### 🟡 P1：系统拓扑页无入口

`topology.js` 实现了完整的拓扑图（GPU→容器→模型→任务四层）和健康度评分（5维度+环形进度条+Top问题），但**侧边栏没有这个页面的入口**，用户无法访问。需要在index.html侧边栏添加"系统拓扑"导航项。

#### 🟡 P1：模型登记台缺评测数据

- 后端有完整的模型评测台帐（`docs/模型评测台帐.md`，10分制评分），但前端模型卡片只显示"类别/来源/状态/显存"，**没有评分、能力标签、推荐场景**
- ComfyUI模型的 `loaded` 状态永远是 `false`（代码注释："ComfyUI 模型加载状态需要单独查询"，但一直没做）
- "详情"按钮无onclick，无法查看模型详细信息

#### 🟡 P1：诊断中心多个交互无效

- "查看关联事件(N)"按钮无onclick
- 时间线类别筛选下拉框无onchange
- 故障场景库5个场景（FC-001~FC-005）是前端硬编码的，没有从 `/api/diagnose/rules` 获取
- 诊断结果的"处置建议"是纯文本，没有"一键执行"按钮

## 四、代码质量问题

### 4.1 pages.js 过大（1846行）

虽然平均每页约200行（可接受），但单文件包含9个页面导致：
- 查找特定页面代码困难
- 多人协作易冲突
- 无法按需加载

**建议**：拆分为 `pages/dashboard.js`、`pages/diagnose.js`、`pages/alerts.js`、`pages/models.js`、`pages/vram.js`、`pages/scenes.js`、`pages/queue.js`、`pages/guard.js`、`pages/settings.js`、`pages/audit.js`，每个文件约150-250行。

### 4.2 全局变量hack

**`window._serviceVramMap`**（pages.js L204）：
```javascript
// 在模板字符串的IIFE中计算并存到window
window._serviceVramMap = serviceVramMap;
// 之后在另一个模板字符串中读取
const sv = window._serviceVramMap || {};
```
这是因为模板字符串渲染时无法在两个独立的 `${...}` 块间传递变量。**应该先计算好所有数据，再一次性渲染模板**。

### 4.3 模块级可变状态

- `Pages._allModels = []`（L810）
- `Pages._loadedModels = []`（L811）
- `TopologyPage._selectedNode`、`_topologyData`、`_healthData`

这些应该通过 `State.set()` 管理，而不是挂在模块对象上。

### 4.4 大量内联样式

pages.js 中估计有超过100处 `style="..."`，例如：
```html
<div style="font-size:24px;font-weight:700">
<button style="width:180px">
<div style="max-height:500px;overflow-y:auto">
```
应该定义CSS类（如 `.text-xl`、`.w-48`、`.scroll-y`），保持样式与结构分离。

### 4.5 事件绑定方式不统一

混用三种方式：
1. 内联onclick：`<button onclick="Pages._serviceAction('ollama', 'stop')">`
2. 渲染后绑定：`Utils.$('#btn-refresh').onclick = () => ...`
3. addEventListener：`Utils.$('#model-search').addEventListener('input', ...)`

建议统一为渲染后绑定（方式2），内联onclick需要函数挂在全局，不利于模块化。

### 4.6 无前端错误边界

任何页面渲染函数抛出异常都会导致白屏。建议在 `Router._handle()` 中包裹 try-catch，渲染失败时显示错误提示页而非白屏。

### 4.7 API层缺少重试和超时

`API.request()` 没有请求超时设置（fetch默认无超时），也没有失败重试机制。后端服务可能因显存操作而响应缓慢，前端应设置合理超时（如30秒）并在关键操作上支持重试。

## 五、用户体验问题

### 5.1 无实时数据推送

当前数据更新完全依赖：
- 页面加载时请求一次
- 用户手动点"刷新"按钮
- dashboard页有10秒轮询（但其他页面没有）

后端有 `event_bus` 和 `/api/events/timeline`，但前端**没有WebSocket或SSE订阅**。显存变化、任务进度、告警触发都不能实时反映到UI上。

**建议**：
- 短期：所有页面统一5-10秒轮询关键数据
- 中期：后端增加SSE端点 `/api/events/stream`，前端订阅后实时更新状态

### 5.2 无全局loading状态

API请求期间页面可能空白或显示旧数据。建议在 `API.request()` 中维护全局请求计数器，在顶栏显示加载指示器。

### 5.3 长操作无进度反馈

以下操作可能耗时>10秒，但前端只有一个Toast"正在..."：
- 场景切换（10-60秒）
- 模型加载（5-30秒）
- 显存释放（2-10秒）
- 任务提交后生成（30秒-数分钟）

**建议**：统一使用"任务进度"组件——提交后返回task_id，前端轮询进度并显示进度条+当前步骤。

### 5.4 空状态缺乏引导

多个页面的空状态只有"暂无数据"，没有引导用户下一步做什么。例如：
- 任务队列空：应该显示"去提交一个任务"按钮
- 模型登记台空：应该显示"扫描新模型"按钮
- 告警中心空：应该显示"系统运行正常"的积极反馈

### 5.5 危险操作确认不一致

- 卸载模型：有Modal.confirm ✅
- 一键释放显存：有Modal.confirm ✅
- 驱逐进程：有Modal.confirm ✅
- 停止服务：**直接执行，无确认** ❌
- 取消任务：有Modal.confirm ✅
- 切换场景：有Modal.confirm ✅

建议所有破坏性操作统一确认。

## 七、改进建议（按优先级排序）

### 第一阶段：补P0功能缺口（2-3天）

#### 1. 让设置页"真"起来
- 系统配置：对接 `/api/status` 读取真实端口/地址，保存调用配置更新API
- 服务管理：从 `/api/status` 获取真实容器状态，重启/停止按钮对接 `/api/service` 和 `/api/container/stop`
- QoS配置：从 `/api/qos/status` 读取真实阈值，保存调用 `/api/qos/config`（如存在）
- 自动防死机：从 `/api/auto-protect/status` 读取状态，开关对接 `/api/auto-protect/config`
- 看门狗：从后端获取真实PID和运行时长（需要新增API或从status中取）
- 账号管理：修改密码对接 `/api/auth/change-password`
- 所有"保存"按钮绑定真实事件

#### 2. 完善任务队列
- 提交前调用 `/api/admission` 做显存预算预检，根据结果显示"显存充足/紧张/不足"
- 模型列表从 `/api/registry` 动态获取
- 提交后每3秒轮询 `/api/queue` 更新进度
- "清空已完成"和"查看"按钮绑定事件
- 任务完成后显示结果（生成的图片/视频缩略图）

#### 3. 给拓扑页加入口
- 在index.html侧边栏添加"系统拓扑"导航项（建议放在"总览"后面）
- 路由注册 `/topology` → `TopologyPage.render()`

### 第二阶段：补P1功能（2-3天）

#### 4. 场景切换进度反馈
- 场景列表从 `/api/scene` 获取（后端返回场景配置+服务列表+预估显存）
- 切换时显示进度弹窗："正在停止服务... → 正在释放显存... → 正在启动服务... → 等待就绪..."
- 后端 `scene_switch()` 已有步骤回调，前端通过轮询或SSE获取当前步骤

#### 5. 模型登记台增强
- ComfyUI模型加载状态：调用ComfyUI API查询已加载模型（或从 `/api/status` 的gpu_processes推断）
- 模型卡片增加评分显示（从模型评测台帐读取，需要后端提供API）
- "详情"按钮打开Modal显示模型完整信息（参数/能力/评测结果/推荐场景）
- 增加"手动登记"按钮，对接 `/api/scan/register`

#### 6. 诊断中心交互修复
- "查看关联事件"按钮：打开Modal显示该根因关联的事件列表
- 时间线筛选：绑定onchange事件，过滤显示
- 故障场景库：从 `/api/diagnose/rules` 获取，而非硬编码
- 处置建议增加"一键执行"按钮（对接 `/api/qos/execute`）

### 第三阶段：体验优化（2天）

#### 7. 实时数据推送
- 所有页面统一5秒轮询 `/api/status`（只在页面可见时轮询，用 `document.visibilityState` 判断）
- 后端增加SSE端点 `/api/events/stream`，前端订阅后实时更新告警/事件/任务进度

#### 8. 全局loading和错误边界
- `API.request()` 维护请求计数器，顶栏显示加载指示器
- `Router._handle()` 包裹try-catch，渲染失败显示错误页（含"刷新"按钮）

#### 9. pages.js拆分
- 按页面拆分为10个独立文件
- 公共函数（_calcVramSegments, _getVramBreakdown, _getEventDescription）抽到 `core/vram.js` 或 `core/format.js`

#### 10. 代码质量清理
- 消除 `window._serviceVramMap` hack（先算数据再渲染）
- 内联样式提取为CSS类
- 统一事件绑定方式
- 模块级状态迁入State

## 八、功能设计层面的建议（超出代码审计）

### 8.1 建议增加"一键诊断"入口

当前诊断中心需要手动选择告警类型和时间窗再点"执行诊断"。建议在总览页的告警横幅上增加"一键诊断"按钮，点击后自动传递告警类型到诊断页并执行诊断，减少用户操作步骤。

### 8.2 建议增加"显存预测"功能

基于 `State.vramHistory` 趋势数据，前端可以简单预测"按当前使用率，X分钟后显存将达到阈值"，在总览页显示预警。这比单纯显示当前值更有价值。

### 8.3 建议场景切换支持"自定义场景"

当前6个场景是预设的，用户无法自定义。建议设置页增加"场景管理"，允许用户添加/编辑/删除场景（定义包含哪些服务、显存预算、描述），后端 `registry.json` 已有场景配置结构。

### 8.4 建议任务队列支持"工作流模板"

当前提交任务需要手动填模型/提示词/尺寸/步数/CFG。建议支持保存常用参数为模板（如"Flux高质量出图"、"Wan2.2短视频"），一键填充。

### 8.5 建议增加"操作撤销"

显存释放、模型卸载、服务停止等操作后，Toast通知中增加"撤销"按钮（5秒内可点击恢复），降低误操作风险。

### 8.6 建议暗色/亮色主题切换

当前只有暗色主题。CSS已有设计令牌系统，增加亮色主题只需新增一套变量值，工作量不大但能显著提升用户体验。

## 九、总结

GMae前端WEBUI的**架构设计质量明显高于功能完成度**。模块化拆分、统一显存账本、SVG图表、事件翻译层等设计决策都很出色，说明开发者有良好的前端架构意识。但功能实现上存在明显的"最后一公里"问题——设置页全假、任务队列半成品、多个按钮无效、拓扑页没入口。

**建议优先级**：
1. **最紧急**：让设置页可用（P0，用户最常访问的页面之一却是摆设）
2. **次紧急**：完善任务队列（P0，核心功能链路）
3. **重要**：场景切换进度反馈 + 拓扑页加入口（P1）
4. **优化**：实时推送 + 错误边界 + pages.js拆分（P2）

预计6-8个工作日可将前端功能完成度从67%提升到90%以上，达到可演示、可交付的水平。
