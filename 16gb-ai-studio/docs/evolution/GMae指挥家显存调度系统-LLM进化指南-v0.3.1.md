## 1. 进化背景与目标

### 1.1 为什么进化

v0.3 的 GMae 是一个**规则引擎级**的显存调度工具：场景切换是硬编码的动作序列，预算引擎是静态查表，门卫驱逐是阈值触发的固定流程。大赛评审视角下，这与"写个 shell 脚本管理显存"没有本质区别，技术创新维度得分受限。

v0.3.1 引入 LLM 认知编排层，将系统从"按规则执行"升级为"理解意图、自主规划、动态决策"的认知系统。

### 1.2 进化目标

1. **技术创新**：从规则引擎升级为 LLM 驱动的认知编排，填补消费级 GPU 智能编排空白
2. **场景落地**：自然语言创作编排，用户一句话即可完成多模态任务序列
3. **通用性**：从"为 16GB 单卡定制"扩展为"支持所有消费级 AI 服务器"
4. **大赛获奖**：目标三等奖以上，综合评分 73-78

### 1.3 核心叙事

**M-Eng（感官）→ C-Eng（大脑）→ P-Eng（身体）**：感知模型能力，理解用户意图，安全执行调度。三者构成"感知→决策→执行"的自主闭环。

### 2.1 引擎职责边界

| 引擎 | 全称 | 角色 | 核心职责 | 不做什么 |
|------|------|------|---------|---------|
| **P-Eng** | Prism Engine | 执行层 | 铁律兜底、显存管理、任务执行、服务编排 | 不做意图理解，不做任务规划 |
| **C-Eng** | Cognitive Engine | 决策层 | 意图理解、任务规划、调度决策、自然语言交互 | 不直接操作硬件，不绕过铁律 |
| **M-Eng** | Model Benchmark Engine | 感知层 | 新模型发现、自动评测、能力数据维护 | 不做调度决策，不影响用户任务 |

### 2.2 进程边界

- **C-Eng 独立进程**（端口 8789），通过 HTTP 调用 P-Eng
- **P-Eng 独立进程**（端口 8787），M-Eng 作为 P-Eng 内后台线程运行
- 两进程各自有看门狗、日志、启动/停止脚本
- C-Eng 故障不影响 P-Eng；P-Eng 故障时 C-Eng 降级为"只读+提示"

## 3. C-Eng 认知引擎设计

### 3.1 定位与边界

C-Eng 是 LLM 驱动的调度大脑，用户用自然语言表达创作意图，C-Eng 理解意图、规划多模态任务序列、动态管理显存资源，P-Eng 负责安全执行。

**边界**：
- 不重写 P-Eng——P-Eng 的铁律引擎/预算引擎/门卫/队列全部保留
- 不替代用户手动操作——手动场景切换、手动提交任务仍然可用，C-Eng 是"自动驾驶"选项
- 不引入 DSH 运行时——用 DSH 的架构思想（插件化 Tool、Session Log、Capability Seam），代码轻量自研
- 不是通用 Agent——只做 GPU 资源编排 + 多模态创作任务规划

### 3.2 LLM 推理后端

#### 3.2.1 Provider 抽象层

C-Eng 不直接调用特定 API，通过统一 `LLMProvider` 接口：

```
LLMProvider（抽象接口）
  ├── OllamaProvider（本地，支持任意 Ollama 模型）
  ├── OpenAICompatProvider（云端，兼容 DeepSeek/通义/Kimi/智谱/OpenAI）
  └── （预留）AnthropicProvider / GeminiProvider
```

接口定义：`chat(messages, tools, temperature, max_tokens) → LLMResponse` + `health_check() → bool`

#### 3.2.2 三档推理策略

| 档位 | 后端 | 模型 | 显存 | 速度 | 能力 | 适用场景 |
|------|------|------|------|------|------|---------|
| **L1 本地快道** | 本地 Ollama | qwen3.5:0.8b (64K) | 3.5G | ~3秒 | 足够 | 单步任务、状态查询、简单切换 |
| **L2 云端深道** | 用户配置API | DeepSeek-V3（默认）/ 用户自选 | **0G** | ~2-5秒 | **最强** | 多步编排、异常恢复、复杂规划 |
| **L3 本地深道** | 本地 Ollama | qwen3.5:9b (128K) | 9.9G | ~12秒 | 强 | 云端不可用时的降级 |

**档位选择逻辑**：
- 简单任务（单步/查询/已知场景切换）→ L1 本地快道
- 复杂任务（多步/多模态/异常恢复）→ 云端可用则 L2，不可用则 L3
- 显存极度紧张（>13G）→ 云端可用则 L2（0显存最佳），不可用则纯规则模式

**调用参数**：`think: false`（必须，Qwen3.5 默认 think 会空回复），`temperature: 0.2`，`max_tokens: 1024`

#### 3.2.3 实测模型数据（2026-08-29，RTX 4060 Ti 16GB）

| 模型 | Context | 显存 | 生成速度 | 工具调用 | 多模态 | 综合 |
|------|---------|------|---------|---------|--------|------|
| qwen3.5:0.8b | 64K | 3.5G | 155 tok/s | A-（JSON规范） | ✅ OCR 100% | A |
| qwen3.5:0.8b | 256K | 6.6G | 155 tok/s | A- | ✅ | A |
| qwen3.5:9b | 128K | 9.9G | 43 tok/s | A（JSON规范） | ✅ | A |
| gemma4:12b-it-q4 | 64K | 10.4G | 30 tok/s | A（JSON数组规范） | ✅ vision+audio | A |
| minicpm5-1b | 128K | 5.4G | 231 tok/s | B+（格式不标准） | 无 | A- |

**快道选型结论**：qwen3.5:0.8b 是唯一正确选择——工具调用 JSON 规范（minicpm5 系列格式不标准），64K 仅 3.5G（比 0.6b 的 5.4G 还省），多模态能力可做图像理解，262K 上下文余量充足。

**深道选型结论**：默认 qwen3.5:9b（稳+快），gemma4:12b 按需做多模态理解（理解生成的图/音后做后续编排）。

#### 3.2.4 Context 大小

默认 **64K（3.5G）**。C-Eng 单次调用上下文实际占用约 4,800 token（System Prompt ~2,100 + 状态快照 ~450 + 用户输入 ~100 + 历史决策 ~400 + few-shot ~800 + 输出 ~800），64K 使用率仅 7%，完全够用。

更小的 context（16K/32K）无实测数据验证，且只省 0.5-1G，收益不大。

**自指管理**：Flux 独占（13G）时，如配置了云端 API 则复杂决策走云端（0显存）；未配置则临时卸载 0.8b，Flux 任务完成后重新加载（约 5-10 秒）。

### 3.3 单阶段决策流程

意图理解与调度决策**合并**为一次 LLM 调用（0.8b 一条龙），复杂任务自动升级深道重规划。

```
用户输入（自然语言）
  │
  ▼
[1] 构建上下文
  - System Prompt（角色+铁律+Tool Schema+输出格式+2个few-shot示例）
  - 实时状态快照（从 P-Eng GET /api/status 获取，不缓存）
  - 最近2条历史决策
  - 用户原始输入
  │
  ▼
[2] L1 0.8b 单次调用（~3秒）
  同时完成：意图理解 → 任务拆解 → 资源评估 → 行动序列规划
  输出结构化 JSON：
  {
    "intent": "multimodal_creation",
    "tasks": [...],
    "plan": [
      {"step":1, "tool":"switch_scene", "args":{...}, "reason":"..."},
      {"step":2, "tool":"submit_task", "args":{...}, "reason":"..."}
    ],
    "estimated_vram_peak": 13.5,
    "confidence": 0.85,
    "needs_deep": false
  }
  │
  ▼
[3] 深道判断
  ├─ needs_deep=false 且 confidence≥0.7 → 进入校验
  └─ needs_deep=true 或 confidence<0.7 → 深道重规划
       ├─ 云端可用 → L2 云端 API（0显存，~2-5秒）
       └─ 云端不可用 → 临时加载9b（~12秒），用毕即卸
  │
  ▼
[4] P-Eng 安全校验（逐步骤，三道防线）
  防线1：格式校验（C-Eng侧，<10ms）
  防线2：铁律校验（P-Eng准入闸门，R1-R8）
  防线3：预算校验（P-Eng /api/budget 实时计算，不信任LLM数字）
  ├─ 全部通过 → 进入执行
  └─ 任一不通过 → 反馈具体原因给LLM，最多重试2次；2次失败则中止
  │
  ▼
[5] 用户确认（默认每次确认）
  前端展示规划步骤+显存峰值+预计耗时
  设置中可改为"自动执行"，高风险操作仍需确认
  │
  ▼
[6] 执行（C-Eng 逐步骤调用 P-Eng API）
  每步：调用Tool → 记录结果 → 失败则重试/换方案/中止
  L0反射弧独立：显存飙升时 P-Eng 自动中断释放，不等待C-Eng
  │
  ▼
[7] 完成 + 决策归档
  完整决策链写入决策日志
  通知用户，附生成结果路径
```

### 3.4 Tool 层（HTTP 调用 P-Eng）

C-Eng 不直接操作硬件，全部通过 P-Eng REST API。Tool 是 LLM 与 P-Eng 之间的唯一接口。

| Tool | 功能 | P-Eng API | 权限 |
|------|------|-----------|------|
| `get_system_status` | 显存/场景/模型/队列全景 | GET /api/status | 只读 |
| `get_model_budget` | 指定模型显存预算与可行性 | GET /api/budget | 只读 |
| `list_models` | 已登记模型列表 | GET /api/registry | 只读 |
| `switch_scene` | 切换场景 | POST /api/scene | 写（过闸门） |
| `submit_task` | 提交生成任务 | POST /api/queue | 写（过闸门） |
| `cancel_task` | 取消队列任务 | POST /api/queue/cancel | 写 |
| `get_task_status` | 任务进度 | GET /api/queue/{id} | 只读 |
| `free_vram` | 主动释放显存 | POST /api/free | 写（过闸门） |
| `evict_process` | 强制驱逐进程 | POST /api/guard/kick | 高风险（用户确认） |
| `get_advice` | P-Eng 智能建议（参考输入） | GET /api/advice | 只读 |

**设计要点**：
- 每个 Tool 的 JSON Schema 注入 System Prompt，包含**显存代价提示**（如 `switch_scene(flux)` 描述里写"需约13G显存，会自动卸载对话模型"）
- 只读 Tool 直接返回，写操作必须过 P-Eng 准入闸门
- 高风险 Tool（evict_process）执行前必须弹用户确认框
- C-Eng 内置 P-Eng API client，处理超时（默认10秒）、重试（最多2次）、错误解析

### 3.5 安全兜底（三道防线 + 熔断）

#### 三道防线

1. **格式校验**（C-Eng 侧）：JSON 合法 + 字段完整 + action 在白名单内
2. **铁律校验**（P-Eng 准入闸门）：R1-R8 逐条检查，返回 `{allowed, reason, required_free_gb}`
3. **预算校验**（P-Eng 预算引擎）：实时 nvidia-smi 数据 + registry 实测值，不信任 LLM 输出的数字

**核心原则**：所有数值从 P-Eng 实时查询，永远不信任 LLM 输出的数字。

#### 熔断机制

| 触发条件 | 行为 |
|---------|------|
| 连续3次决策被拦截 | 本次任务中止，提示"智能决策未通过安全校验，请手动操作" |
| C-Eng 进程崩溃 | 独立看门狗5秒重启，重启后进入"纯规则模式" |
| P-Eng 连续3次超时 | C-Eng 进入"只读模式"，只能查询不能执行 |
| Ollama 不可用 | C-Eng 完全不可用，前端提示"本地大模型未启动" |
| 所有推理后端不可用 | 纯规则模式，P-Eng 照常工作 |

**铁律**：C-Eng 的任何故障都不能导致 P-Eng 不可用，更不能导致系统死机。

### 3.6 隐私分级（云端推理时）

C-Eng 调用云端 API 前经过 `PrivacyFilter`：

| 级别 | 内容 | 可否发云端 | 处理 |
|------|------|-----------|------|
| 🟢 公开级 | 显存量、GPU型号、场景名、模型名、队列深度、进程名 | ✅ | 直接发送 |
| 🟡 敏感级 | 用户创作 prompt 文本、生成文件名 | ⚠️ 可选 | 默认不发；用户开启"发送创作内容"才发 |
| 🔴 禁止级 | API Key、用户密码、生成的图片/音频内容、个人文件路径 | ❌ | 永远过滤 |

默认行为：云端推理只接收"系统资源状态 + 任务类型"，不接收具体创作内容。用户可在设置中开启"允许发送创作内容到云端以获得更智能的编排"（默认关）。

### 3.7 决策日志

复用 P-Eng 结构化日志系统，新增 `decision` 事件类型，写入 `ceng-decision.log`（按天轮转，保留7天）。

每条记录：`turn_id, timestamp, user_input, state_snapshot, llm_model, llm_prompt_tokens, llm_output_tokens, latency_ms, llm_output, validation_results, execution_log, result, total_duration_s, vram_peak`。

完整 prompt 存7天，7天后自动清理 prompt 字段只留元数据。可通过 `turn_id` 回放完整决策过程。

### 3.8 前端交互

**入口**：Dashboard 页显存水位条旁加"🤖 智能编排"按钮；Queue 页加"自然语言描述"切换。

**对话框流程**：
1. 用户输入 → "思考中...（0.8b）"
2. 规划完成 → 展示步骤列表（每步带 reason）+ 显存峰值 + 预计耗时
3. 用户确认/修改/取消 → 执行中实时显示进度+显存变化
4. 完成 → 结果路径 + "查看决策详情"链接

**设置页"智能编排"区**：启用开关、推理后端管理、默认后端、自动执行/每次确认、决策日志保留天数、高风险确认开关、发送创作内容到云端开关。

## 4. M-Eng 模型自感知引擎设计

### 4.1 定位

类似 Immich 上传图片后自动后台识别人脸/OCR，GMae 在用户安装新模型后，**自动在后台评测该模型在本机的真实表现**（显存、速度、能力、多模态），结果自动写入 registry 和模型档案。

M-Eng 是 C-Eng 决策质量的基础——C-Eng 依赖 registry 里的真实数据，没有 M-Eng，C-Eng 就是"盲人调度"。

### 4.2 触发机制

- **自动**：`/api/scan` 发现新模型 → 自动创建 P0 评测任务；已有模型缺关键指标 → 自动补测；模型文件变更 → 自动重测
- **手动**：模型登记台卡片"重新评测"按钮；`POST /api/benchmark`

### 4.3 三级评测

| 级别 | 内容 | 耗时 | 自动触发 |
|------|------|------|---------|
| **P0 基础指标** | 多档显存、prefill速度、生成速度、加载时间 | ~2min | 新模型发现后 |
| **P1 能力评测** | 中文/英文/计算/编程/工具调用（22题统一Prompt集） | ~5min | P0完成后空闲时 |
| **P2 多模态** | 图像描述/OCR/图像问答/图表/音频（如模型声明多模态） | ~3min | P1完成后，多模态模型 |

复用现有 `scripts_global/model_bench_*.ps1`，M-Eng 负责调度+结果解析+归档，不重写评测逻辑。

### 4.4 执行时机

- 默认窗口：夜间 00:00-06:00 + 系统空闲（显存<4G 且队列空）
- 设置可改为"任意空闲时间"
- 用户任务到达时立即暂停评测、释放显存，从中断处恢复（P0已测档位不重测）
- 评测任务走 P-Eng 队列，受铁律约束

### 4.5 结果输出

1. **自动覆盖 registry.json 实测字段**（vram/speed/ability/score），人工字段（描述/许可证/作者）不覆盖
2. **生成/更新模型档案** `docs/models/<model>.md`（复用现有模板）
3. **前端通知**：toast "模型 xxx 评测完成，评分 8.5"，登记台显示"已评测"徽章

### 4.6 无实测数据时的估算

```
峰值显存 ≈ 模型文件大小 × (1 + 中间计算比例) + 底噪
  LLM: +15%（KV cache）
  T2I: +25%（VAE+注意力）
  T2V: +40%（时序注意力）
  T2A: +25%
```
估算值标注为"估算"，M-Eng 评测后替换为实测值。

## 5. P-Eng 执行引擎强化

C-Eng 是"大脑"，P-Eng 是"身体"。大脑再聪明，身体不稳也白搭。v0.3.1 对 P-Eng 做三支柱强化。

| 场景切换加速 | 量化每场景切换耗时；跳过不必要步骤；目标<10秒（不含模型加载） |

### 5.3 支柱三：牢固

| 任务 | 交付 |
|------|------|
| 操作审计日志 | 所有写操作记录 `{timestamp, user, action, args, before_state, after_state, result}` 到 audit.log，保留90天 |
| 铁律完备性审查 | R1-R8 逐条审查代码覆盖，每条至少2个测试用例；铁律测试覆盖率100% |

### 5.4 硬件抽象与动态阈值

**启动时 HardwareProbe 自动探测**：
- GPU：nvidia-smi 获取型号、显存、数量、驱动版本
- 底噪：空载时连续5次测量取平均
- 内存：总 RAM、可用 RAM
- OS：Windows / Linux、Docker 是否可用
- 生成 `hardware_profile.json`

**动态阈值**（替换硬编码的 16GB 阈值）：
```python
SAFE_THRESHOLD = vram_total * 0.85
DANGER_THRESHOLD = vram_total * 0.92
CRITICAL_THRESHOLD = vram_total * 0.97
FREE_TARGET = max(2.0, vram_total * 0.15)
```

多卡数据结构预留（按 GPU index 分别管理），MVP 只实现单卡调度。

### 5.5 服务适配器

```
ServiceAdapter（统一接口）：
  detect() → 扫描常见端口+Docker容器名
  get_vram_usage() → 当前显存占用
  free_vram() → 释放显存
  submit_task(workflow) → 提交生成任务
  get_task_status(task_id) → 查询进度
  health_check() → 服务是否可用

MVP 实现：ComfyUIAdapter、OllamaAdapter、FooocusAdapter
预留：SD.WebUI、vLLM、LM Studio
```

首次启动自动扫描常见端口和 Docker 容器，发现的服务自动注册，未发现的提示用户配置。未安装服务优雅降级（相关功能灰显）。

## 9. 评测指标（大赛量化数据）

### 9.1 对比实验：纯规则 vs 认知编排

10 个测试任务，两种模式各跑 3 次取平均：

| 指标 | 纯规则 | 认知编排 | 预期 |

| 显存峰值 | 基线 | ≈基线 | 都受铁律约束 |
| OOM次数 | 0 | 0 | P-Eng兜底 |
| 用户操作步骤数 | 基线 | 显著更少 | 1句自然语言 vs 多次手动 |
| 决策可解释性 | N/A | 有reason链 | 认知模式独有 |

- 新模型发现到 P0 评测完成的平均耗时
- 评测结果与手动评测的偏差率（目标 <5%）
- 用户任务抢占后评测恢复成功率（目标 100%）
