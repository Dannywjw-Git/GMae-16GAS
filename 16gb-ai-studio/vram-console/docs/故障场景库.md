# GMae 故障场景库

> **版本**：v1.0（2026-09-02）
> **用途**：定义 16GAS 系统的常见故障场景、告警模板、处置步骤和预防建议，为告警管理器（AlertManager）和根因推断规则引擎（RuleEngine）提供场景依据。
> **关联**：S3.1 故障场景库文档；对应根因规则 RC-001~RC-009；对应告警规则 ALERT-001~ALERT-005。

---

## 场景总览

| 场景 ID | 名称 | 告警级别 | 对应根因规则 | 处置难度 |
|---------|------|---------|-------------|---------|
| FC-001 | 显存耗尽/OOM 风险 | critical | RC-001/002/003/005 | 中 |
| FC-002 | 容器异常退出/频繁重启 | warning | RC-006 | 中 |
| FC-003 | 推理延迟升高 | warning | RC-007 | 低 |
| FC-004 | 任务队列堆积 | warning | RC-008 | 低 |
| FC-005 | 服务不可达 | critical | RC-009 | 高 |

## FC-001：显存耗尽/OOM 风险

### 触发条件
- `free_vram < 1GB` 持续 10 秒
- 检测频率：每 5 秒检查一次
- 触发来源：QoS 引擎状态跃迁（ok→emergency）+ 事件总线 vram 类别事件

### 告警模板
- **级别**：critical
- **标题**：显存耗尽风险
- **内容**：显存剩余 {free_mb}MB，已持续 {duration}秒，存在 OOM 死机风险
- **对应根因规则**：RC-001（ComfyUI 任务溢出）/ RC-002（大模型加载）/ RC-003（Fooocus 显存未释放）/ RC-005（桌面应用占用）
- **告警类型**：`vram_critical`

### 处置步骤（可执行）

1. **预览释放**：查看当前显存占用和可释放资源
   ```bash
   curl -H "X-API-Key: $TOKEN" http://127.0.0.1:8787/api/status | jq '.data.vram_ledger'
   ```

2. **一键释放 L1**（释放未使用模型，最安全）：
   ```bash
   curl -X POST -H "X-API-Key: $TOKEN" -H "Content-Type: application/json" \
     -d '{"level": "L1"}' http://127.0.0.1:8787/api/free
   ```

3. **如仍 critical，释放 L2**（释放 ComfyUI 生成模型显存）：
   ```bash
   curl -X POST -H "X-API-Key: $TOKEN" -H "Content-Type: application/json" \
     -d '{"level": "L2"}' http://127.0.0.1:8787/api/free
   ```

4. **如仍 critical，切换到 idle 场景**（停止所有 AI 服务）：
   ```bash
   curl -X POST -H "X-API-Key: $TOKEN" -H "Content-Type: application/json" \
     -d '{"scene": "idle"}' http://127.0.0.1:8787/api/scene
   ```

5. **验证**：确认 free_vram > 4GB
   ```bash
   curl -H "X-API-Key: $TOKEN" http://127.0.0.1:8787/api/status | jq '.data.vram_ledger.free_mb'
   ```

### 验证方法
- 处置后 10 秒内 `free_vram > 4GB`
- 告警自动消除（`/api/alerts` 中该告警消失）
- 无 OOM 崩溃（系统未死机，服务正常响应）

### 预防建议
- 避免同时加载多个大模型（>7B）
- 生成高分辨率内容前先检查显存（`/api/status`）
- 启用自动防死机（`/api/auto-protect/config`，默认关闭，建议 standard 模式）
- 桌面应用（游戏/浏览器）使用完毕后及时关闭，避免占用显存
- Fooocus 使用完毕后切换到不含 Fooocus 的场景，避免显存残留

## FC-002：容器异常退出/频繁重启

### 触发条件
- 5 分钟内 `container_die` 事件 ≥ 3 次（同一容器）
- 检测频率：事件总线实时监听 container 类别事件
- 触发来源：Docker Events 监听（S2.4）+ 事件统计

### 告警模板
- **级别**：warning
- **标题**：容器异常退出
- **内容**：容器 {container_name} 在 5 分钟内异常退出 {count} 次，可能存在 OOM 或配置错误
- **对应根因规则**：RC-006（容器异常退出/频繁重启）
- **告警类型**：`container_crash_loop`

### 处置步骤（可执行）

1. **查看容器日志**：
   ```bash
   docker logs --tail 50 {container_name}
   ```

2. **检查是否 OOM killed**：
   ```bash
   docker inspect {container_name} | jq '.[0].State.OOMKilled'
   ```

3. **如 OOM killed，释放显存后重启容器**：
   ```bash
   curl -X POST -H "X-API-Key: $TOKEN" -H "Content-Type: application/json" \
     -d '{"level": "L1"}' http://127.0.0.1:8787/api/free
   docker restart {container_name}
   ```

4. **如非 OOM，检查容器配置和依赖**：
   ```bash
   docker inspect {container_name} | jq '.[0].Config.Env'
   docker ps -a --filter name={container_name}
   ```

5. **如持续崩溃，暂时停止容器并记录**：
   ```bash
   docker stop {container_name}
   ```

### 验证方法
- 重启后容器稳定运行 > 5 分钟（无新的 die 事件）
- 容器健康检查通过（`/api/status` 中该容器 ok=true）
- 告警自动消除或手动 resolve

### 预防建议
- 容器启动前检查显存是否充足（`/api/status`）
- 避免在显存紧张时启动多个大容器
- 定期检查容器日志，及时发现潜在问题
- 重要容器配置重启策略（`restart: unless-stopped`）
- 容器版本升级前先在测试环境验证

## FC-003：推理延迟升高

### 触发条件
- 最近 3 次推理响应时间 > 阈值（LLM > 30秒 / 图生成 > 120秒）
- 检测频率：每次推理完成时记录耗时，滑动窗口统计
- 触发来源：任务队列完成事件 + 响应时间统计

### 告警模板
- **级别**：warning
- **标题**：推理延迟升高
- **内容**：{model} 最近 {count} 次推理平均耗时 {avg_seconds}秒，超过阈值 {threshold}秒
- **对应根因规则**：RC-007（推理延迟升高）
- **告警类型**：`inference_latency_high`

### 处置步骤（可执行）

1. **检查当前显存状态**：
   ```bash
   curl -H "X-API-Key: $TOKEN" http://127.0.0.1:8787/api/status | jq '.data.vram_ledger'
   ```

2. **如显存不足，释放空闲模型**：
   ```bash
   curl -X POST -H "X-API-Key: $TOKEN" -H "Content-Type: application/json" \
     -d '{"level": "L1"}' http://127.0.0.1:8787/api/free
   ```

3. **降低模型参数或 context 长度**：
   - LLM：降低 context 长度（如从 8192 降到 4096）
   - 图生成：降低分辨率（如从 1024x1024 降到 768x768）或步数（如从 30 降到 20）

4. **切换到小模型**（如 qwen3:0.6b 替代 qwen3.5:9b）：
   ```bash
   curl -X POST -H "X-API-Key: $TOKEN" -H "Content-Type: application/json" \
     -d '{"name": "qwen3:0.6b", "action": "load"}' http://127.0.0.1:8787/api/model
   ```

5. **验证**：重新执行推理，确认耗时 < 阈值

### 验证方法
- 后续 3 次推理平均耗时 < 阈值
- 显存充足（free_vram > 4GB）
- 告警自动消除或手动 resolve

### 预防建议
- 大模型推理前先检查显存，避免显存交换（swap）导致延迟
- 合理设置 context 长度，避免过长 context 导致推理慢
- 图生成时根据显存选择合适的分辨率和步数
- 定期清理未使用的模型，释放显存
- 监控推理耗时趋势，提前发现性能退化

## FC-004：任务队列堆积

### 触发条件
- ComfyUI 队列 pending > 5 持续 30 秒
- 检测频率：每 10 秒检查一次队列状态
- 触发来源：任务队列状态查询 + 事件总线 task 类别事件

### 告警模板
- **级别**：warning
- **标题**：任务队列堆积
- **内容**：ComfyUI 队列当前 pending {pending_count} 个任务，已持续 {duration}秒，可能 worker 卡住或生成速度慢
- **对应根因规则**：RC-008（任务队列堆积）
- **告警类型**：task_queue_backlog

### 处置步骤（可执行）

1. **查看队列状态**：
   ```bash
   curl -H "X-API-Key: $TOKEN" http://127.0.0.1:8787/api/queue | jq '.data'
   ```

2. **取消低优先级任务**（如测试任务、重复任务）：
   ```bash
   curl -X POST -H "X-API-Key: $TOKEN" -H "Content-Type: application/json" \
     -d '{"id": "{task_id}"}' http://127.0.0.1:8787/api/queue/cancel
   ```

3. **检查 ComfyUI worker 是否卡住**：
   ```bash
   docker logs --tail 20 comfyui
   ```

4. **如 worker 卡住，重启 ComfyUI**：
   ```bash
   docker restart comfyui
   ```

5. **验证**：队列 pending 数下降到 < 5

### 验证方法
- 队列 pending 数 < 5 持续 30 秒
- 新提交的任务能正常开始执行
- 告警自动消除或手动 resolve

### 预防建议
- 避免一次性提交大量任务（建议批量 < 5）
- 高优先级任务优先提交，低优先级任务错峰提交
- 定期检查队列状态，及时发现堆积
- ComfyUI worker 异常时及时重启
- 监控生成速度，如持续变慢考虑优化模型或参数

## FC-005：服务不可达

### 触发条件
- health check 连续 3 次失败（间隔 10 秒）
- 检测频率：每 10 秒一次健康检查
- 触发来源：服务健康探测引擎（observability.health_probe）

### 告警模板
- **级别**：critical
- **标题**：服务不可达
- **内容**：服务 {service_name} 健康检查连续 {count} 次失败，可能已崩溃或端口被占用
- **对应根因规则**：RC-009（服务不可达）
- **告警类型**：service_unreachable

### 处置步骤（可执行）

1. **检查服务进程状态**：
   ```bash
   docker ps -a --filter name={service_name}
   ```

2. **检查端口是否被占用**：
   ```bash
   netstat -ano | findstr :{port}
   ```

3. **如容器已停止，重启容器**：
   ```bash
   docker restart {service_name}
   ```

4. **如端口被占用，查找并停止占用进程**：
   ```bash
   netstat -ano | findstr :{port}
   taskkill /PID {pid} /F
   ```

5. **查看服务日志定位崩溃原因**：
   ```bash
   docker logs --tail 50 {service_name}
   ```

6. **验证**：服务健康检查通过
   ```bash
   curl http://127.0.0.1:{port}/health
   ```

### 验证方法
- 服务健康检查连续 3 次通过
- 服务正常响应 API 请求
- 告警自动消除或手动 resolve

### 预防建议
- 重要容器配置重启策略（`restart: unless-stopped`）
- 定期检查服务健康状态，及时发现异常
- 避免端口冲突（启动新服务前检查端口占用）
- 服务版本升级前先备份配置，升级后验证健康
- 监控系统资源（CPU/内存/磁盘），避免资源耗尽导致服务崩溃
